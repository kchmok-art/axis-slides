### AgentOps (에이전트옵스)

`Agent` · AI Agent Operations · 추가 2026-10-31

> **셰프에게 장보기·결제까지 맡길 때 — 영수증 검사와 카드 한도 걸기**

**정의** 스스로 도구를 쓰고 일하는 AI 에이전트를 운영하는 일. 무엇을 했는지 기록하고, 권한을 제한하고, 실수·비용·무한 반복을 감시한다.

**자세히**

비유: 셰프에게 요리만이 아니라 장보기·결제·예약 전화까지 맡기면 편하지만, 엉뚱한 걸 사 오거나 카드를 긁을 수 있다. 그래서 영수증을 남기게 하고, 카드 한도를 걸고, 큰 결제는 사장 확인을 받게 한다.  
실제: 에이전트의 모든 행동(도구 호출) 기록과 추적, 권한 제한(허락한 폴더·명령만), 위험한 행동 전 사람 승인, 비용·반복 상한, 결과 평가. LLMOps가 '말을 잘하게' 관리한다면, AgentOps는 '행동을 안전하게' 관리한다. 도구: AgentOps, LangSmith, Langfuse 등.

**흐름**

- ① 권한 정하기 — 할 수 있는 일·폴더·명령
- ② 위험 행동에 승인 지점 걸기
- ③ 모든 행동 기록
- ④ 비용·반복 상한
- ⑤ 결과 평가 — 잘했나, 틀렸나
- ⑥ 규칙·스킬 개선

**헷갈리는 점**

- **흔한 오해** AgentOps vs LLMOps
- **차이** LLMOps = 모델이 '말'을 잘하게(프롬프트·환각·토큰) / AgentOps = 에이전트가 '행동'을 안전하게(권한·승인·기록·상한)
- **기억법** 말 관리(LLMOps) → 손발 관리(AgentOps)

**예시**

- 에이전트가 파일을 지우려 하면 사람 승인 요청
- 같은 작업을 50번 넘게 반복하면 자동 중단(예산 상한)
- 에이전트가 한 일을 단계별 기록으로 남겨 나중에 되짚기
- \[우리 서버 실제 사례\] Hermes에는 강제 푸시·저장소 삭제·핵심 폴더 삭제 등 위험 명령 차단 규칙이 걸려 있다(2026-10-23 설정). 2026-10-26 커리큘럼 수정 명령이 실제로 '사용자 동의 없음'으로 막혔고, 동의를 받은 뒤 안전하게 나눠서 다시 했다

**카톡으로 이해하기**

> **💬 A** AI한테 일을 통째로 맡겨도 돼?
>
> **🙋 B** 똑똑하니까 알아서 잘하겠지?
>
> **💬 A** 똑똑해도 엉뚱한 파일을 지울 수 있어  
> 그래서 권한 제한, 위험한 일은 사람 승인, 행동 기록을 걸어
>
> **🙋 B** 우리도 그래?
>
> **💬 A** 응, 저(Hermes)도 위험 명령은 막혀 있어. 실제로 10/26에 한 번 막혔다가 동의받고 다시 했어

### MCP (Model Context Protocol)

`Agent` · Model Context Protocol · 추가 2026-10-23

**정의** AI 앱이 외부 도구·데이터(파일, DB, 슬랙, 깃허브 등)에 연결할 때 쓰는 공통 규격. Anthropic이 2024년 공개한 오픈 프로토콜.

**자세히**

AI 쪽(클라이언트)과 도구 쪽(MCP 서버)이 같은 규격으로 대화하므로, 한 번 만든 MCP 서버를 여러 AI 앱에서 재사용할 수 있다. Claude Code, Codex 모두 MCP를 지원한다.  

\[lecture\_016 보안 포인트\] MCP 서버는 에이전트의 샌드박스 밖에서 '내 권한 그대로' 실행된다(Claude·Codex 공식 문서 공통). 그래서 폴더를 잠가도 파일 접근 MCP를 연결해 두면 그 경로로 밖을 볼 수 있다. 연결된 MCP 목록을 따로 점검해야 한다.

**흐름**

- ① AI 앱 설정에 MCP 서버 등록
- ② AI가 도구 목록을 받아 옴
- ③ 필요할 때 MCP 서버에 도구 실행 요청
- ④ MCP 서버가 실제 작업(파일·API) 수행
- ⑤ 결과를 AI에게 반환

**헷갈리는 점**

- **흔한 오해** 샌드박스를 켜면 MCP 도구도 같이 갇힌다고 생각함
- **차이** MCP 서버는 별도 프로세스라 샌드박스 밖에서 내 권한으로 돈다. 권한 규칙·서버 목록으로 따로 관리해야 한다
- **기억법** MCP = AI용 USB 포트. 꽂은 장치는 방 잠금과 상관없이 동작한다

**카톡으로 이해하기**

> **💬 A** MCP 알아?
>
> **🙋 B** 요즘 자주 들리던데
>
> **💬 A** AI가 외부 도구에 연결하는 공통 규격이야. AI용 USB 포트 같은 거
>
> **🙋 B** 편하겠다
>
> **💬 A** 근데 보안상 주의할 게 있어  
> MCP 서버는 샌드박스 밖에서 내 권한으로 돌아
>
> **🙋 B** 폴더 잠가도 소용없다는 거야?
>
> **💬 A** 파일 읽는 MCP를 꽂아 두면 그걸로 밖을 볼 수 있어  
> 연결된 MCP 목록도 꼭 점검해야 해

### n8n

`Agent` · n8n (nodemation) · 추가 2026-10-09

> **코드 없이 앱·API·AI를 연결해 자동화 워크플로를 만드는 오픈소스 자동화 도구**

**자세히**

n8n은 노드(블록)를 드래그&드롭으로 연결해 자동화 워크플로를 만드는 도구다. Zapier·Make(Integromat)와 비슷하지만 오픈소스라 자체 서버에 설치해 무제한으로 사용할 수 있다. AI 에이전트·API·DB·슬랙·이메일·구글시트 등 400개 이상의 서비스를 연결할 수 있다.

**흐름**

- ① 트리거 노드 설정(웹훅·스케줄·이메일 등)
- ② 연결할 서비스 노드 추가(슬랙·구글시트·API 등)
- ③ 노드 간 데이터 흐름 연결
- ④ 워크플로 활성화
- ⑤ 트리거 발생 시 자동 실행

**헷갈리는 점**

- **흔한 오해** n8n을 단순 자동화 도구로만 이해하는 경우
- **정확한 뜻** n8n은 AI 에이전트 오케스트레이션까지 가능한 풀스택 자동화 플랫폼
- **vs_zapier** Zapier·Make = 클라우드 유료 / n8n = 자체 서버 설치 무제한 무료
- **기억법** 레고 블록처럼 — 앱과 AI를 연결 블록으로 붙여 워크플로 완성

**예시**

- 구글 폼 응답 → n8n → 슬랙 알림 + 구글시트 자동 저장
- 매일 오전 9시 → n8n → AI가 뉴스 요약 → 이메일 발송
- GitHub PR 생성 → n8n → Jira 이슈 자동 생성 + 팀 알림
- 동아리 신청서 제출 → n8n → 회원 DB 저장 + 환영 이메일 발송
- AI 에이전트 워크플로 — LLM 호출·조건 분기·반복 루프를 시각적으로 설계

**왜 중요한가** AX(AI Transformation)의 핵심 도구 — 코드 없이 업무 자동화 루프를 설계할 수 있어 루프 엔지니어링의 실전 구현 도구로 활용

**카톡으로 이해하기**

> **💬 A** n8n이 뭔지 알아?
>
> **🙋 B** 자동화 도구 아니야?
>
> **💬 A** 맞아! 노드(블록) 연결로 앱들을 연결하고 자동화하는 워크플로 도구야  
> Zapier랑 비슷한데 자체 서버에 설치하면 무제한 무료야
>
> **🙋 B** Zapier랑 차이가 뭐야?
>
> **💬 A** Zapier·Make = 클라우드 유료 / n8n = 서버에 설치하면 무제한 무료  
> 그리고 n8n은 AI 에이전트 오케스트레이션까지 가능해서 더 강력해
>
> **🙋 B** AI 에이전트 연결이 어떻게 돼?
>
> **💬 A** LLM 노드 추가해서 '이 데이터를 AI로 요약해서 슬랙으로 보내' 같은 워크플로 만들 수 있어  
> 레고 블록처럼 앱과 AI를 붙여서 자동화 완성이야

### 검증자 (Verifier)

`Agent` · Verifier · 추가 2026-10-21

**정의** AI가 만든 결과가 진짜 됐는지 확인하는 쪽. 만든 AI가 아닌 테스트·린터·다른 AI가 맡는다.

**자세히**

\[lecture\_015 루프 엔지니어링 입문\]  
핵심 문장: '끝났어요'는 주장이지 증명이 아니다. 루프의 '완료'는 AI의 말이 아니라 검사가 정한다.  

검증 수단:  
- 테스트, 타입 검사, 린터(코드 규칙 검사기)
- 다른 AI의 리뷰(채점 AI) — 만드는 AI와 다른 컨텍스트로 분리

카드뉴스 루프의 2층 검사:  
- 1층 기계 검사 — 글자 수·금칙어·해상도·숫자 출처 (확실히 판정 가능한 것)
- 2층 채점 AI — 훅·한 장 한 메시지·행동 유도 (점수, 9점 이상)
이걸 안 나누면 '생성 버튼 여러 번 누르기'가 된다.  

한계: 수치·날짜가 실제로 맞는지는 AI가 못 본다(출처 표기 여부까지만). 사실 확인은 사람 몫. AI가 테스트를 약하게 고쳐 '통과'하는 꼼수도 있으니 검사는 속일 수 없게 만들어야 한다.

**흐름**

- ① 만드는 AI가 결과 제출 ('다 했어요')
- ② 기계 검사 (테스트·린터·글자 수 등)
- ③ 채점 AI 평가 (기준 점수)
- ④ 미달 → '틀렸어, 다시' 돌려보냄
- ⑤ 통과해야 '완료'
- ⑥ 상한 도달 시 사람 호출

**헷갈리는 점**

- **흔한 오해** AI에게 '스스로 검토해'라고 하면 검증이 된다고 생각함(자기 채점)
- **차이** 자기 채점은 같은 머리가 자기 답을 맞다고 하는 것. 검증자는 만든 쪽과 떨어진 별도 검사
- **기억법** 학생이 자기 시험지를 채점하지 않는다 — 채점은 선생님(검증자)이 한다

**카톡으로 이해하기**

> **💬 A** AI가 '다 했어요' 하면 믿어도 돼?
>
> **🙋 B** 다 했다는데 믿어야지?
>
> **💬 A** 그건 주장이지 증명이 아니야. 그래서 검증자가 필요해
>
> **🙋 B** 검증자가 누군데?
>
> **💬 A** 만든 AI가 아닌 다른 쪽이야. 테스트, 린터, 아니면 다른 AI
>
> **🙋 B** 그냥 같은 AI한테 '다시 검토해' 하면 안 돼?
>
> **💬 A** 그건 자기 채점이야. 학생이 자기 시험지 채점하는 거랑 같아
>
> **🙋 B** 아 그래서 만드는 쪽이랑 검사하는 쪽을 떼어놓는구나
>
> **💬 A** 맞아. 근데 숫자나 날짜가 진짜 맞는지는 AI가 못 봐. 그건 사람 몫이야

### 권한 프로필 (Codex Permission Profile)

`Agent` · Permission Profile (OpenAI Codex) · 추가 2026-10-23

**정의** Codex CLI가 실행하는 명령이 어떤 폴더를 읽고 쓰고, 어디로 접속할 수 있는지를 이름 붙여 정해 두는 설정 묶음(베타).

**자세히**

~/.codex/config.toml의 \[permissions.&lt;이름>\]에 정의하고 default\_permissions로 고른다.  
- 기본 제공: :read-only, :workspace(작업폴더+임시폴더 쓰기), :danger-full-access
- 값: read / write / deny — 같은 경로면 deny > write > read, 더 구체적인 경로가 우선
- 특수 경로: :root(전체), :minimal(실행 필수 최소), :workspace\_roots, :tmpdir, :slash\_tmp
- extends로 기본 프로필 상속 (:workspace 상속 시 작업폴더의 .git·.codex·.agents·.aws는 읽기 전용 보호)
주의: sandbox\_mode나 --sandbox가 있으면 권한 프로필은 무시됨. MCP·커넥터·웹검색·브라우저는 프로필 밖.  

\[lecture\_016 사례\] workspace-only = extends ':workspace' + ':root'=deny + ':minimal'=read + tmp deny + network.enabled=false

**흐름**

- ① config.toml에 \[permissions.workspace-only\] 작성
- ② default\_permissions = "workspace-only"
- ③ sandbox\_mode 줄 삭제 확인
- ④ D:\\AX에서 codex 실행
- ⑤ /status·/debug-config로 적용 확인
- ⑥ 차단 테스트

**헷갈리는 점**

- **흔한 오해** 권한 프로필과 옛 sandbox\_mode를 같이 쓰면 더 안전하다고 생각함
- **차이** 둘은 섞이지 않는다. sandbox\_mode가 하나라도 있으면 권한 프로필이 통째로 무시된다
- **기억법** 규칙집은 한 권만 — 두 권 놓으면 옛날 책을 펼친다

- 매 바퀴 새 머리로 시작 — 지난 대화를 기억하지 않는다

- ③ 진행 상황을 파일에 적는다

- ⑤ 대화를 버리고 처음부터 다시(새 머리)
- ⑥ 다음 바퀴가 진행 상황 파일을 읽고 이어받는다

- **흔한 오해** '기억을 안 넘기면 매번 처음부터 하는 것 아닌가?'

- **기억법** 교대 근무자 — 사람은 바뀌어도 인수인계 노트는 남는다

**카톡으로 이해하기**

>
> **🙋 B** 아니, 그게 뭔데?

>
> **🙋 B** 그냥 같은 지시를 계속 주는 거네?
>
> **💬 A** 맞아. 대신 매 바퀴 지난 대화는 기억 안 해. 새 머리로 시작해

>
> **🙋 B** 단순한데 그게 통한다고?
>
> **💬 A** 멍청할 만큼 단순해서 오히려 통한대. 교대 근무자 인수인계 노트 같은 거야

### 루프 엔지니어링

`Agent` · Loop Engineering · 추가 2026-10-05 · 보강 2026-10-21

**정의** AI가 목표 조건을 향해 스스로 반복 실행하는 구조(루프)를 설계하는 것.

**자세히**

프롬프트 엔지니어링 → 컨텍스트 엔지니어링 → 루프 엔지니어링 순으로 진화.  

핵심 개념: loop = goal(목표조건) + cadence(반복주기)  
AI에게 '이 조건이 충족되면 완료'를 알려주면, 조건이 충족될 때까지 스스로 반복 실행한다.  

기본 구조 (개발자 관점):  
while not goal\_met: result = run\_ai() → evaluate() → repeat  

설계 5요소:  
- ① Goal(목표조건): 무엇이 달성되면 성공인가
- ② Cadence(반복주기): 언제마다 실행할 것인가
- ③ Tools(도구연결): 어떤 앱·데이터에 접근할 것인가
- ④ Exit(종료조건): 언제 사람에게 돌려줄 것인가
- ⑤ Observability(관찰가능성): AI가 성공 여부를 측정할 수 있는가

60점 → 90점 원리: 처음 세팅은 60점이지만 루프가 돌수록 실패 케이스가 쌓이고 자동 개선되어 90점에 수렴.  

\[lecture\_015 보강 — 루프 엔지니어링 입문\]  
- 진화는 4층: 프롬프트(지시 한 줄) → 컨텍스트(AI가 볼 자료) → 하네스(한 번의 실행 환경) → 루프(반복 전체 설계: 언제 시작·멈출지, 무엇을 남길지). 서로를 포함하며, 루프는 하네스 위에 한 층 더 올린 것
- 실무 공식: 루프 = 시작 조건 + 일 + 검사 + 멈춤 + 사람이 보는 지점
- 이름의 유래: 2026.6 Boris Cherny·Steinberger·Addy Osmani가 며칠 사이 같은 말을 하며 '루프 엔지니어링' 이름이 생김. 루프 자체는 옛날부터 있었고, 새로운 건 '설계하는 일'이 됐다는 것
- 꼭 필요한 두 가지: 시작 조건 + 검증 가능한 목표. 하나라도 없으면 '자신만만한 토큰 소각로'
- 60→90점 주장 보정: 루프는 점수를 올리지만 좋아진다는 보장은 없다(검사하는 것만 좋아짐). 카드뉴스 실험에서 채점 7.8→8.8, 기준 9.0 미달로 사람 호출
- 한계: 한 번 하고 말 일엔 안 맞음 / 검사 없으면 돈만 탐(48시간 800만 토큰 사례) / 읽을 사람이 필요

**흐름**

- ① 목표(Goal) 정의
- ② 반복 주기(Cadence) 설정
- ③ 사용 도구(Tools) 연결
- ④ AI 실행
- ⑤ 결과 평가(Observability)
- ⑥ 종료 조건(Exit) 확인 → 미충족 시 다시 ④로

**헷갈리는 점**

- **흔한 오해** 루프 엔지니어링을 단순 반복문(for/while)과 혼동 / 크론(예약 작업)과 혼동
- **차이** 코드 반복문 = 조건 만족까지 기계적 반복 / 루프 엔지니어링 = AI가 판단하며 개선하는 자율 반복 / 크론 = 정해진 시간에 같은 스크립트를 결과 안 보고 실행, 루프 = 지금 상태를 보고 다음 행동을 고르고 결과를 검사해 멈춤
- **기억법** for 루프 = 로봇이 반복 / 루프 엔지니어링 = AI가 생각하며 반복

**카톡으로 이해하기**

> **💬 A** 루프 엔지니어링이 그냥 while 루프 짜는 거야?
>
> **🙋 B** 이름이 루프니까 그런 거 아니야?
>
> **💬 A** 아니! 그냥 코드 반복문이랑 달라  
> AI가 목표 조건을 향해 스스로 판단하면서 반복 실행하는 구조를 설계하는 거야
>
> **🙋 B** 어떻게 달라?
>

>

### 스킬 문서 (Skill Document)

`Agent` · Skill Document · 추가 2026-10-21

**정의** 우리 프로젝트의 지식과 규칙을 적어 둔 문서. 루프가 매 바퀴 읽어서 처음부터 다시 파악하지 않게 한다.

**자세히**

\[lecture\_015 루프 엔지니어링 입문\]  
루프 재료 6가지 중 하나: '우리 프로젝트의 지식과 규칙'.  

쓸수록 똑똑해지는 이유: 배운 것은 스킬 문서에 쌓인다. 스킬 문서가 없으면 매 바퀴 프로젝트를 처음부터 다시 파악해야 한다.  
바깥의 개선 루프가 기록을 읽고 안쪽 루프의 지시문과 도구를 고친다.  

\[우리 서버 실제 사례\] Hermes의 SKILL.md(예: lecture-knowledge-base, maro-ppt)가 스킬 문서다. 작업하면서 배운 절차·주의사항을 여기에 쌓는다.

**흐름**

- ① 루프가 바퀴 시작 시 스킬 문서를 읽는다
- ② 규칙대로 일한다
- ③ 실패·발견한 것을 기록
- ④ 개선 루프가 기록을 읽고 스킬 문서를 고친다
- ⑤ 다음 바퀴부터 고쳐진 규칙 적용

**헷갈리는 점**

- **흔한 오해** 스킬 문서 = 프롬프트 한 번 잘 쓴 것
- **차이** 프롬프트는 한 번의 지시. 스킬 문서는 계속 쌓이고 고쳐지는 프로젝트 지식
- **기억법** 프롬프트 = 오늘 업무 지시, 스킬 문서 = 회사 업무 매뉴얼

**카톡으로 이해하기**

>
> **💬 A** 모델이 바뀌는 건 아니고, 스킬 문서에 배운 게 쌓여
>
> **🙋 B** 스킬 문서가 뭔데?
>
> **💬 A** 우리 프로젝트의 지식과 규칙을 적어 둔 문서야  
> 없으면 매 바퀴 프로젝트를 처음부터 다시 파악해야 해
>
> **🙋 B** 프롬프트 잘 써두는 거랑 같은 거 아냐?
>
> **💬 A** 프롬프트는 오늘 업무 지시, 스킬 문서는 계속 고쳐지는 업무 매뉴얼이야

### 위임 4단계 (턴·목표·시간·자율형)

`Agent` · Loop Delegation Levels · 추가 2026-10-21

**정의** AI에게 얼마나 넘길지에 따른 4단계: 턴 기반 → 목표 기반(/goal) → 시간 기반(/loop) → 자율형.

**자세히**

\[lecture\_015 루프 엔지니어링 입문\]  
Addy Osmani의 분류(2026.7).  

- 1. 턴 기반 — 매 턴 사람이 확인한다. 오늘 대부분이 여기
- 2. 목표 기반 — '끝' 조건을 넘긴다. 테스트 다 통과할 때까지 (/goal)
- 3. 시간 기반 — '언제'를 넘긴다. 매일 아침 8시, 5분마다 (/loop, 예약)
- 4. 자율형 — '무엇을 할지'까지 넘긴다. 일을 스스로 찾는다

아래로 갈수록 더 많이 넘긴다.  
원칙: 한 칸씩. 바로 꼭대기로 가지 않는다. 루프를 키우는 건 신뢰가 쌓인 다음.  

/goal, /loop는 2026년 3~5월 Claude Code·Codex 제품 안에 들어온 명령.

**흐름**

- ① 턴 기반: 매 턴 사람 확인
- ② 목표 기반: 끝 조건 위임 (/goal)
- ③ 시간 기반: 시작 시점 위임 (/loop, 예약)
- ④ 자율형: 할 일 선택까지 위임
- ※ 신뢰가 쌓일 때마다 한 칸씩 올라간다

**헷갈리는 점**

- **흔한 오해** 시간 기반(3단계)이 목표 기반(2단계)보다 더 어렵다는 게 직관과 다름
- **차이** 목표 기반은 사람이 시작은 눌러줌. 시간 기반은 '언제 시작할지'까지 넘겨서 사람이 없어도 돈다
- **기억법** 넘기는 것: 끝(언제 멈출지) → 언제(언제 시작할지) → 무엇(뭘 할지)

**카톡으로 이해하기**

> **💬 A** AI한테 일을 얼마나 맡길지 4단계가 있대
>
> **🙋 B** 4단계? 어떻게 나뉘어?
>
> **💬 A** 1단계 턴 기반은 매 턴 사람이 확인. 지금 대부분이 여기야  
> 2단계 목표 기반은 '끝' 조건을 넘겨. 테스트 다 통과할 때까지 같은 거. /goal
>
> **🙋 B** 3단계는?
>
> **💬 A** 시간 기반. '언제'를 넘겨. 매일 아침 8시처럼. /loop나 예약  
> 4단계 자율형은 '무엇을 할지'까지 넘겨. 일을 스스로 찾아
>
> **🙋 B** 바로 4단계로 가면 제일 좋겠네
>
> **💬 A** 그게 함정이야. 한 칸씩 올라가야 해. 신뢰가 쌓인 다음에

### 컨텍스트 엔지니어링

`Agent` · Context Engineering · 추가 2026-10-05 · 보강 2026-10-21

**정의** LLM에게 어떤 정보를, 얼마나, 어떤 순서로 넣을지 설계하는 기술.

**자세히**

프롬프트 엔지니어링(2024)의 진화 버전.  
단순히 '질문을 잘 쓰는 것'을 넘어, 모델에게 전달하는 전체 정보 구조를 설계한다.  

컨텍스트 엔지니어링이 다루는 것:  
- 시스템 프롬프트 설계: 모델의 역할·제약·말투 정의
- RAG 연동: 필요한 문서만 골라 컨텍스트에 삽입
- 대화 히스토리 관리: 어디까지 기억시킬지
- 토큰 효율화: 같은 정보를 더 적은 토큰으로 전달
- 멀티모달 입력: 텍스트·이미지·파일을 어떻게 조합할지

진화 순서: 프롬프트 엔지니어링(2024) → 컨텍스트 엔지니어링(2025) → 루프 엔지니어링(2026)  

\[lecture\_015 보강\] 최신 정리는 4층: 프롬프트 → 컨텍스트 → 하네스 → 루프. 컨텍스트는 2층 'AI가 볼 자료를 잘 챙긴다'.

**흐름**

- ① LLM에 넣을 정보 목록 파악
- ② 시스템 프롬프트 설계
- ③ 관련 문서·예시 선별
- ④ 토큰 예산 내에서 우선순위 결정
- ⑤ 컨텍스트 윈도우 구성
- ⑥ 결과 평가 → 컨텍스트 개선

**헷갈리는 점**

- **흔한 오해** 컨텍스트 엔지니어링을 프롬프트 엔지니어링과 동일시
- **차이** 프롬프트 엔지니어링 = 질문을 잘 쓰는 것 / 컨텍스트 엔지니어링 = 어떤 정보를 얼마나 어떤 순서로 넣을지 설계
- **기억법** 프롬프트 = 질문 / 컨텍스트 = 질문+배경+자료+예시 전체 설계

**카톡으로 이해하기**

> **💬 A** 컨텍스트 엔지니어링이 프롬프트 엔지니어링이랑 뭐가 달라?
>
> **🙋 B** 그냥 프롬프트 잘 쓰는 것 아니야?
>
> **💬 A** 프롬프트 엔지니어링의 진화 버전이야  
> 단순히 질문 잘 쓰는 걸 넘어서, 모델에게 전달하는 전체 정보 구조를 설계해
>
> **🙋 B** 어떤 걸 설계하는 거야?
>
> **💬 A** 시스템 프롬프트, RAG로 넣을 문서 선별, 대화 히스토리 얼마나 유지할지  
> 토큰 효율화까지 다 포함이야
>
> **🙋 B** 아 프롬프트는 질문 하나고, 컨텍스트 엔지니어링은 그 주변 환경 전체 설계구나
>
> **💬 A** 맞아! 프롬프트 = 질문  
> 컨텍스트 = 질문+배경+자료+예시 전체 설계라고 기억해

**자세히**

\[lecture\_015 루프 엔지니어링 입문\]  
루프 재료 6가지 중 첫 번째. 로봇청소기로 치면 '정해진 시간에 출발'.  

종류:  
- 시간 기반 — 매일 아침 8시, 5분마다 (/loop, 예약 작업)
- 사건 기반 — PR이 열린다, 취약점 공지가 뜬다, 장애 알림이 울린다

루프가 되려면 '시작 조건 + 검증 가능한 목표' 두 가지가 꼭 있어야 한다. 트리거가 그중 '시작 조건'.  

\[우리 서버 실제 사례\] Hermes 크론잡의 schedule(예: 0 8 \* \* \*)이 시간 기반 트리거다.

**흐름**

- ① 시작 조건 정의 (시간 or 사건)
- ② 조건 감시
- ③ 조건 충족 → 루프 깨움
- ④ 에이전트가 일 시작

**헷갈리는 점**

- **흔한 오해** 트리거만 있으면 루프라고 생각함
- **차이** 트리거는 '언제 시작'일 뿐. 검사와 멈춤 조건이 없으면 루프가 아니라 그냥 예약 실행
- **기억법** 알람시계 — 깨우는 것까지만 한다. 일어나서 뭘 할지는 따로 정해야 한다

**카톡으로 이해하기**

> **💬 A** 루프에서 트리거가 뭔지 알아?
>
> **🙋 B** 방아쇠? 시작 버튼 같은 거?
>
> **💬 A** 맞아. 루프를 언제 시작할지 정하는 조건이야
>
> **🙋 B** 어떤 게 있어?
>
> **💬 A** 두 종류야. 시간 기반은 매일 아침 8시처럼 정해진 시각  
> 사건 기반은 PR이 열리거나 장애 알림이 울릴 때

> **🙋 B** 트리거만 있으면 루프 완성이야?
>
> **💬 A** 아니! 트리거는 알람시계일 뿐이야. 깨우는 것까지만 해  
> 검사하고 멈추는 조건까지 있어야 루프가 돼

> **AI 에이전트가 도구·환경·외부 시스템을 안전하게 사용하도록 묶어주는 실행 구조**

**자세히**

하네스는 원래 말(馬)에 채우는 마구(馬具)에서 온 단어다. AI 맥락에서는 에이전트가 도구(API·브라우저·코드 실행 등)를 사용할 때 범위·권한·순서를 제어하는 틀을 말한다. 하네스가 없으면 AI가 의도치 않은 행동을 하거나 시스템을 망가뜨릴 수 있다.

**흐름**

- ① AI 에이전트 목표 정의
- ② 사용 가능 도구 목록 설정
- ③ 실행 범위·권한 제한
- ④ 에이전트 실행
- ⑤ 결과 수집·검증
- ⑥ 이상 감지 시 중단

**헷갈리는 점**

- **흔한 오해** 하네스를 단순히 '코드 테스트용 도구(Test Harness)'로만 아는 경우가 많음
- **차이** Test Harness = 코드 테스트 자동화 도구 / AI Harness = 에이전트 실행 제어 구조
- **기억법** 말 마구(馬具) — 말이 뛰어나도 마구 없으면 방향을 못 잡음. AI도 마찬가지

**예시**

- AI 에이전트가 파일을 읽고 수정할 때 — 어느 폴더까지만 접근 가능한지 제한하는 것
- 말에 마구(하네스)를 채워 방향을 제어하듯 — AI에게 실행 범위를 채워 제어
- LangChain·AutoGPT의 Tool 실행 구조 = 하네스의 일종
- 하네스 엔지니어링 = AI가 도구를 안전하게 쓰도록 실행 환경 자체를 설계하는 것

**카톡으로 이해하기**

> **💬 A** 하네스(Harness)가 AI에서 무슨 의미야?
>
> **🙋 B** 테스트 도구 같은 거 아니야?
>
> **💬 A** 그건 Test Harness야. AI 하네스는 다른 맥락이야  
> AI 에이전트의 실행 환경, 도구, 권한을 통제하는 구조 전체를 말해
>
> **🙋 B** 테스트랑 어떻게 달라?
>
> **💬 A** Test Harness = 코드 자동화 테스트 도구  
> AI Harness = 에이전트가 뭘 할 수 있는지 범위 정하고 통제하는 구조야
>
> **🙋 B** 예를 들어?
>
> **💬 A** 에이전트에게 '웹 검색은 되는데 파일 삭제는 안 됨' 이런 권한 설정하는 게 하네스야  
> 말 마구(馬具) — 말이 뛰어나도 마구 없으면 방향 못 잡듯이  
> AI도 하네스 없으면 통제 불능이야

### 하네스 엔지니어링

`Agent` · Harness Engineering · 추가 2026-10-05 · 보강 2026-10-21

**정의** AI 에이전트가 도구·환경·제약 조건을 안전하게 다룰 수 있도록 실행 구조를 설계하는 것.

**자세히**

Harness = 마구(馬具). 말의 힘을 안전하게 통제하듯, AI 에이전트의 능력을 목적에 맞게 통제·연결하는 구조.  

하네스가 다루는 것:  
- 도구 연결(Tool Binding): AI가 쓸 수 있는 도구(웹 검색·파일·API 등) 정의
- 권한 범위(Permission): AI가 접근 가능한 범위 제한
- 실행 환경(Sandbox): AI가 코드를 실행할 안전한 격리 환경
- 에러 처리: 실패 시 재시도·폴백 구조
- 관찰가능성: 에이전트 실행 과정 추적·기록

루프 엔지니어링과의 관계:  
루프 엔지니어링이 '무엇을 반복할지 설계'라면, 하네스 엔지니어링은 '그 루프가 안전하게 실행될 환경을 설계'하는 것.  

Hermes의 browser\_harness가 대표적 예시 — 브라우저를 AI가 안전하게 조작하도록 래핑.  

\[lecture\_015 보강\] 지시 방식 4층에서 3층: '한 번의 실행 환경을 잘 꾸린다'. 루프는 하네스 위에 한 층 더 올린 것 — 하네스가 한 번의 실행이라면 루프는 여러 번의 실행을 설계한다.

**흐름**

- ① AI 에이전트 실행 목표 정의
- ② 사용 가능한 도구·API 목록 설정
- ③ 접근 권한·실행 범위 제한(샌드박스)
- ④ 실행 순서·의존관계 정의
- ⑤ 에이전트 실행 → 결과 수집
- ⑥ 이상 동작 감지·중단 메커니즘

**헷갈리는 점**

- **흔한 오해** 하네스 엔지니어링을 루프 엔지니어링과 혼동
- **차이** 루프 엔지니어링 = 반복 실행 구조 설계 / 하네스 엔지니어링 = 안전한 실행 환경 설계
- **기억법** 루프 = 얼마나 반복할지 / 하네스 = 어디까지 실행 허용할지

**카톡으로 이해하기**

> **💬 A** 하네스 엔지니어링이 뭔지 설명해줄 수 있어?
>
> **🙋 B** 그게 뭔지 처음 들어보는데
>
> **💬 A** AI 에이전트가 안전하게 도구랑 환경 다룰 수 있도록 실행 구조 설계하는 거야  
> Harness가 말의 마구(馬具)잖아. 말의 힘을 통제하듯 AI를 통제하는 거지
>
> **🙋 B** 루프 엔지니어링이랑은 다른 거야?
>
> **💬 A** 달라! 루프 엔지니어링은 얼마나 반복할지 설계하는 거고  
> 하네스 엔지니어링은 어디까지 실행 허용할지 설계하는 거야
>
> **🙋 B** 예를 들면?
>
> **💬 A** AI가 쓸 수 있는 도구 목록 정하고, 접근 권한 제한하고, 샌드박스 환경 만드는 거야  
> 이상 동작 감지하면 중단하는 메커니즘도 포함이고

### 훅 (Hook, Claude Code)

`Agent` · Hooks (Claude Code) · 추가 2026-10-23

**정의** Claude Code에서 도구 실행 전후 같은 특정 순간에 자동으로 실행되도록 등록해 두는 내 셸 명령.

**자세히**

예: PreToolUse 훅으로 위험한 명령을 실행 전에 검사해 거부, 파일 수정 후 자동 포맷. 권한 규칙을 보완하는 '내가 짠 검문소' 역할.  

\[lecture\_016 보안 포인트\] 훅 명령은 샌드박스 밖에서 내 권한 그대로 실행된다(공식). 프로젝트 폴더의 .claude/settings.json에 훅이 들어 있을 수 있으니 남이 만든 프로젝트를 열 때 확인한다. 단, PreToolUse 훅이 'allow'를 반환해도 deny 규칙은 무시하지 못한다(deny 우선).

**흐름**

- ① settings.json에 훅 이벤트(PreToolUse 등)+명령 등록
- ② Claude가 도구 사용 시도
- ③ 훅 명령이 먼저 실행돼 검사
- ④ 허용/거부/질문 결정 반환
- ⑤ deny 규칙은 훅과 상관없이 항상 적용

**헷갈리는 점**

- **흔한 오해** 훅도 샌드박스 안에서 안전하게 돈다고 생각함
- **차이** 훅은 Claude가 아니라 내가 등록한 명령이라 샌드박스 밖에서 내 권한으로 실행된다
- **기억법** 훅 = 내가 고용한 경비원. 경비원은 잠긴 방 밖에 서 있다

**카톡으로 이해하기**

> **💬 A** Claude Code 훅 써봤어?
>
> **🙋 B** 그게 뭐야?
>
> **💬 A** 도구 쓰기 전후에 자동으로 도는 내 명령이야  
> 위험한 명령을 실행 전에 검사하는 데 많이 써
>
> **🙋 B** 오 보안에 좋겠다
>
> **💬 A** 좋은데 주의할 점이 있어. 훅은 샌드박스 밖에서 내 권한으로 돌아
>
> **🙋 B** 남의 프로젝트 열 때 조심해야겠네
>
> **💬 A** 맞아. .claude/settings.json에 훅이 있는지 확인해

### 휴먼 인 더 루프 / 온 더 루프 (Human in/on the loop)

`Agent` · Human in the loop / Human on the loop · 추가 2026-10-21

**정의** in = 매 바퀴마다 사람이 끼어드는 방식. on = 사람은 루프를 설계하고 결과만 보는 방식.

**자세히**

\[lecture\_015 루프 엔지니어링 입문\]  
루프 엔지니어링의 장점 ②: 사람이 루프 '안'에서 루프 '위'로 올라간다.  

- Human in the loop — 매 바퀴(트리거 → 일·검사 → 다시) 사이사이에 사람이 끼어든다. 오늘날 대부분(턴 기반)
- Human on the loop — 루프를 설계하고, 결과를 본다. 매 턴을 지켜보는 대신 루프가 잘 설계됐는지와 결과를 본다

사람 개입 횟수 예: 기존 6번 → 루프로 2번(시작과 결과 확인). 레버리지 지점이 '한 번 잘 시키기'에서 '잘 시키는 시스템 만들기'로 옮겨갔다.  

주의: on the loop라도 사람이 사라지는 건 아니다. 보고서를 읽을 사람이 없는 루프는 살아남지 못하고, 돌릴 수 있는 루프 수는 사람의 리뷰 능력이 정한다.

**흐름**

- ① (in) 사람 지시 → AI 실행 → 사람 확인 → 사람 재지시… 매 턴 반복
- ② (on) 사람이 루프 설계 (트리거·검사·멈춤)
- ③ 루프가 스스로 일·검사·재시도
- ④ 사람은 결과·보고서만 확인
- ⑤ 루프 설계를 고친다

**헷갈리는 점**

- **흔한 오해** on the loop = 사람이 아예 빠진다
- **차이** 사람이 빠지는 게 아니라 하는 일이 바뀐다. 매 턴 감시 → 설계와 최종 판단
- **기억법** in = 운전석에서 직접 운전 / on = 관제탑에서 항로 설계하고 지켜봄

**카톡으로 이해하기**

> **💬 A** Human in the loop랑 on the loop 차이 알아?
>
> **🙋 B** 전치사 하나 차이인데 뭐가 달라?
>
> **💬 A** in은 매 바퀴마다 사람이 끼어드는 거야. 해줘 → 했어요 → 테스트는? 이런 식
>
> **🙋 B** 지금 우리가 AI 쓰는 방식이네
>
> **💬 A** 맞아. on은 사람이 루프를 설계하고 결과만 봐  
> 사람 개입이 6번에서 2번으로 줄어
>
> **🙋 B** 그럼 사람은 이제 필요 없는 거야?
>
> **💬 A** 아니! 하는 일이 바뀌는 거야. 매 턴 감시 대신 설계랑 최종 판단  
> 보고서 읽을 사람이 없으면 루프는 살아남지 못해
