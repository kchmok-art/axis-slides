### ACME (자동 인증서 발급 규약)

`Infra` · ACME (Automatic Certificate Management Environment) · 추가 2026-10-22

**정의** 서버 프로그램이 사람 없이 인증기관과 대화해서 인증서를 받고 갱신하는 표준 규약. 대표 확인 방식이 HTTP-01.

**자세히**

Let's Encrypt가 만든 규약으로, 지금은 국제 표준(RFC 8555)이다.  

도메인 주인 확인 방식(챌린지):  
- HTTP-01 — 'http://주소/.well-known/acme-challenge/암호'에 파일을 올려 증명. 80번 포트가 열려 있어야 함
- DNS-01 — DNS에 특정 TXT 기록을 올려 증명. 와일드카드(\*.도메인) 인증서 가능
- TLS-ALPN-01 — 443번 포트에서 특수 TLS 응답으로 증명

ACME를 쓰는 프로그램: Traefik(내장), Caddy(내장), certbot(nginx·apache용).  

\[우리 서버 실제 사례 · 2026-10-22 직접 확인\] 우리 Traefik은 HTTP-01 방식으로 설정돼 있다(인증 담당 이름 letsencrypt). 그래서 DNS A 레코드가 VPS를 가리키고 80번 포트가 열려 있어야 인증서가 나온다.

**흐름**

- ① 계정 등록 (서버 ↔ 인증기관)
- ② 도메인 인증서 주문
- ③ 인증기관이 챌린지(숙제) 출제
- ④ 서버가 숙제 수행 (HTTP-01: 파일 올리기)
- ⑤ 인증기관이 확인
- ⑥ 인증서 발급 → 서버 저장

**헷갈리는 점**

- **흔한 오해** ACME를 인증기관 이름이나 프로그램 이름으로 생각함
- **차이** ACME는 '대화 규칙(규약)'. Let's Encrypt는 기관, Traefik·certbot은 그 규칙을 쓰는 프로그램
- **기억법** ACME = 주문서 양식, Let's Encrypt = 가게, Traefik = 주문서를 대신 내는 비서

**카톡으로 이해하기**

> **💬 A** ACME가 뭔지 알아?
>
> **🙋 B** 만화에 나오는 회사 이름 같은데?
>
> **💬 A** ㅋㅋ 여기선 인증서 자동 발급 규칙이야  
> 서버 프로그램이 사람 없이 인증기관이랑 대화하는 방법
>
> **🙋 B** 어떻게 주인인지 확인해?
>
> **💬 A** 숙제를 내. HTTP-01 방식이면 그 주소에 암호 파일을 올려 보라고 해  
> 인증기관이 직접 들어가서 파일 있으면 통과
>
> **🙋 B** 우리 서버도 그거야?
>
> **💬 A** 응, HTTP-01이야. 그래서 DNS가 VPS를 가리켜야 인증서가 나와

### AIOps (에이아이옵스)

`Infra` · Artificial Intelligence for IT Operations · 추가 2026-10-31

> **AI '를' 운영하는 게 아니라, AI '가' 운영을 돕는다**

**정의** AI·머신러닝으로 IT 운영을 돕는 것. 로그와 지표를 AI가 분석해 장애 징후를 먼저 찾고, 원인을 좁히고, 알림을 정리한다.

**자세히**

비유: 사람 매니저 대신 AI 매니저가 식당 전체 센서를 지켜보다가 '냉장고 온도가 평소와 달라요, 30분 뒤 고장 날 수 있어요' 하고 먼저 알려 준다. 알림 100개가 동시에 울리면 '원인은 전기 하나예요' 하고 묶어 준다.  
실제: 이상 탐지(평소 패턴과 다른 지표), 알림 묶기(같은 원인 알림 합치기), 원인 추정, 자동 조치 제안. 2016~2017년 가트너가 이름 붙였다. 도구: Datadog·Dynatrace·Splunk 등의 AI 기능.  
가장 헷갈리는 점: 이름에 AI가 들어가지만 MLOps·LLMOps와 방향이 반대다.

**흐름**

- ① 로그·지표 수집
- ② AI가 평소 패턴 학습
- ③ 이상 탐지
- ④ 알림 묶기·원인 추정
- ⑤ 사람에게 알림 또는 자동 조치
- ⑥ 결과로 다시 학습

**헷갈리는 점**

- **흔한 오해** AIOps vs MLOps·LLMOps — 셋 다 AI가 들어가서 같은 줄 앎
- **차이** MLOps·LLMOps = AI(모델)를 돌보는 운영 — 대상이 AI / AIOps = AI가 IT 시스템을 돌보는 운영 — 도구가 AI
- **기억법** MLOps·LLMOps는 'AI를 돌보는 일', AIOps는 'AI가 돌보는 일'

**예시**

- 서버 응답이 평소보다 조금씩 느려지는 패턴을 AI가 잡아 장애 전에 알림
- 새벽에 알림 200개가 울렸지만 AI가 '원인은 DB 하나'로 묶음
- 사람이 정한 기준선 대신 AI가 평소 패턴을 학습해 이상만 알림

**카톡으로 이해하기**

> **💬 A** AIOps랑 MLOps는 같은 거지? 둘 다 AI잖아
>
> **🙋 B** AI 운영하는 거 아니야?
>
> **💬 A** 반대야! MLOps는 AI 모델을 돌보는 일이고  
> AIOps는 AI가 서버를 돌보는 일이야
>
> **🙋 B** 아 AI가 매니저인 거네
>
> **💬 A** 맞아. 냉장고 이상하다고 먼저 알려 주는 AI 매니저가 AIOps야

### AP 서버 (Application Server)

`Infra` · Application Server · 추가 2026-10-09

> **웹 서버와 데이터베이스 사이에서 실제 비즈니스 로직을 처리하는 서버**

**자세히**

AP 서버는 사용자 요청을 받아 실제 계산·처리·판단을 수행하는 서버다. 웹 서버(nginx 등)가 요청을 받아 AP 서버로 넘기면, AP 서버가 DB에서 데이터를 가져와 가공한 뒤 결과를 돌려준다. Node.js, Spring, Django 등이 AP 서버 역할을 한다.

**흐름**

- ① 웹서버로부터 요청 전달받음
- ② 비즈니스 로직 실행
- ③ 필요 시 DB 서버에 쿼리
- ④ DB 결과 가공
- ⑤ 웹서버에 응답 반환

**헷갈리는 점**

- **흔한 오해** AP 서버와 웹 서버를 같은 것으로 혼동
- **차이** 웹서버 = 정적 파일 서빙·요청 수신(nginx) / AP서버 = 비즈니스 로직 처리(Node.js)
- **기억법** 웹서버 = 접수 창구 / AP서버 = 실제 업무 처리 담당

**예시**

- 로그인 요청 → 웹서버 수신 → AP서버가 DB에서 계정 확인 → 결과 반환
- 쇼핑몰 주문 → AP서버가 재고 확인·결제·주문 처리 로직 실행
- 웹서버(nginx) = 접수 직원 / AP서버(Node.js) = 실무 처리 직원 / DB = 창고
- 동아리 홈페이지 구조: nginx(웹서버) → Node.js(AP서버) → DB

**카톡으로 이해하기**

> **💬 A** AP 서버가 뭔데? 웹 서버랑 다른 거야?
>
> **🙋 B** 둘 다 서버 아니야?
>
> **💬 A** 역할이 달라. 웹 서버는 HTML·이미지 같은 정적 파일 내보내주는 거고  
> AP 서버(애플리케이션 서버)는 실제 비즈니스 로직을 처리하는 거야
>
> **🙋 B** 비즈니스 로직이 뭔데?
>
> **💬 A** 로그인 처리, 결제 계산, 추천 알고리즘 같은 '앱의 두뇌' 역할  
> Node.js, Python(Django/FastAPI), Java(Spring) 같은 게 AP 서버야
>
> **🙋 B** 아 그럼 서버 3단 구조에서 중간 역할이구나
>
> **💬 A** 맞아! 웹서버(nginx) → AP서버(Node.js) → DB서버(MySQL) 순서야  
> 클라이언트 요청 받아서 처리하고 DB에서 데이터 가져와 응답 만드는 게 AP 서버

### Argo CD (아르고 CD)

`Infra` · Argo CD · 추가 2026-11-02

> **큰 주방 안의 검수 담당 — 레시피북(Git)과 실제 요리를 계속 대조하고 다르면 고쳐 놓는다**

**정의** 쿠버네티스 클러스터 안에 설치해, Git 저장소에 적힌 상태와 실제 클러스터 상태를 계속 비교하고 자동으로 맞춰 주는 GitOps 배포 도구. 오픈소스(CNCF 프로젝트).

**자세히**

비유: 주방장(쿠버네티스) 옆에 검수 담당이 서 있다. 레시피북(Git)과 실제로 나가는 요리를 계속 대조하다가, 레시피가 바뀌면 주방에 새 레시피대로 하라고 알리고, 누가 몰래 요리를 바꾸면 레시피대로 되돌린다.  
실제: Git 저장소의 설정(YAML)을 주기적으로 읽어 클러스터와 비교한다. 화면에 앱마다 '동기화됨(Synced) / 어긋남(OutOfSync)', '건강함(Healthy)' 상태가 보인다. 자동 동기화를 켜면 Git이 바뀔 때 자동 배포되고, 자가 치유(self-heal)를 켜면 손으로 바꾼 것을 다시 되돌린다. 되돌리기는 Git에서 이전 커밋으로 돌리면 된다.  
위치: 클러스터 '안'에서 Git을 '끌어오는'(pull) 방식이라, 밖에서 서버에 밀어 넣는 일반 CI/CD보다 클러스터 열쇠를 바깥에 덜 나눠 줘도 된다. 비슷한 도구: Flux.

**흐름**

- ① Git에 원하는 상태(YAML) 저장
- ② Argo CD가 저장소를 주기적으로 읽음
- ③ 클러스터 실제 상태와 비교
- ④ 다르면 OutOfSync 표시
- ⑤ 동기화 — 클러스터를 Git 상태로 맞춤(자동 또는 버튼)
- ⑥ 문제 시 Git 이전 커밋으로 되돌려 롤백

**헷갈리는 점**

- **흔한 오해** Argo CD = CI/CD 전체 / Argo CD = GitHub Actions 같은 것
- **차이** GitHub Actions 같은 CI는 코드를 검사·빌드해 이미지를 만든다(요리 준비). Argo CD는 그 결과를 클러스터에 맞춰 놓는 '배포·동기화(CD)' 담당이다. 이름의 CD도 지속적 배포(Continuous Delivery)다
- **기억법** CI = 재료 손질·포장 / Argo CD = 주방 검수 담당(레시피북과 대조)

**예시**

- 개발자가 Git에서 앱 버전을 1.2 → 1.3으로 고쳐 합침 → Argo CD가 감지 → 클러스터에 1.3 배포
- 누가 클러스터에서 직접 설정을 바꿈 → Argo CD 화면에 OutOfSync → 자가 치유가 켜져 있으면 Git 상태로 복구
- \[우리 서버 실제 사례\] 우리는 호스팅어 VPS 한 대(VPS-IP) 위에 Hermes·Traefik·sign 사이트 등 도커 컨테이너 여러 개를 띄워 쓴다 — 화구 하나에 냄비 여러 개를 올린 '서버 1대' 구성이라 Argo CD를 쓸 대상(쿠버네티스 클러스터)이 없다 (2026-10 대화에서 확인한 구성 기준)

**카톡으로 이해하기**

> **💬 A** Argo CD가 뭐야? 음악 CD?
>
> **🙋 B** 배포 프로그램 이름인가?
>
> **💬 A** 응, 쿠버네티스 클러스터 안에 사는 배포 담당이야  
> Git에 적힌 상태랑 실제 서버 상태를 계속 비교해
>
> **🙋 B** 다르면?
>
> **💬 A** 레시피대로 맞춰 놔. 누가 몰래 바꿔도 되돌리고  
> 주방에서 레시피북이랑 요리를 계속 대조하는 검수 담당이라고 보면 돼
>
> **🙋 B** 우리도 써야 해?
>
> **💬 A** 우리는 서버 한 대라 아직 필요 없어. 클러스터를 쓸 때 쓰는 도구야

### BaaS

`Infra` · Backend as a Service · 추가 2026-10-05

**정의** 로그인·DB·파일 저장 등 백엔드 기능을 직접 만들지 않고 서비스로 가져다 쓰는 것.

**자세히**

백엔드 서버를 직접 구축하지 않고, 자주 필요한 백엔드 기능(인증·DB·스토리지·알림 등)을 API로 제공받아 쓴다.  

대표 예시:  
- Firebase (Google) — 인증·실시간 DB·파일 저장·푸시 알림 제공
- Supabase — PostgreSQL 기반 오픈소스 BaaS
- Appwrite — 셀프호스팅 가능한 BaaS

장점: 백엔드 개발 없이 프론트엔드만으로 앱 완성 가능. 1인 개발자나 MVP 제작에 특히 유용.  
단점: 복잡한 비즈니스 로직 구현이 어려움. 제공자 정책 변경에 취약.  

AX 맥락: AI 에이전트와 BaaS를 조합하면 백엔드 없이 풀스택 자동화 앱 제작 가능.

**흐름**

- ① 프론트엔드 코드 작성
- ② BaaS SDK 연결(Firebase 등)
- ③ 로그인·DB·스토리지를 API로 호출
- ④ BaaS가 백엔드 처리 대신 수행

**헷갈리는 점**

- **흔한 오해** BaaS를 SaaS로 혼동
- **차이** SaaS = 완성된 앱 사용 / BaaS = 내 앱에 백엔드 기능을 API로 연결
- **기억법** BaaS = 재료 배달(내가 요리, 재료만 받음)

**카톡으로 이해하기**

> **💬 A** Firebase 쓰면 백엔드 직접 안 만들어도 된다던데 진짜야?
>
> **🙋 B** 백엔드 없이 어떻게 앱이 작동해?
>
> **💬 A** BaaS를 쓰면 돼. Backend as a Service — 로그인·DB·파일 저장 같은 기능을  
> API로 제공받아서 쓰는 거야
>
> **🙋 B** 아 직접 서버 안 만들고 가져다 쓰는 거구나
>
> **💬 A** 맞아. 프론트엔드 코드에서 Firebase SDK 연결하면  
> 구글 로그인, 실시간 DB, 파일 업로드 같은 거 다 쓸 수 있어
>
> **🙋 B** SaaS랑 다른 게 뭐야?
>
> **💬 A** SaaS는 완성된 앱을 쓰는 거고, BaaS는 내 앱에 백엔드 기능을 API로 연결하는 거야  
> 재료만 배달받아서 내가 요리하는 셈이지

### Build (빌드 단계)

`Infra` · Build · 추가 2026-10-09 · 보강 2026-10-26

> **DevOps 3단계 — 소스코드를 실행 가능한 패키지·이미지로 변환하는 단계**

**자세히**

Build는 사람이 읽는 소스코드를 컴퓨터가 실행할 수 있는 형태로 변환하는 과정이다. 웹은 번들링(Webpack, Vite), 서버는 컴파일·Docker 이미지 생성이 대표적이다. CI/CD가 코드 push 시 자동으로 빌드를 실행한다.  

\[2026-10-26 보강\] 밀키트 비유: 코드는 레시피라 그 자체로는 실행할 수 없다. 빌드는 레시피대로 재료(실행 엔진·부품)를 갖추고 손질해 상자 하나에 담는 일이고, 그 상자가 '도커 이미지'다. 빌드와 배포는 다른 단계다 — 빌드는 포장, 배포는 식탁에 내놓기. 상자는 포장한 날의 재료로 굳기 때문에, 나중에 나온 보안 수정을 넣으려면 최신 재료로 다시 빌드(재빌드)해야 한다.

**헷갈리는 점**

- **흔한 오해** 빌드 vs 배포
- **차이** 빌드 = 실행할 수 있는 완성품(이미지)으로 포장 / 배포 = 그 완성품을 서버에 올려 실제로 켜기
- **기억법** 빌드 = 밀키트 포장, 배포 = 손님 식탁에 올리기

**예시**

- React 코드 → npm run build → 브라우저가 읽을 수 있는 HTML/JS/CSS 파일 생성
- Node.js 앱 → Docker 이미지 빌드 → 어디서나 동일하게 실행 가능
- 빌드 실패 = 코드에 문법 오류·의존성 문제 있음
- \[우리 서버 실제 사례\] 명부 서명 사이트(axis-sign 컨테이너): 2026-10-25에 확인해 보니 공개 화면이 10/19 첫 버전 코드와 똑같았다. 그 뒤에 고친 보안 강화판(10/19 시도 횟수 제한, 10/23 보안 패치)은 코드(레시피)만 준비돼 있고, 새 이미지로 빌드·배포되지 않은 상태 → 재빌드·재배포가 필요.

**카톡으로 이해하기**

> **💬 A** 빌드(Build)가 뭐야? 컴파일하는 거?
>
> **🙋 B** 소스코드를 실행 파일로 만드는 거?
>
> **💬 A** 맞아! 소스코드를 실행 가능한 패키지로 변환하는 단계야  
> Java면 컴파일, JavaScript면 번들링, Docker면 이미지 생성이 빌드야
>
> **🙋 B** 왜 따로 빌드를 해야 해?
>
> **💬 A** 개발 환경이랑 실제 서버 환경이 달라서  
> 빌드를 거쳐야 어떤 환경에서도 실행 가능한 형태가 돼
>
> **🙋 B** CI/CD에서 빌드가 자동화되는 거야?
>
> **💬 A** 맞아! git push 하면 자동으로 빌드 돌아가게 설정해  
> 빌드 실패하면 배포 안 되도록 막는 거야

### ChatOps (챗옵스)

`Infra` · Chat Operations · 추가 2026-10-31

> **단톡방에 '1번 주문 시작'이라고 치면 주방이 움직인다**

**정의** 슬랙·텔레그램 같은 채팅방에서 명령을 내리면 봇이 배포·조회·점검 같은 운영 작업을 실행하고, 결과도 채팅방에 남기는 방식.

**자세히**

비유: 주방에 직접 들어가지 않고 단톡방에 주문을 치면 주방이 움직이고, 완료 사진이 단톡방에 올라온다. 모두가 같은 방에서 무슨 일이 일어났는지 본다.  
실제: 채팅 봇에 '배포해', '서버 상태 보여줘' 같은 명령 → 봇이 실행 → 결과를 채팅으로 보고. 장점: 기록이 대화로 남고, 팀이 함께 보고, 휴대폰으로도 운영할 수 있다. 2013년 무렵 GitHub(Hubot)에서 퍼졌다.  
주의: 채팅 계정이 곧 운영 열쇠가 되므로 누가 어떤 명령을 쓸 수 있는지 권한을 나눠야 한다.

**흐름**

- ① 채팅방에 명령
- ② 봇이 권한 확인
- ③ 작업 실행
- ④ 결과를 채팅방에 보고
- ⑤ 대화가 곧 작업 기록

**헷갈리는 점**

- **흔한 오해** ChatOps = 챗봇 상담
- **차이** 고객 상담 챗봇은 손님 응대, ChatOps는 운영자가 채팅으로 시스템을 움직이는 방식
- **기억법** 손님용 챗봇이 아니라 주방 단톡방

**예시**

- 슬랙에 '/deploy 홈페이지' → 배포 → 결과 링크 회신
- \[우리 서버 실제 사례\] 텔레그램으로 Hermes에 지시 → 서버에서 파일 만들기·검사·홈페이지 반영 → 결과와 파일을 텔레그램으로 회신. 예약 작업의 점검 결과도 같은 대화방으로 온다 (2026-10-31 기준)

**카톡으로 이해하기**

> **💬 A** 챗옵스가 챗GPT야?
>
> **🙋 B** 채팅하니까 비슷한 거 아니야?
>
> **💬 A** 채팅방에서 명령하면 서버 작업이 실행되는 운영 방식이야
>
> **🙋 B** 아 지금 텔레그램으로 너한테 시키는 거?
>
> **💬 A** 맞아! 그게 바로 ChatOps야. 기록도 대화로 남고

### CI/CD

`Infra` · Continuous Integration / Continuous Deployment · 추가 2026-10-09

> **코드 변경 시 자동으로 테스트·빌드·배포까지 실행하는 자동화 파이프라인**

**자세히**

CI(지속적 통합)는 코드를 올릴 때마다 자동으로 테스트·빌드를 실행하는 것이고, CD(지속적 배포)는 테스트 통과 시 자동으로 서버에 배포하는 것이다. 사람이 수동으로 배포하던 작업을 자동화해 실수를 줄이고 배포 속도를 높인다.

**흐름**

- ① 개발자 git push
- ② CI: 자동 테스트 실행
- ③ CI: 자동 빌드
- ④ 테스트 실패 시 → 알림·배포 중단
- ⑤ CD: 자동 서버 배포
- ⑥ 배포 완료 알림

**헷갈리는 점**

- **흔한 오해** CI와 CD를 하나로 묶어 구분 못 함
- **차이** CI(Continuous Integration) = 코드 통합·테스트 자동화 / CD(Continuous Deployment) = 배포 자동화
- **기억법** CI = 품질 검사 자동화 / CD = 배송 자동화

**예시**

- git push → GitHub Actions 자동 실행 → 테스트 → 빌드 → 서버 배포
- 테스트 실패 시 배포 자동 차단 → 버그 있는 코드가 서버에 올라가지 않음
- GitHub Actions, Jenkins, GitLab CI — 대표 CI/CD 도구
- 동아리 홈페이지: 코드 수정 → 자동 배포로 즉시 반영

**카톡으로 이해하기**

> **💬 A** CI/CD가 뭔지 알아?
>
> **🙋 B** 자동 배포 같은 거?
>
> **💬 A** 맞아! CI = Continuous Integration, CD = Continuous Deployment  
> CI는 코드 통합·테스트 자동화, CD는 배포 자동화야
>
> **🙋 B** CI랑 CD 구분이 헷갈려
>
> **💬 A** CI = 품질 검사 자동화 / CD = 배송 자동화로 기억해  
> git push → 자동 테스트 → 자동 빌드 → 자동 배포 이 흐름이야
>
> **🙋 B** 도구가 뭐야?
>
> **💬 A** GitHub Actions, Jenkins, GitLab CI 같은 거야  
> .github/workflows/ 폴더에 YAML 파일 설정하면 git push 할 때마다 자동 실행돼

### CloudOps (클라우드 운영)

`Infra` · Cloud Operations · 추가 2026-10-31

> **내 건물이 아니라 빌린 공유주방을 관리하는 법**

**정의** AWS·GCP·Azure 같은 클라우드에 빌려 쓰는 서버·저장소·서비스를 운영하는 일.

**자세히**

비유: 내 건물을 사지 않고 공유주방을 빌려 쓴다. 필요할 때 화구를 더 빌리고, 안 쓰면 반납한다. 대신 임대 규칙·권한·요금을 잘 관리해야 한다.  
실제: 클라우드 자원 만들기·늘리기·줄이기(오토스케일링), 접근 권한(IAM), 감시(CloudWatch 등), 비용 관리(FinOps와 겹침).  
InfraOps와의 관계: 대상이 '클라우드에 있는 인프라'로 좁혀진 것. 클라우드를 쓰면 InfraOps의 상당 부분이 CloudOps가 된다.

**흐름**

- ① 필요한 자원 빌리기
- ② 권한 나누기(IAM)
- ③ 감시·알림
- ④ 사용량 따라 늘리고 줄이기
- ⑤ 요금 확인

**헷갈리는 점**

- **흔한 오해** 클라우드를 쓰면 운영할 게 없다고 생각함
- **차이** 건물 관리(하드웨어)는 클라우드 회사가 하지만, 무엇을 얼마나 빌려 어떻게 쓰고 누가 열쇠를 갖는지는 내가 운영해야 한다
- **기억법** 공유주방도 화구 수·열쇠·임대료는 내가 관리

**예시**

- 접속자가 몰리면 서버 자동 증설, 새벽엔 자동 축소
- IAM으로 사람·프로그램마다 권한 따로 주기
- VPS(호스팅어)는 서버 한 대를 통째로 빌린 형태라, 대형 클라우드의 자동 증설 기능은 없다

**카톡으로 이해하기**

> **💬 A** 클라우드 쓰면 서버 관리 안 해도 되지?
>
> **🙋 B** 응, 아마존이 다 해 주잖아
>
> **💬 A** 기계는 아마존이 관리해. 근데 몇 대 빌릴지, 누가 열쇠를 갖는지,  
> 요금이 얼마 나오는지는 우리가 운영해야 해
>
> **🙋 B** 아 공유주방 빌린 거랑 비슷하네
>
> **💬 A** 맞아. 그게 CloudOps야

> **💬 A** 혼자라도 버전 관리는 해야 해! 나중에 뭔가 잘못됐을 때 되돌릴 수 있으니까  
> git commit은 작게 자주 해야 해 — 나중에 문제 생기면 찾기 쉬워
>
> **🙋 B** 아 코드 자체보다 협업 방식이 포인트구나
>
> **💬 A** 맞아. 코드 단계 = 개발 + Git 협업 관리

### DB 서버 (Database Server)

`Infra` · Database Server · 추가 2026-10-09

> **데이터를 저장하고 조회·수정·삭제 요청을 처리하는 전용 서버**

**자세히**

DB 서버는 데이터를 체계적으로 저장하고 AP 서버의 요청에 따라 데이터를 꺼내주거나 저장하는 서버다. 엑셀 파일이 창고라면 DB 서버는 창고 관리 시스템이다. MySQL, PostgreSQL, MongoDB 등이 대표적인 DB다.

**흐름**

- ① AP 서버로부터 SQL 쿼리 수신
- ② 쿼리 파싱·최적화
- ③ 데이터 검색·저장·수정·삭제
- ④ 결과 반환 → AP 서버

**헷갈리는 점**

- **흔한 오해** DB와 스토리지 혼동
- **차이** 스토리지 = 파일 단위 저장 / DB = 구조화된 데이터 저장+빠른 검색+관계 관리
- **기억법** 스토리지 = 파일 캐비넷 / DB = 색인 달린 정리된 서랍장

**예시**

- 로그인 시 → AP서버가 DB서버에 '이 이메일 있어?' 질문 → DB서버가 답변
- 게시글 저장 → AP서버가 DB서버에 '이 내용 저장해줘' 요청
- 웹서버(접수) → AP서버(처리) → DB서버(창고) 3단 구조
- MySQL, PostgreSQL(관계형) / MongoDB(비관계형) / Redis(캐시용)

**카톡으로 이해하기**

> **💬 A** DB 서버가 그냥 데이터베이스 아니야?
>
> **🙋 B** 그냥 데이터 저장하는 거잖아?
>
> **💬 A** DB 서버는 데이터베이스 관리 시스템(DBMS)을 실행하는 서버야  
> 클라이언트(AP 서버)에서 SQL 쿼리 보내면 처리해서 결과 돌려주는 거지
>
> **🙋 B** 그럼 AP 서버랑 DB 서버가 다른 컴퓨터야?
>
> **💬 A** 보통 달라. 서버 3단 구조에서 각자 역할이 있어  
> AP 서버가 DB 서버에 '이 사용자 정보 줘' 하고 요청하는 거야
>
> **🙋 B** 아 직접 DB에 연결하는 게 아니라 서버가 중간에 있구나
>
> **💬 A** 맞아. 보안상으로도 DB를 외부에 직접 노출하면 안 되니까  
> AP 서버가 인증하고 DB 서버에 안전하게 요청하는 구조야

### Deploy (배포 단계)

`Infra` · Deploy · 추가 2026-10-09 · 보강 2026-10-26

> **DevOps 6단계 — 준비된 코드·이미지를 실제 서버에 올려 사용자가 접근할 수 있게 하는 단계**

**자세히**

Deploy는 빌드·테스트·릴리즈를 마친 코드를 실제 운영 서버에 반영하는 단계다. CI/CD가 자동으로 처리하며, Blue-Green·Canary 배포 전략으로 무중단 배포가 가능하다.  

\[2026-10-26 보강\] 도커 앱에서 배포 = 새로 빌드한 이미지로 컨테이너를 켜는 일. 이미 돌아가는 컨테이너는 저절로 바뀌지 않으므로 옛 컨테이너를 끄고 새 이미지로 다시 켜야 한다(재배포). 같은 이미지로 끄고 켜는 '재시작'은 배포가 아니다 — 내용이 그대로다.

**헷갈리는 점**

- **흔한 오해** 재배포 vs 재시작
- **차이** 재시작 = 같은 이미지로 다시 켜기(수정 반영 안 됨) / 재배포 = 새 이미지로 바꿔 켜기(수정 반영됨)
- **기억법** 재시작 = 같은 요리 데우기, 재배포 = 새 요리로 교체

**예시**

- GitHub Actions가 main 브랜치 push 감지 → 자동으로 VPS 서버에 배포
- Blue-Green 배포 — 구 버전(Blue)·신 버전(Green) 동시 운영 후 트래픽 전환
- Canary 배포 — 전체 사용자의 5%에게만 먼저 새 버전 배포해 안전성 확인
- 동아리 홈페이지 GitHub Pages 배포 = Deploy 단계
- \[우리 서버 실제 사례\] 명부 서명 사이트(axis-sign 컨테이너): 2026-10-25에 확인해 보니 공개 화면이 10/19 첫 버전 코드와 똑같았다. 그 뒤에 고친 보안 강화판(10/19 시도 횟수 제한, 10/23 보안 패치)은 코드(레시피)만 준비돼 있고, 새 이미지로 빌드·배포되지 않은 상태 → 재빌드·재배포가 필요.

**카톡으로 이해하기**

> **💬 A** Deploy(배포)가 그냥 서버에 올리는 거야?
>
> **🙋 B** 파일 복사하면 되는 거 아니야?
>
> **💬 A** 단순히 파일 복사가 아니야. 기존 서비스 중단 없이 새 버전으로 교체하는 게 핵심이야
>
> **🙋 B** 무중단 배포가 어떻게 가능해?
>
> **💬 A** 블루-그린 배포: 새 버전 서버(그린)를 완전히 세팅 후 트래픽 전환  
> 롤링 배포: 서버를 순차적으로 교체해 일부는 항상 살아있게
>
> **🙋 B** 배포 실패하면 어떡해?
>
> **💬 A** 롤백(Rollback)! 이전 버전으로 되돌리는 거야  
> 그래서 버전 관리가 중요해 — 배포 실패해도 바로 롤백 가능하게  
> Deploy = 새 코드를 사용자에게 전달하는 마지막 단계야

### DevOps

`Infra` · Development + Operations · 추가 2026-10-09 · 보강 2026-10-31

> **개발(Dev)과 운영(Ops)을 합쳐 빠르게 배포하고 안정적으로 운영하는 문화·방법론**

**자세히**

DevOps는 Dev(개발)+Ops(운영)의 합성어지만, 단순한 합성어를 넘어 훨씬 광범위한 개념이다.  

DevOps는 다음 5가지를 모두 포괄하는 방법론이자 기술이다:  
- 1. 문화 — 개발팀과 운영팀이 협력하는 조직 문화
- 2. 자동화 — 반복 작업을 자동화해 속도와 품질을 높임
- 3. 셰어링 — 잘된 점과 잘못된 점을 팀 전체가 공유
- 4. 축적 — 공유된 경험과 지식을 쌓아 자산으로 만듦
- 5. 측정 — 문제와 성과를 데이터로 측정해 판단의 근거로 삼음

즉, 어떤 문제나 요구사항이 발생했을 때 — 문제를 잘 분석하고, 측정하고, 자동화하고, 잘못된 점과 잘된 점을 셰어링해서 축적하고 발전시키는 것이 DevOps의 본질이다.  

\[2026-10-31 보강\] Ops 패밀리의 뿌리. 식당 비유로는 주방(개발)과 홀(운영)이 한 팀이라, 새 메뉴가 손님상까지 매끄럽게 나가는 방식이다. GitOps·DevSecOps·DataOps·MLOps·LLMOps·AgentOps 등은 DevOps의 생각(협업·자동화·측정·공유)을 다른 대상에 옮긴 것이다.

**흐름**

- ① Plan — 기능 기획·이슈 등록(Jira)
- ② Code — 개발·PR(GitHub)
- ③ Build — 빌드 자동화(Webpack)
- ④ Test — 자동 테스트(Jest·pytest)
- ⑤ Release — 릴리즈 준비
- ⑥ Deploy — 자동 배포(Docker·K8s)
- ⑦ Operate — 운영(nginx·서버)
- ⑧ Monitor — 관제(Grafana·Datadog)

**헷갈리는 점**

- **흔한 오해** DevOps를 직군(역할)으로만 이해하는 경우
- **정확한 뜻** DevOps는 직군이기도 하지만 본질은 개발+운영을 통합하는 문화·철학
- **기억법** Dev(개발) + Ops(Operations=운영) = 경계를 없애는 것

**예시**

- 코드 push → 자동 테스트 → 자동 빌드 → 자동 배포 (CI/CD 파이프라인)
- Docker — '내 컴퓨터에서는 됐는데' 문제 해결 → 어디서나 동일한 환경
- Netflix — DevOps로 하루 수백 번 배포, 수억 명 사용자 서비스 안정 유지
- 쿠팡 배송 추적 — 실시간 업데이트를 무중단으로 배포하는 것도 DevOps
- GitHub Actions — 코드 올리면 자동으로 테스트·배포 실행
- Kubernetes — 수백 개 서버 컨테이너를 자동으로 관리·확장

**단계**

- **Plan** 기능 계획·이슈 관리 (Jira, Notion)
- **Code** 개발 (Git, GitHub)
- **Build** 코드 → 실행 가능한 패키지로 변환
- **Test** 자동화 테스트 (Jest, pytest)
- **Release** 배포 준비·승인
- **Deploy** 서버에 자동 배포 (CI/CD)
- **Operate** 서버 운영·스케일링 (Kubernetes, Docker)
- **Monitor** 실시간 관제·알림 (Grafana, Datadog)

**도구**

- **CI/CD** GitHub Actions, Jenkins, GitLab CI
- **컨테이너** Docker, Kubernetes
- **클라우드** AWS, GCP, Azure, Hostinger VPS
- **관제** Grafana, Prometheus, Datadog
- **코드관리** Git, GitHub, GitLab

**왜 중요한가** AI 서비스는 모델 업데이트·데이터 변경이 잦아 DevOps 없이는 운영 불가. AI 에이전트 배포·관제도 DevOps의 영역

**다섯 기둥**

- **1\_문화** 개발팀과 운영팀이 사일로(벽) 없이 협력하는 조직 문화. '내 일 네 일' 구분 없이 함께 책임짐
- **2\_자동화** 빌드·테스트·배포·모니터링 등 반복 작업을 자동화. CI/CD, Docker, GitHub Actions 등 활용
- **3\_셰어링** 잘된 것·잘못된 것·배운 것을 팀 전체와 공유. 회고(Retrospective), 문서화, 지식 공유
- **4\_축적** 셰어링된 경험이 조직의 자산으로 쌓임. 위키, 런북(Runbook), 지식베이스 형태로 저장
- **5\_측정** 감이 아닌 데이터로 판단. 배포 빈도, 장애 복구 시간, 오류율 등을 수치로 측정

**카톡으로 이해하기**

> **💬 A** DevOps가 개발팀이야 운영팀이야?
>
> **🙋 B** Dev랑 Ops 합쳤으니 둘 다?
>
> **💬 A** 직군이기도 하지만 본질은 개발+운영을 통합하는 문화·철학이야  
> 개발자와 운영자 사이 벽을 허물고 협업하는 방식이지
>
> **🙋 B** 왜 분리되어 있었어?
>
> **💬 A** 개발자는 빠르게 새 기능 만들고 싶고, 운영자는 안정성 원하잖아  
> 이 충돌을 해결하려고 DevOps가 나온 거야 — 자동화로 빠르게 + 안정적으로
>
> **🙋 B** CI/CD가 DevOps 도구야?
>
> **💬 A** 맞아! Plan→Code→Build→Test→Release→Deploy→Operate→Monitor 8단계 사이클이야  
> 자동화로 이 사이클을 빠르게 돌리는 게 DevOps 목표야

### DevOps 사이클 (8단계)

`Infra` · DevOps Lifecycle · 추가 2026-10-09

**예시**

- 코드 수정 → 자동 테스트 → 자동 빌드 → 자동 배포 → 모니터링 → 다시 개선

**구조**

- **1단계 Plan** 기능 계획·이슈 관리
- **2단계 Code** 개발·코드 작성
- **3단계 Build** 코드 → 실행 가능한 패키지 변환
- **4단계 Test** 자동화 테스트
- **5단계 Release** 배포 준비·승인
- **6단계 Deploy** 서버에 자동 배포
- **7단계 Operate** 서버 운영·스케일링
- **8단계 Monitor** 실시간 관제·알림

**카톡으로 이해하기**

> **💬 A** DevOps 사이클이 8단계라던데 다 기억해?
>
> **🙋 B** Plan이랑 Code는 알겠는데 나머지는 모르겠어
>
> **💬 A** Plan→Code→Build→Test→Release→Deploy→Operate→Monitor야  
> 왼쪽이 개발 파트, 오른쪽이 운영 파트야
>
> **🙋 B** 순서가 중요해?
>
> **💬 A** 중요해! 계획 세우고 → 코드 짜고 → 빌드하고 → 테스트하고  
> → 릴리즈 준비 → 서버 배포 → 운영 → 모니터링 → 다시 계획  
> 이게 무한 반복이야
>
> **🙋 B** CI/CD가 이 중에 어디야?
>
> **💬 A** Build~Test~Deploy 구간을 자동화한 게 CI/CD야  
> 이 사이클이 빠르게 돌수록 서비스가 빠르게 발전해

### DevSecOps (데브섹옵스)

`Infra` · Development + Security + Operations · 추가 2026-10-31

> **위생 검사를 개업 날 한 번이 아니라 조리 단계마다 한다**

**정의** 보안 점검을 마지막에 한 번 하지 않고, 개발·빌드·배포 단계마다 자동으로 끼워 넣는 방식.

**자세히**

비유: 위생 검사를 가게 문 열기 직전 한 번만 하면, 문제가 나왔을 때 다 뜯어고쳐야 한다. 재료 받을 때, 손질할 때, 담을 때마다 짧게 검사하면 일찍 잡고 싸게 고친다.  
실제: 코드 올릴 때 비밀값(토큰) 노출 검사, 빌드 때 부품(라이브러리) 취약점 검사, 이미지 검사, 배포 전 설정 검사를 파이프라인에 자동으로 넣는다. 이를 '왼쪽으로 당기기(Shift Left)'라고 부른다.  
포인트: 보안 수정이 '코드에만' 있고 배포가 안 되면 서비스는 여전히 취약하다 — 검사와 배포가 한 줄로 이어져야 한다.

**흐름**

- ① 코드 — 비밀값·위험 코드 자동 검사
- ② 빌드 — 부품 취약점 검사
- ③ 이미지·설정 검사
- ④ 배포 — 검사 통과한 것만
- ⑤ 운영 — 감시(SecOps로 이어짐)

**헷갈리는 점**

- **흔한 오해** DevSecOps vs SecOps
- **차이** DevSecOps = 만들 때부터 보안을 끼워 넣기(예방) / SecOps = 운영 중인 시스템을 실시간 감시·대응(경비)
- **기억법** DevSecOps = 조리 단계마다 위생 검사 / SecOps = 가게 CCTV와 경비원

**예시**

- GitHub에 토큰이 섞인 커밋을 올리면 자동 차단
- npm 부품에 알려진 취약점이 있으면 빌드 실패
- \[우리 서버 실제 사례\] 명부 서명 사이트(axis-sign): 10/23 보안 패치 코드는 준비됐지만 새 이미지로 배포되지 않아, 10/25 확인 때 공개 화면은 10/19 첫 버전 그대로였다 — 보안 수정도 배포까지 가야 효과가 있다

**카톡으로 이해하기**

> **💬 A** 보안 검사는 다 만들고 마지막에 하면 되지?
>
> **🙋 B** 응, 완성품을 검사해야지
>
> **💬 A** 그러면 문제 나왔을 때 다 뜯어고쳐야 해  
> 단계마다 자동으로 짧게 검사하는 게 DevSecOps야
>
> **🙋 B** 고친 코드만 있으면 안전한 거지?
>
> **💬 A** 아니! 배포까지 해야 서버에 반영돼. 우리 서명 사이트가 딱 그 상황이었어

### Docker

`Infra` · Docker · 추가 2026-10-09 · 보강 2026-10-26

> **애플리케이션을 환경에 상관없이 동일하게 실행할 수 있도록 컨테이너로 패키징하는 도구**

**자세히**

Docker는 '내 컴퓨터에서는 됐는데 서버에서 안 된다' 문제를 해결한다. 앱 실행에 필요한 코드·라이브러리·설정을 하나의 컨테이너 이미지로 묶어두면, 어떤 서버에서 실행해도 동일한 환경이 보장된다.  

\[2026-10-26 보강\] 도커의 3요소: Dockerfile(레시피) → 이미지(포장된 밀키트 상자, 빌드 결과물) → 컨테이너(상자를 뜯어 조리 중인 요리). '도커 이미지'는 사진 파일이 아니라 빌드한 순간의 프로그램 상태를 통째로 떠 둔 복사본이다(ISO = CD 이미지와 같은 뜻). 수정 사항을 반영하려면 재빌드 → 옛 컨테이너 끄기 → 새 이미지로 켜기 순서를 거친다.

**흐름**

- ① Dockerfile 작성(실행 환경 정의)
- ② docker build → 이미지 생성
- ③ docker push → 레지스트리 업로드
- ④ 서버에서 docker pull → 이미지 다운
- ⑤ docker run → 컨테이너 실행

**헷갈리는 점**

- **흔한 오해** Docker 컨테이너와 가상머신(VM) 혼동
- **차이** VM = OS 전체 가상화(무거움) / Docker = OS 커널 공유, 앱만 격리(가벼움)
- **기억법** VM = 집 전체 복사 / Docker = 방 하나만 격리

**예시**

- 개발 PC·테스트 서버·운영 서버 → 동일한 Docker 이미지 실행 → 환경 차이 없음
- Hermes(VPS)도 Docker 컨테이너로 실행 중
- docker run nginx → nginx 서버를 단 한 줄로 실행
- 컨테이너 = 배 위의 화물 컨테이너 — 규격화되어 어떤 배(서버)에도 실을 수 있음

>
> **🙋 B** 컨테이너 만드는 거?

> **💬 A** 맞아! 앱 실행에 필요한 환경(코드+런타임+설정)을 컨테이너로 패키징하는 거야  
> 어떤 서버에서 실행해도 동일하게 동작해
>
> **🙋 B** 가상머신이랑 다른 거야?
>
> **💬 A** VM은 OS 전체 가상화라서 무거워. Docker는 OS 커널 공유하고 앱만 격리해서 가벼워  
> VM = 집 전체 복사 / Docker = 방 하나만 격리
>
> **🙋 B** 그럼 Dockerfile이 뭐야?
>
> **💬 A** 컨테이너 환경 설정서야. '이 버전 Python에, 이 라이브러리 설치하고, 이 포트 열어' 같이  
> Dockerfile 작성 → docker build → docker run 하면 어디서든 같은 환경 실행돼

### Dockerfile (도커파일)

`Infra` · Dockerfile · 추가 2026-10-26

> **docker build가 위에서부터 한 줄씩 읽어 이미지를 포장하는 레시피**

**정의** 도커 이미지를 어떻게 만들지 순서대로 적어 둔 설계도(레시피) 파일.

**자세히**

Dockerfile 한 줄이 포장 작업 한 단계다. 자주 나오는 명령: FROM = 기본 상자(베이스 이미지) 가져오기, WORKDIR = 작업할 폴더 정하기, COPY = 파일 담기, RUN = 포장하면서 명령 실행(부품 설치 등), ENV = 설정값 적기, EXPOSE = 쓰는 문 번호(포트) 표시, CMD = 컨테이너가 켜질 때 실행할 명령.  

Dockerfile을 고쳐도(예: FROM 버전 변경) 이미 만든 이미지와 켜져 있는 컨테이너는 그대로다. 다시 빌드하고 다시 배포해야 반영된다.

**흐름**

- ① FROM node:22-alpine — Node(실행 엔진)가 든 기본 상자 가져오기
- ② COPY package.json + RUN npm install — 부품 목록을 넣고 부품(Express 등) 설치
- ③ COPY server.js / public — 우리가 쓴 코드와 화면 파일 담기
- ④ ENV / EXPOSE 3001 — 설정값과 문 번호 적기
- ⑤ CMD node server.js — 켜질 때 실행할 명령 지정
- ⑥ docker build → 위 단계를 차례로 실행해 이미지 완성

**헷갈리는 점**

- **흔한 오해** Dockerfile vs docker-compose.yml
- **차이** Dockerfile = 상자 하나를 어떻게 포장할지(이미지 만드는 법) / docker-compose.yml = 상자 여러 개를 어떻게 함께 켤지(포트·볼륨·재시작 규칙) 적은 운영표
- **기억법** Dockerfile = 레시피, compose = 식탁 차림표

**예시**

- \[우리 서버 실제 사례\] 위 흐름은 명부 서명 사이트 첫 버전(10/19) Dockerfile 그대로다
- \[우리 서버 실제 사례\] 10/23 보강판에서 FROM을 node:24-alpine으로 바꿈(보안 수정된 Node) → 이 한 줄도 재빌드·재배포해야 서버에 반영됨

**카톡으로 이해하기**

> **💬 A** Dockerfile이 뭐야?
>
> **🙋 B** 도커 설정 파일?
>
> **💬 A** 맞아, 이미지를 어떻게 포장할지 적은 레시피야  
> 'Node 상자 가져와 → 부품 설치해 → 코드 담아 → 켜질 때 이거 실행해' 이런 순서로 적혀 있어
>
> **🙋 B** 이 파일 고치면 바로 서버에 반영돼?
>
> **💬 A** 아니! 레시피를 고친 것뿐이야. 다시 포장(빌드)하고 식탁에 다시 올려야(배포) 반영돼

### FinOps (클라우드 비용 운영)

`Infra` · Financial Operations (Cloud FinOps) · 추가 2026-10-31

> **식당 가계부 — 재료비·전기세가 새는 곳을 매달 함께 찾는다**

**정의** 쓴 만큼 돈이 나가는 클라우드·AI 서비스 비용을 개발·운영·재무가 함께 보고 줄이는 운영 방식.

**자세히**

비유: 식당 가계부. 장사가 잘돼도 재료가 버려지고 불을 켜 둔 채 두면 남는 게 없다. 주방·홀·사장이 같이 가계부를 보고 새는 곳을 막는다.  
실제: 클라우드는 켜 둔 시간·쓴 양만큼 과금된다. 안 쓰는 서버 끄기, 예약 할인, 팀별 비용 나누기, 예산 초과 알림. LLM 서비스에서는 토큰 비용이 FinOps의 큰 축이 된다(LLMOps와 겹침).  
FinOps Foundation(리눅스 재단 산하)이 원칙과 자격 과정을 만든다.

**흐름**

- ① 보기 — 어디에 얼마 나가는지 나눠서 본다
- ② 줄이기 — 안 쓰는 것 끄기, 할인·캐싱
- ③ 운영 — 예산·알림을 정하고 매달 되돌아보기

**헷갈리는 점**

- **흔한 오해** FinOps = 재무팀이 비용 깎는 일
- **차이** 돈을 쓰는 버튼은 개발·운영자가 누른다. 그래서 개발·운영·재무가 같은 숫자를 함께 보는 방식이 FinOps다
- **기억법** 가계부는 사장 혼자가 아니라 주방도 같이 본다

**예시**

- 주말에 개발용 서버 자동 끄기
- 예산 80% 도달하면 알림
- LLM 호출을 캐싱해 같은 질문은 토큰을 다시 쓰지 않기

**카톡으로 이해하기**

> **💬 A** 핀옵스는 재무팀 일이야?
>
> **🙋 B** 돈 얘기니까 그렇겠지?
>
> **💬 A** 클라우드는 개발자가 서버 하나 켜면 바로 돈이 나가  
> 그래서 개발·운영·재무가 같은 가계부를 보는 방식이야
>
> **🙋 B** AI도 해당돼?
>
> **💬 A** 응, AI는 토큰마다 돈이 나가서 FinOps가 더 중요해졌어

### GitOps (깃옵스)

`Infra` · GitOps · 추가 2026-10-31 · 보강 2026-11-02

> **레시피북(Git)이 유일한 정답 — 주방은 레시피북대로 자동으로 맞춰진다**

**정의** 서버·인프라의 '있어야 할 상태'를 Git 저장소에 글로 적어 두고, 실제 시스템이 자동으로 그 상태에 맞춰지게 하는 운영 방식.

**자세히**

비유: 레시피북이 유일한 기준이다. 주방이 레시피와 다르면 자동으로 레시피대로 되돌린다. 메뉴를 바꾸고 싶으면 주방에서 몰래 바꾸지 않고 레시피북을 고친다.  
실제: 설정 파일(YAML 등)을 Git에 올리면, 클러스터 안의 도구(Argo CD·Flux)가 저장소를 계속 지켜보다가 실제 상태와 다르면 저장소 쪽으로 맞춘다(동기화). 누가 서버를 손으로 바꿔도 다시 되돌아간다.  
왜 중요한가: ① 모든 변경이 Git 기록으로 남아 누가·언제·왜 바꿨는지 보인다 ② 되돌리기 = 이전 커밋으로 돌리기 ③ '서버에 직접 접속해서 고치기'가 줄어 실수가 준다.  
핵심 원칙(OpenGitOps): 선언형으로 적기 · Git에 버전으로 남기기 · 자동으로 끌어오기 · 계속 맞추기.  

\[2026-11-02 보강\] 설명에 나오는 '클러스터' = 서버 여러 대를 묶어 한 대처럼 쓰는 큰 주방, 'Argo CD' = 그 주방 안에서 레시피북(Git)과 실제 요리를 계속 대조하는 검수 담당. 각각 별도 항목으로 정리했다.

**흐름**

- ① 원하는 상태를 설정 파일로 적는다
- ② Git에 커밋·push (리뷰 거쳐 합치기)
- ③ 자동화 도구가 저장소 변경을 감지
- ④ 실제 시스템을 저장소 상태로 맞춤
- ⑤ 계속 비교 — 어긋나면 다시 맞춤
- ⑥ 문제 시 이전 커밋으로 되돌리기 = 롤백

**헷갈리는 점**

- **흔한 오해** GitOps = Git을 쓰는 것 / GitOps = CI/CD
- **차이** Git은 버전 관리 도구, CI/CD는 빌드·배포를 자동으로 '밀어 넣는' 파이프라인. GitOps는 Git을 '정답지'로 삼고 시스템이 그 정답을 계속 '끌어와 맞추는' 운영 방식이다
- **기억법** CI/CD = 요리를 식탁까지 배달 / GitOps = 식탁이 레시피북과 늘 같은지 감시하고 맞추기

**예시**

- Kubernetes 설정을 Git에 올림 → Argo CD가 감지 → 클러스터에 자동 반영
- 누가 서버 설정을 손으로 바꿈 → 몇 분 뒤 Git에 적힌 대로 자동 원상복구
- \[우리 서버 실제 사례\] 홈페이지(kchmok-art/axis-slides)는 저장소에 push하면 GitHub Pages가 자동 게시한다 — 'Git이 기준'이라는 점은 GitOps와 닮았지만, 계속 지켜보며 되돌리는 기능은 없어 엄밀히는 '자동 배포'다 (2026-10-26 push로 확인)

**카톡으로 이해하기**

> **💬 A** 깃옵스가 뭐야? 깃허브 쓰는 거?
>

### HTTPS

`Infra` · HTTP Secure · 추가 2026-10-22

**정의** HTTP 통신을 TLS로 감싸서 암호화한 것. 주소창의 🔒 표시가 HTTPS라는 뜻.

**자세히**

HTTP + TLS = HTTPS.  
- HTTP — 80번 포트, 평문(누구나 내용을 읽을 수 있음)
- HTTPS — 443번 포트, 암호화

'HTTP가 인증을 받으면 HTTPS가 된다'의 정확한 뜻: 서버가 인증기관에서 인증서를 받아 설치하면, 그 서버와의 HTTP 통신이 TLS로 감싸져 HTTPS가 된다. 인증서 자체가 암호화를 하는 게 아니라, 인증서로 신원을 증명하고 그 뒤에 만든 세션 키로 암호화한다.  

\[우리 서버 실제 사례 · 2026-10-22 직접 확인\] http://sign.axmaster.cloud로 접속하면 Traefik이 308 Permanent Redirect로 https://로 자동으로 보낸다. 사용자가 http로 쳐도 결국 HTTPS로 통신한다.

**흐름**

- ① 사용자가 http://주소 입력
- ② 서버(Traefik)가 https://로 리다이렉트(308)
- ③ 443번 포트로 TLS 연결 시작
- ④ 인증서 검증 + 세션 키 생성
- ⑤ 암호화된 HTTP 통신 = HTTPS

**헷갈리는 점**

- **흔한 오해** 🔒 표시가 있으면 '안전한 사이트'라고 생각함
- **차이** 🔒는 '통신이 암호화됐고 주소의 주인이 맞다'는 뜻일 뿐, 그 사이트가 착한 사이트라는 보증이 아니다. 피싱 사이트도 무료 인증서로 🔒를 달 수 있다
- **기억법** 🔒 = 봉투가 밀봉됐다는 뜻. 편지 내용이 진실이라는 뜻이 아니다

**카톡으로 이해하기**

> **💬 A** HTTP랑 HTTPS 차이가 뭔지 알아?
>
> **🙋 B** S가 붙으면 보안이 된다는 거?
>
> **💬 A** 맞아. HTTP를 TLS로 감싼 게 HTTPS야  
> HTTP는 엽서, HTTPS는 밀봉된 편지라고 생각하면 돼
>
> **🙋 B** 그럼 자물쇠 있으면 안전한 사이트지?
>
> **💬 A** 그게 함정이야! 자물쇠는 '봉투가 밀봉됐다'는 뜻일 뿐이야  
> 피싱 사이트도 무료 인증서로 자물쇠 달 수 있어
>
> **🙋 B** 헐 그렇구나
>
> **💬 A** 우리 서버는 http로 들어와도 Traefik이 https로 자동으로 돌려보내

- Terraform으로 서버·네트워크를 코드로 만들기(IaC)

>
> **🙋 B** 식당으로 치면?
>

### ISP (Internet Service Provider)

`Infra` · Internet Service Provider · 추가 2026-10-09

**헷갈리는 점**

- **흔한 오해** ISP와 IX 혼동

**예시**

- KT, SKT(SK브로드밴드), LG U+ — 한국 3대 ISP
- 집에서 인터넷 개통 = ISP와 계약하는 것

**카톡으로 이해하기**

### IX (Internet Exchange)

`Infra` · Internet Exchange Point · 추가 2026-10-09

> **여러 ISP와 네트워크가 서로 직접 연결되어 트래픽을 교환하는 물리적 거점**

**자세히**

IX는 인터넷 교환 노드로, 각기 다른 ISP(인터넷 서비스 제공자)들이 한 곳에 모여 서로의 네트워크를 직접 연결하는 시설이다. IX를 통해 데이터가 먼 길을 돌아가지 않고 빠르게 전달된다. 서울 IX, 도쿄 IX 등 주요 도시에 위치한다.

**흐름**

- ① KT 사용자가 SKT 서버에 접속 요청
- ② KT 라우터 → IX 포인트로 전달
- ③ IX에서 SKT 네트워크와 직접 연결
- ④ SKT 서버 응답 → IX → KT → 사용자

**헷갈리는 점**

- **흔한 오해** IX를 ISP로 혼동
- **차이** ISP = 인터넷 서비스 제공자(KT, SKT) / IX = ISP들이 만나는 교환 거점
- **기억법** ISP = 도로 / IX = 고속도로 인터체인지(IC)

**예시**

- KT 사용자 → SKT 서버 접속 시: IX에서 두 망이 직접 연결되어 빠르게 전달
- IX 없이는: KT → 해외 → SKT 같은 우회 경로 발생
- 데이터 고속도로의 인터체인지(IC) 같은 역할
- 넷플릭스가 한국 IX에 서버를 두는 이유 = 한국 사용자에게 빠른 속도 제공

**카톡으로 이해하기**

> **💬 A** IX가 뭔지 알아?
>
> **🙋 B** 처음 들어봐. 뭔 약자야?
>
> **💬 A** Internet Exchange. 인터넷 교환 지점이야  
> 여러 ISP(인터넷 서비스 제공자)들이 서로 직접 연결해서 트래픽을 교환하는 곳
>
> **🙋 B** 왜 그게 필요해?
>
> **💬 A** ISP끼리 직접 연결 안 하면 데이터가 멀리 돌아가야 해  
> IX에서 직접 연결하면 더 빠르고 비용도 줄어들어
>
> **🙋 B** 그럼 인터넷이 빠른 이유 중 하나가 IX야?
>
> **💬 A** 맞아! 한국에는 KIX(한국 인터넷 교환 지점)가 있어  
> 도시 간 고속도로 분기점처럼 인터넷 트래픽이 여기서 방향을 정해

### Kubernetes (쿠버네티스)

`Infra` · Kubernetes · 추가 2026-10-09 · 보강 2026-11-02

> **수많은 Docker 컨테이너를 자동으로 배포·확장·관리하는 컨테이너 오케스트레이션 도구**

**자세히**

Kubernetes(K8s)는 Docker 컨테이너가 수백~수천 개로 늘어날 때 이를 자동으로 관리하는 도구다. 컨테이너 죽으면 자동 재시작, 트래픽 많으면 자동 증설, 업데이트 시 무중단 배포를 처리한다.  

\[2026-11-02 보강\] 식당 비유로는 '큰 주방(클러스터)의 주방장'이다 — 화구(노드)마다 요리(컨테이너)를 배정하고, 화구가 꺼지면 다른 화구로 옮긴다. 기존 비유(컨테이너 항구 자동화)와 같은 이야기다. 쿠버네티스가 관리하는 서버 묶음을 클러스터, 그 안의 서버 한 대를 노드라고 부른다.  

\[2026-11-02 보강\] 주방장이 다루는 단위는 쟁반(Pod)이고, '쟁반 N개 유지' 주문서는 디플로이먼트, 바뀌지 않는 픽업 창구는 서비스다. 전체 지도는 '흐름: 쿠버네티스 큰 주방 지도 (클러스터→노드→Pod→컨테이너)'.

**흐름**

- ① 컨테이너 이미지 준비
- ② K8s에 배포 설정(YAML) 제출
- ③ K8s가 최적 서버에 컨테이너 배치
- ④ 컨테이너 죽으면 자동 재시작
- ⑤ 트래픽 증가 시 Auto Scaling

**헷갈리는 점**

- **흔한 오해** Kubernetes를 Docker와 같은 것으로 혼동
- **차이** Docker = 컨테이너 하나 실행 / Kubernetes = 수백 개 컨테이너 자동 관리·조율
- **기억법** Docker = 화물 컨테이너 / Kubernetes = 컨테이너 항구 자동화 시스템

**예시**

- 컨테이너 1개 죽으면 → K8s가 자동으로 새 컨테이너 실행
- 트래픽 10배 급증 → Auto Scaling으로 컨테이너 자동 10배 증설
- Google·Netflix·카카오 — 모두 Kubernetes로 서비스 운영
- Docker = 컨테이너 하나 / Kubernetes = 컨테이너 함대 관리

> **💬 A** Kubernetes가 Docker랑 같은 거야?
>
> **🙋 B** 컨테이너 관련된 거잖아?
>
> **💬 A** 달라! Docker는 컨테이너 하나 실행하는 거고  
> Kubernetes는 컨테이너 수백 개를 자동으로 관리·조율하는 거야
>
> **🙋 B** 왜 Kubernetes가 필요해?
>
> **💬 A** 컨테이너가 죽으면 자동 재시작, 트래픽 많으면 자동으로 컨테이너 늘리기  
> 여러 서버에 컨테이너 분산 배치 — 이런 걸 사람이 다 하면 못 따라가
>
> **🙋 B** 아 컨테이너 항구 자동화 시스템이네
>
> **💬 A** 맞아! Docker = 화물 컨테이너 / Kubernetes = 항구 자동화 시스템  
> 줄여서 K8s라고도 해

### LLMOps

`Infra` · Large Language Model Operations · 추가 2026-10-13 · 보강 2026-10-31

**자세히**

LLMOps는 MLOps에서 LLM(거대 언어모델) 특화 문제들을 추가로 다루는 개념이다. LLM은 일반 ML 모델과 달리 프롬프트 관리, 토큰 비용, 환각(Hallucination) 모니터링, RAG 파이프라인 관리 등 고유한 운영 과제가 있다.  

\[2026-10-31 보강\] 식당 비유: 이미 다 배운 유명 셰프를 모셔 와 쓰는 일 — 키우지는 않고 주문서(프롬프트)를 잘 쓰고, 맛(답변 품질)을 검사하고, 몸값(토큰 비용, FinOps와 겹침)과 그럴듯한 거짓말(환각)을 관리한다. 셰프에게 장보기·결제 같은 '행동'까지 맡기면 AgentOps로 이어진다.

**흐름**

- ① LLM 선택 및 API 연결 (GPT/Claude/자체모델)
- ② 프롬프트 엔지니어링 및 버전 관리

**헷갈리는 점**

- **흔한 오해** MLOps와 LLMOps를 같은 것으로 혼동
- **차이** MLOps = 모델 학습·배포 중심 / LLMOps = 프롬프트·토큰비용·환각·RAG 등 LLM 고유 문제 추가

**예시**

- 고객센터 LLM: 잘못된 답변 로깅 → 프롬프트 개선 → A/B 테스트 → 배포

**LLM 고유 과제**

- **프롬프트\_버전관리** 코드처럼 프롬프트도 버전 관리 필요

- **RAG\_관리** 검색 문서 최신화·품질 유지
- **지연시간** LLM은 일반 API보다 응답이 느림 → 스트리밍·캐싱 전략 필요

**난이도** ⭐⭐⭐⭐⭐ — DevOps + ML + LLM 특화 지식 모두 필요

### MLOps

`Infra` · Machine Learning Operations · 추가 2026-10-13 · 보강 2026-10-31

> **AI 모델을 코드처럼 배포·관리·모니터링하는 DevOps의 ML 버전**

**자세히**

MLOps는 DevOps 개념을 AI/ML 모델에 적용한 것이다. 모델을 학습시키는 것에서 끝나지 않고, 실제 서비스에 배포하고, 성능을 모니터링하고, 데이터가 바뀌면 재학습시키는 전체 사이클을 자동화·관리하는 방법론이다.  

\[2026-10-31 보강\] 식당 비유: 견습 셰프(모델)를 직접 키우는 일 — 훈련 → 맛 시험 → 주방 투입 → 손님 입맛(데이터)이 바뀌면 재교육. 재료 공급은 DataOps가 맡는다. 주의: AIOps와 이름이 비슷하지만 방향이 반대다(MLOps = AI를 돌봄 / AIOps = AI가 IT 운영을 돌봄).

**흐름**

- ① 데이터 수집·전처리 파이프라인 구축
- ② 모델 학습 자동화
- ③ 모델 성능 평가 및 버전 관리
- ④ 서비스 배포 (API 서버로 서빙)
- ⑤ 실시간 성능 모니터링
- ⑥ 데이터 드리프트 감지 → 재학습 트리거
- ⑦ 새 모델로 교체 (무중단 배포)

**헷갈리는 점**

- **흔한 오해** MLOps를 단순히 '모델 배포'로만 이해
- **차이** 모델 배포는 MLOps의 일부일 뿐. 데이터 파이프라인·모니터링·재학습·버전관리까지 전체 생애주기 관리가 MLOps
- **기억법** DevOps = 코드 관리 / MLOps = 코드 + 모델 + 데이터 관리

**예시**

- 스팸 필터 모델을 학습 → 서버에 배포 → 정확도 모니터링 → 새 스팸 패턴 생기면 재학습 → 다시 배포 = MLOps 사이클
- 넷플릭스 추천 모델: 매일 새 시청 데이터로 재학습 → 자동 배포 → 클릭률 측정
- 이상거래 탐지 모델: 사기 패턴 변화 감지 → 자동 재학습 트리거

**난이도** ⭐⭐⭐⭐ — DevOps 이해 후 ML 지식까지 필요

**DevOps와 차이** DevOps에 '모델 학습·데이터 드리프트·실험 추적' 등 ML 특화 문제가 추가됨

**도구**

- MLflow
- Kubeflow
- Airflow
- Seldon
- BentoML
- Weights & Biases

> **💬 A** MLOps가 DevOps랑 어떻게 달라?
>

### nginx

`Infra` · nginx (Engine-X) · 추가 2026-10-09 · 보강 2026-10-22

> **고성능 웹서버이자 리버스 프록시 — 외부 요청을 받아 내부 서버로 전달하는 대문지기**

**자세히**

nginx(엔진엑스)는 웹서버·리버스 프록시·로드밸런서 역할을 하는 오픈소스 소프트웨어다. Apache보다 가볍고 빠르며 동시 접속 처리 성능이 뛰어나다. 현재 전 세계 웹서버 점유율 1위. VPS에서 80/443 포트로 외부 요청을 받아 내부 Node.js·Python 서버로 전달하는 역할을 한다.

**흐름**

- ① 브라우저 → axis.axmaster.cloud:80 요청
- ② nginx → server\_name 매칭
- ③ proxy\_pass → localhost:3000으로 전달
- ④ Node.js 처리 → 응답 반환
- ⑤ nginx → 브라우저에 응답 전달

**헷갈리는 점**

- **흔한 오해** nginx를 단순 웹서버로만 이해하는 경우
- **정확한 뜻** 웹서버 + 리버스 프록시 + 로드밸런서 + SSL 처리까지 담당하는 만능 대문지기
- **vs_apache** Apache = 요청당 프로세스 생성(무거움) / nginx = 이벤트 기반(가볍고 빠름)
- **기억법** nginx = VPS의 대문지기 — 모든 외부 요청이 nginx를 먼저 통과

**예시**

- axis.axmaster.cloud:80 → nginx 수신 → localhost:3000(Node.js)으로 전달
- HTTPS 인증서(SSL) 처리 — nginx가 담당하고 내부 서버는 HTTP만 써도 됨
- 여러 도메인을 하나의 VPS에서 운영 — nginx가 도메인별로 분리 처리
- 정적 파일(이미지·CSS·JS) 직접 서빙 — AP서버 부하 감소

**설정 예시**

- **설명** axis.axmaster.cloud를 localhost:3000으로 프록시 라우팅하는 nginx 설정
- **code** 
server {
    listen 80;
    server\_name axis.axmaster.cloud;

    location / {
        proxy\_pass http://localhost:3000;
        proxy\_set\_header Host $host;
        proxy\_set\_header X-Real-IP $remote\_addr;
    }
}


**쉽게 말하면**

- **한줄요약** 아파트 경비원 — 모든 방문객(요청)이 경비실(nginx)을 먼저 거치고, 경비원이 '몇 호(포트)로 가세요'라고 안내
- **왜필요한가** 서버 포트는 숫자(3000, 8000 등)인데 사람들은 'axis.axmaster.cloud'같은 주소를 씀. nginx가 이 주소를 보고 알맞은 포트로 연결해줌
- **없으면어떻게되나** axis.axmaster.cloud:3000처럼 포트번호를 직접 입력해야 함 → 불편하고 비전문적
- **비유\_3가지** {"경비원": "아파트 경비실 — 방문객이 오면 '몇 호 가세요?' 안내", "전화교환원": "회사 대표번호로 전화하면 교환원이 담당 부서로 연결", "호텔프런트": "호텔 입구 프런트 — 손님 맞이 후 알맞은 객실(서버)로 안내"}

**단계별로**

- **1\_외부에서\_보이는것** axis.axmaster.cloud (포트 없음, 깔끔)
- **2\_실제\_작동** nginx가 80번 포트에서 대기 중 → 요청 수신
- **3\_nginx가\_하는일** 이 주소는 동아리 홈페이지네 → 3000번 포트로 보내줌

**실제 사례**

- 카카오톡 서버 — 수억 명 요청을 nginx가 먼저 받아 분산
- 네이버 — 뉴스/쇼핑/블로그 등 서비스별로 다른 서버에 nginx가 라우팅
- 우리 VPS — axmaster.cloud(녹음기)와 axis.axmaster.cloud(동아리)를 nginx가 분리

**우리 서버 메모** \[우리 서버 실제 사례 · 2026-10-22 확인\] 우리 VPS의 80·443 정문은 nginx가 아니라 Traefik이다. nginx는 nightdesk-web 등 특정 앱 컨테이너 안에서 정적 파일을 내주는 역할. 위 예시의 'axis.axmaster.cloud → nginx'는 일반적인 구조 설명이고, 우리 서버에서는 Traefik 라벨로 연결한다.

### Ops (운영) — OO+Ops 이름 읽는 법

`Infra` · Operations · 추가 2026-10-31

> **한 번 잘 만드는 기술이 아니라, 매일 안 틀리고 돌아가게 하는 기술**

**정의** Ops는 Operations(운영)의 줄임말이다. 'OO+Ops'는 OO을 만드는 일과 운영하는 일을 끊기지 않게 잇고, 자동화해서 늘 같은 품질로 돌아가게 하는 방식이라는 뜻이다.

**자세히**

비유: 식당 하나를 떠올린다. 요리를 개발하는 주방, 손님을 받는 홀, 건물·가스·전기, 재료 공급, 위생, 가계부가 모두 '운영'이다. OO+Ops는 그중 어느 부분을 '만들기 ↔ 운영' 사이 벽 없이 자동으로 굴리느냐에 따라 이름이 붙는다.  
읽는 법: 앞에 붙은 말 = 대상(무엇을 운영하나) 또는 방법(무엇으로 운영하나).  
- 대상: Dev(소프트웨어)·Infra(기반 시설)·Cloud(클라우드)·Data(데이터)·ML(모델)·LLM(거대 언어모델)·Agent(일하는 AI)·Fin(돈)·Sec(보안)
- 방법: Git(저장소가 기준)·Chat(채팅으로 명령)·AI(AI가 운영을 도움)
뿌리는 DevOps이고, 나머지는 DevOps의 생각(협업·자동화·측정·공유)을 다른 대상에 옮긴 것이다. 업계 표준으로 굳은 이름(DevOps·GitOps·MLOps·FinOps·DevSecOps·AIOps)과 회사마다 다르게 쓰는 이름(InfraOps 등)이 섞여 있다.

**흐름**

- ① 앞말 보기 — 대상(Dev·Data·ML…)인지 방법(Git·Chat·AI)인지
- ② 그 대상을 '만들기'와 '운영' 사이 벽 없이 잇는다
- ③ 반복 작업을 자동화한다
- ④ 측정하고 공유해서 다음 번에 더 잘 돌게 한다

**헷갈리는 점**

- **흔한 오해** Ops = 운영팀(사람)이라고만 생각함 / 이름마다 전혀 다른 기술이라고 생각함
- **차이** Ops는 직군 이름이기도 하지만, OO+Ops는 대부분 '운영하는 방식'을 말한다. 생각의 뿌리는 모두 DevOps 하나다
- **기억법** OO+Ops = OO을 '매일 안 틀리고 돌아가게' 만드는 법

**예시**

- DevOps · GitOps · InfraOps · CloudOps · FinOps · DevSecOps · SecOps · DataOps · MLOps · LLMOps · AgentOps · AIOps · ChatOps
- \[우리 서버 실제 사례\] 텔레그램으로 Hermes에 일 시키기(ChatOps), 매일 sign 감시·보안 점검·백업 예약 작업(DevOps·SecOps 자동화), 홈페이지 저장소 push → 자동 게시(GitOps 맛보기) — 2026-10-31 예약 작업 목록으로 확인

**카톡으로 이해하기**

>

### PaaS

`Infra` · Platform as a Service · 추가 2026-10-05

**정의** 개발자가 앱을 만들고 배포할 수 있는 플랫폼 환경을 서비스로 제공하는 것.

**자세히**

서버·운영체제·런타임(실행 환경)을 제공자가 관리. 개발자는 코드와 데이터만 신경 쓰면 된다.  

대표 예시:  
- Heroku — 코드를 올리면 자동으로 서버에 배포
- Vercel, Netlify — 프론트엔드 앱 배포 플랫폼
- Google App Engine, AWS Elastic Beanstalk

장점: 서버 설정·운영체제 관리 불필요. 배포가 쉽고 빠름.  
단점: 플랫폼 종속성 발생. 세밀한 서버 설정이 어려울 수 있음.  

SaaS vs PaaS: SaaS는 완성된 소프트웨어를 쓰는 것, PaaS는 내 앱을 만들어 올리는 플랫폼을 빌리는 것.

**흐름**

- ① 코드 작성
- ② PaaS 플랫폼에 배포(git push 등)
- ③ 플랫폼이 자동으로 서버·OS·런타임 관리
- ④ 서비스 운영

**헷갈리는 점**

- **흔한 오해** PaaS와 IaaS 혼동
- **차이** IaaS = 서버(VM)만 제공 / PaaS = 서버+OS+런타임+배포까지 제공
- **기억법** PaaS = 주방 빌리기(주방 도구 포함) / IaaS = 빈 공간만 빌리기

### Pod (파드, 쿠버네티스)

`Infra` · Pod · 추가 2026-11-02

> **같이 나가야 하는 요리를 담은 쟁반 하나 — 쿠버네티스는 요리가 아니라 쟁반 단위로 옮긴다**

**정의** 쿠버네티스가 실행·관리하는 가장 작은 단위. 컨테이너 하나 이상을 한 묶음으로 담은 포장이다.

**자세히**

이름: 쿠버네티스 공식 문서는 '고래 무리(a pod of whales)·콩깍지(pea pod)'에서 따왔다고 설명한다. 도커 로고가 고래라서, 컨테이너 몇 마리를 한 무리로 묶은 셈이다.  
비유: 클러스터 = 큰 주방, 노드 = 화구, 컨테이너 = 요리, Pod = 쟁반. 같이 나가야 하는 요리를 한 쟁반에 담는다.  
쟁반 규칙 = Pod 특징  
- 보통 쟁반 하나에 요리 하나(컨테이너 1개 = Pod 1개)가 가장 흔하다.
- 곁들임을 같이 담기도 한다: 메인 앱 옆에 로그 수집기 같은 보조 컨테이너 = '사이드카'.
- 쟁반은 통째로 한 화구에 올라간다: 한 Pod 안의 컨테이너는 같은 노드에서 함께 돌고, 같은 번호표(IP 주소)와 저장공간을 나눠 쓴다.
- 쟁반은 일회용: 고장 나면 고치지 않고 새 Pod를 만든다 → 번호표(IP)가 바뀐다 → 그래서 고정 창구 '서비스(Service)'가 필요하다.
- '이 쟁반을 항상 3개 유지해' 주문서 = 디플로이먼트(Deployment).

**흐름**

- ① 디플로이먼트(주문서)가 'Pod N개' 요청
- ② 주방장(쿠버네티스)이 Pod를 놓을 노드(화구) 고르기
- ③ 노드에서 Pod 안 컨테이너들 실행 — IP 하나 공유
- ④ 서비스(고정 창구)가 손님을 살아 있는 Pod로 연결
- ⑤ Pod 고장 → 버리고 새 Pod 생성(새 IP)
- ⑥ 서비스가 새 Pod로 자동 연결

**헷갈리는 점**

- **흔한 오해** ① Pod = 컨테이너 ② Pod = 노드
- **차이** ① 컨테이너 = 요리, Pod = 그 요리를 담은 쟁반. 쿠버네티스는 컨테이너를 직접 다루지 않고 늘 Pod 단위로 옮기고·늘리고·다시 만든다 ② 노드 = 화구(서버), Pod = 그 위에 올라가는 쟁반. 화구 하나에 쟁반 여러 개가 올라간다
- **기억법** 주방(클러스터) > 화구(노드) > 쟁반(Pod) > 요리(컨테이너)

**예시**

- 웹앱 컨테이너 1개짜리 Pod를 3개 띄워 손님을 나눠 받기
- 웹앱 + 로그 수집기(사이드카) 2개 컨테이너를 한 Pod에 담기 — 같은 노드에서 같이 뜨고 같이 꺼짐
- \[우리 서버 실제 사례\] 우리 VPS는 쿠버네티스 없이 도커 컨테이너만 쓴다 — 쟁반(Pod) 없이 요리(컨테이너)를 화구에 바로 올리는 구조라 Pod·Deployment·Service가 없다. 대신 정문 역할은 Traefik이 한다 (2026-10 대화에서 확인한 구성 기준)

**카톡으로 이해하기**

> **💬 A** Pod는 또 뭐야?
>
> **🙋 B** 컨테이너랑 같은 거 아니야?
>
> **💬 A** 컨테이너를 담는 쟁반이야. 보통 쟁반 하나에 요리 하나지만  
> 소스 같은 보조 컨테이너를 같이 담기도 해
>
> **🙋 B** 쟁반이 왜 필요해?
>
> **💬 A** 쿠버네티스는 요리가 아니라 쟁반 단위로 옮기고 늘리거든  
> 같은 쟁반 요리는 같은 화구에서 같은 번호표를 써
>
> **🙋 B** 쟁반이 엎어지면?
>
> **💬 A** 닦아 쓰지 않고 새 쟁반을 받아. 번호표가 바뀌니까 고정 창구(Service)를 따로 둬

### SaaS

`Infra` · Software as a Service · 추가 2026-10-05

**정의** 소프트웨어를 설치 없이 인터넷으로 바로 쓰는 서비스 방식.

**자세히**

서버·운영체제·소프트웨어 모두 제공자가 관리. 사용자는 그냥 접속해서 쓰기만 한다.  

대표 예시:  
- Gmail, Google Docs — 설치 없이 브라우저로 사용
- Notion, Slack, Figma — 구독하면 바로 사용
- ChatGPT, Claude — AI 모델을 서비스로 제공

장점: 설치·업데이트·서버 관리 불필요. 어디서든 접속 가능.  
단점: 데이터가 제공자 서버에 있음. 인터넷 없으면 사용 불가.

**흐름**

- ① 브라우저로 URL 접속
- ② 로그인(구독 확인)
- ③ 완성된 소프트웨어 바로 사용
- ④ 데이터는 제공사 서버에 저장

**헷갈리는 점**

- **흔한 오해** SaaS·PaaS·BaaS 구분 혼동
- **차이** SaaS=다 된 밥 / PaaS=주방 빌리기 / BaaS=재료 배달
- **기억법** SaaS=쓰기만 함 / PaaS=개발환경 빌림 / BaaS=백엔드 기능만 빌림

**카톡으로 이해하기**

> **💬 A** 요즘 회사에서 Notion이나 Slack 쓰잖아. 이게 SaaS야?
>
> **🙋 B** SaaS? 그게 뭐야
>
> **💬 A** Software as a Service. 소프트웨어를 설치 없이 인터넷으로 바로 쓰는 거야  
> Gmail, Google Docs, ChatGPT 같은 것들도 다 SaaS야
>
> **🙋 B** 아 그냥 구독하면 쓸 수 있는 거구나
>
> **💬 A** 맞아. 서버·운영체제·소프트웨어 관리를 다 제공자가 해주고  
> 우리는 그냥 접속해서 쓰기만 하면 돼
>
> **🙋 B** PaaS나 BaaS랑은 다른 거야?
>
> **💬 A** SaaS는 다 된 밥, PaaS는 주방 빌리기(개발 환경만), BaaS는 재료 배달(백엔드 기능만)  
> SaaS는 쓰기만 하면 된다는 게 핵심이야

**흐름**

- ① 감시 — 로그·접속·버전

- **흔한 오해** SecOps vs DevSecOps

- **기억법** CCTV(SecOps) vs 조리 단계 위생검사(DevSecOps)

**예시**

- 같은 IP가 로그인을 수백 번 시도 → 차단
- 새 보안 업데이트 발표 → 우리 서버 해당 여부 확인 → 적용
- \[우리 서버 실제 사례\] 매일 KST 09:05 보안 점검, 매일 KST 09:00 sign 사이트 상태 감시 예약 작업 — 정상이면 조용하고 이상할 때만 알린다 (2026-10-31 확인)

**카톡으로 이해하기**

> **💬 A** 보안 점검 알림이 매일 오는 건 왜야?
>
> **🙋 B** 해킹당한 거야?
>
> **💬 A** 아니, 매일 정해진 시간에 스스로 점검하는 거야. 정상이면 조용해
>
> **🙋 B** 아 CCTV 같은 거네
>
> **💬 A** 맞아. 운영 중에 계속 지켜보고 이상하면 바로 대응하는 게 SecOps야

### SSL/TLS

`Infra` · Secure Sockets Layer / Transport Layer Security · 추가 2026-10-22

**정의** 인터넷 통신을 암호화하고, 접속한 서버가 진짜인지 확인해 주는 보안 규약. SSL은 옛 이름, 지금 실제로 쓰는 건 TLS.

**자세히**

TLS가 해 주는 일 3가지:  
- 암호화 — 중간에서 훔쳐봐도 내용을 못 읽는다
- 서버 신원 확인 — 인증서로 '이 서버가 진짜 sign.axmaster.cloud 맞다'를 증명
- 변조 방지 — 오가는 내용이 중간에 바뀌면 알아챈다

역사: SSL 2.0·3.0(구식, 취약점으로 폐기) → TLS 1.0·1.1(폐기) → TLS 1.2(현역) → TLS 1.3(최신, 2018). 습관적으로 'SSL 인증서'라고 부르지만 실제 통신은 TLS다.  

\[우리 서버 실제 사례 · 2026-10-22 직접 확인\] sign.axmaster.cloud, meeting.axmaster.cloud 모두 TLS 1.3 + 암호 방식 TLS\_AES\_128\_GCM\_SHA256으로 통신 중. 브라우저 검증 결과 'Verify return code: 0 (ok)'.

**흐름**

### UTF-8

`Infra` · Unicode Transformation Format - 8bit · 추가 2026-10-09

> **전 세계 모든 문자를 컴퓨터가 읽을 수 있는 숫자(바이트)로 변환하는 인코딩 방식**

**자세히**

UTF-8은 유니코드 문자를 1~4바이트로 변환하는 가변 길이 인코딩 방식이다. 영어는 1바이트, 한국어·중국어는 3바이트로 저장된다. 전 세계 모든 문자와 이모지까지 하나의 방식으로 처리할 수 있어 웹 표준으로 자리잡았다. UTF의 "8"은 8바이트라는 뜻이 아니라, 8비트(1바이트)를 기본 단위로 처리한다는 뜻이다. 실제 저장 크기는 문자마다 다른 가변 길이 방식이다.

**흐름**

- ① 문자 입력(예: '가')
- ② UTF-8 규칙으로 바이트 시퀀스 변환(한글 3바이트)
- ③ 파일·네트워크로 전송
- ④ 수신 측에서 UTF-8 디코딩
- ⑤ 원래 문자 복원

**헷갈리는 점**

- **흔한 오해** UTF-8의 '8'이 8바이트라고 오해
- **차이** 8 = 8비트(1바이트)를 기본 처리 단위로 사용한다는 의미. 실제 저장은 문자에 따라 1~4바이트
- **기억법** 영어=1바이트 / 한글=3바이트 / 이모지=4바이트 — 8비트 단위로 쪼개서 표현

**예시**

- 'A' → 0x41 (1바이트) — 영어는 1바이트
- '안' → 0xEC 0x95 0x88 (3바이트) — 한국어는 3바이트
- '😊' → 0xF0 0x9F 0x98 0x8A (4바이트) — 이모지는 4바이트
- &lt;meta charset='utf-8'> — HTML 파일이 UTF-8로 인코딩됐다는 선언
- 한글 파일 열었을 때 '깨지는' 현상 = 인코딩 방식이 안 맞아서 (EUC-KR vs UTF-8)
- UTF-8 vs UTF-16 vs UTF-32 — 기본 처리 단위가 각각 8비트/16비트/32비트
- UTF-8이 웹 표준인 이유 — 영어는 1바이트로 가볍고, 다국어도 모두 지원

**메모**

- **misconception** UTF-8의 '8'이 8바이트를 뜻한다고 오해하기 쉬움
- **correct** '8'은 8비트(1바이트)를 기본 처리 단위로 쓴다는 의미
- **comparison** {"UTF-8": "8비트 단위, 가변 길이(1~4바이트), 웹 표준", "UTF-16": "16비트 단위, 가변 길이(2~4바이트), 한글 2바이트", "UTF-32": "32비트 단위, 고정 4바이트, 모든 문자 동일"}

**카톡으로 이해하기**

> **💬 A** UTF-8이 뭔지 알아?
>
> **🙋 B** 뭔가 인코딩 관련된 거?
>
> **💬 A** 맞아! 유니코드 문자를 컴퓨터가 저장하고 전송할 수 있는 바이트로 변환하는 방식이야  
> 쉽게 말하면 한글·영어·중국어·이모지 다 표현할 수 있는 글자 인코딩 표준이야
>
> **🙋 B** 왜 UTF-8이 표준이 된 거야?
>
> **💬 A** 영어는 1바이트, 한글은 3바이트로 저장해서 효율적이야  
> 전 세계 거의 모든 문자를 지원하면서 영어 텍스트는 용량도 최소화해
>
> **🙋 B** 그럼 UTF-8 안 쓰면 어떻게 돼?
>
> **💬 A** 한글이 깨져서 '????' 이런 식으로 보여. 웹에서 한글 깨지면 십중팔구 UTF-8 문제야

### WSL2

`Infra` · Windows Subsystem for Linux 2 · 추가 2026-10-23

**정의** Windows 안에서 진짜 리눅스(Ubuntu 등)를 가벼운 가상 머신으로 돌리는 Microsoft 기능.

**자세히**

PowerShell에서 wsl --install -d Ubuntu로 설치, wsl -l -v로 버전 확인(VERSION 2여야 함). Windows 드라이브는 /mnt/c, /mnt/d로 보인다(D:\\AX = /mnt/d/AX).  

\[lecture\_016\] Claude Code의 명령 샌드박스(bubblewrap)는 macOS·Linux·WSL2에서만 동작하고 네이티브 Windows에서는 없다. 그래서 Claude Code는 WSL2 안에 설치해 실행한다. WSL1은 샌드박스 불가.  
주의: WSL2는 Windows와 연결돼 있어(interop, /mnt 드라이브) 완전 격리 수단이 아니다. /mnt 아래 작업은 속도가 느릴 수 있다.

**흐름**

- ① PowerShell: wsl --install -d Ubuntu
- ② 재부팅 + 사용자 이름·비밀번호 설정
- ③ wsl -l -v로 VERSION 2 확인
- ④ wsl -d Ubuntu로 진입
- ⑤ cd /mnt/d/AX 로 Windows 폴더 접근

**헷갈리는 점**

- **흔한 오해** WSL2 안에서 돌리면 Windows와 완전히 분리된다고 생각함
- **차이** WSL2는 Windows 드라이브(/mnt)와 Windows 프로그램 실행(interop)이 연결된 '이웃집'이다. 완전 분리는 VM
- **기억법** WSL2 = 같은 건물 다른 호수, VM = 다른 건물

**카톡으로 이해하기**

> **💬 A** WSL2 알아?
>
> **🙋 B** 윈도우에서 리눅스 쓰는 거?
>
> **💬 A** 맞아. 윈도우 안에 진짜 리눅스를 가볍게 띄우는 거야
>
> **🙋 B** Claude Code는 왜 거기서 돌려?
>
> **💬 A** Claude 샌드박스가 리눅스 기술이라 네이티브 윈도우에선 안 켜져
>
> **🙋 B** 그럼 WSL2 안이면 윈도우랑 완전 분리야?

### 노드 (Node, 클러스터의 서버 한 대)

`Infra` · Node · 추가 2026-11-02 · 보강 2026-11-02

> **큰 주방(클러스터)의 화구 하나**

**정의** 클러스터에 묶인 서버(컴퓨터) 한 대. 쿠버네티스에서는 실제로 컨테이너를 돌리는 일꾼 서버를 말한다.

**자세히**

비유: 클러스터가 큰 주방이면 노드는 그 안의 화구 하나다. 주방장(컨트롤 플레인)이 화구마다 요리(컨테이너)를 배정하고, 화구가 꺼지면 다른 화구로 옮긴다.  
실제: 노드는 실제 컴퓨터일 수도, 클라우드에서 빌린 가상 서버(VM)일 수도 있다. 노드 위에 컨테이너 묶음(Pod)이 올라가 실행된다. 노드를 늘리면 클러스터 전체 힘이 커진다.  
주의: 'Node'는 IT에서 여러 뜻으로 쓰인다 — 네트워크의 연결점, 그래프·트리의 점, 그리고 자바스크립트 실행기 Node.js. 문맥이 클러스터·쿠버네티스면 '서버 한 대'다.  

\[2026-11-02 보강\] 노드(화구) 위에는 컨테이너가 바로 올라가지 않고 쟁반(Pod) 단위로 올라간다. 화구 하나에 쟁반 여러 개가 올라갈 수 있다.

**흐름**

- ① 서버(실제 또는 가상) 준비
- ② 클러스터에 가입 = 노드가 됨
- ③ 주방장이 컨테이너를 배정
- ④ 상태를 지휘부에 계속 보고
- ⑤ 고장 나면 지휘부가 일을 다른 노드로 옮김

**헷갈리는 점**

- **흔한 오해** 노드(Node) vs Node.js
- **차이** 노드 = 클러스터에 묶인 서버 한 대 / Node.js = 자바스크립트를 서버에서 돌리는 프로그램. 'node 명령', 'FROM node:24 이미지'는 Node.js 쪽이다
- **기억법** 쿠버네티스 얘기면 화구(서버), 코드·명령어 얘기면 Node.js

**예시**

- 노드 3대 중 1대 고장 → 그 위의 컨테이너들이 남은 노드로 옮겨 감
- 손님 증가 → 클라우드가 노드를 자동으로 1대 더 붙임(노드 오토스케일링)
- \[우리 서버 실제 사례\] 우리 서버에서 자주 보이는 'node'는 대부분 Node.js(자바스크립트 실행기)다 — 예: sign 사이트 Dockerfile의 FROM node:24-alpine, 덱 검사 스크립트를 돌리는 node 명령. 클러스터의 노드와는 다른 말이다 (2026-11-02 확인)

**카톡으로 이해하기**

> **💬 A** 노드가 3대라는 게 무슨 말이야?
>
> **🙋 B** Node.js를 3번 설치했다는 거?
>
> **💬 A** 아니, 클러스터에 묶인 서버가 3대라는 뜻이야  
> 큰 주방에 화구가 3개 있는 거지
>
> **🙋 B** 그럼 우리 서버의 node는?
>
> **💬 A** 그건 Node.js야. 자바스크립트를 돌리는 프로그램이라 이름만 같아

### 도커 이미지 (Docker Image)

`Infra` · Docker Image · 추가 2026-10-26

> **사진(jpg·png)이 아니다 — 빌드로 포장한 '밀키트 상자'**

**정의** 프로그램 실행에 필요한 것(실행 엔진·부품·코드·설정)을 빌드한 순간 그대로 얼려 둔 복사본. 빌드의 결과물이다.

**자세히**

도커 이미지는 사진 파일(jpg·png)과 이름만 같고 전혀 다른 뜻이다. 컴퓨터 용어에서 '이미지'는 '어떤 순간의 상태를 통째로 떠 놓은 복사본'이라는 뜻도 있다. 윈도우 설치용 ISO 파일을 'CD 이미지', 디스크 전체 복사본을 '디스크 이미지'라고 부르는 것과 같은 쓰임이다. 사진이 그 순간의 장면을 찍어 두듯, 도커 이미지는 그 순간의 프로그램 상태를 찍어 둔다.  

밀키트 비유: 코드 = 레시피, 빌드 = 레시피대로 재료를 손질해 상자에 담는 일, 이미지 = 포장된 밀키트 상자, 컨테이너 = 상자를 뜯어 지금 조리 중인 요리, 배포 = 손님 식탁(서버)에 내놓는 일.  

이미지 자체는 아무 일도 하지 않는다. 켜야(docker run) 컨테이너가 되어 실제로 돌아간다. 이미지는 한 번 만들면 바뀌지 않는다(읽기 전용). 그래서 포장한 날의 Node·부품이 그대로 굳어 있고, 나중에 보안 수정이 나오거나 코드를 고쳐도 기존 이미지에는 반영되지 않는다 → 새로 빌드해야 한다.  

같이 나오는 말: 베이스 이미지 = Dockerfile 첫 줄(FROM)로 가져오는 기본 상자, 태그 = 이미지 이름 뒤 ':' 다음의 버전 이름표(node:22-alpine 의 22-alpine), 레지스트리 = 이미지를 보관·내려받는 창고(Docker Hub 등).

**흐름**

- ① Dockerfile = 레시피(설계도)
- ② docker build = 레시피대로 포장
- ③ 도커 이미지 = 포장된 밀키트 상자 (여기서 멈춰 있음)
- ④ docker run = 상자를 뜯어 조리 시작
- ⑤ 컨테이너 = 조리 중인 요리 (실제로 돌아가는 프로그램)

**헷갈리는 점**

- **흔한 오해** 도커 이미지 vs 사진 이미지(jpg·png)
- **차이** 사진 이미지 = 화면·장면을 담은 그림 파일 / 도커 이미지 = 프로그램 실행 환경을 통째로 떠 둔 복사본(빌드 결과물)
- **기억법** 둘 다 '그 순간을 찍어 둔 것' — 사진은 장면을, 도커 이미지는 프로그램 상태를 찍는다 (ISO 파일 = CD 이미지와 같은 뜻)

**예시**

- node:22-alpine = Node 22가 든 공식 기본(베이스) 이미지. ':' 뒤 '22-alpine'은 태그(버전 이름표)
- docker build → 이미지 생성 / docker images → 서버에 있는 이미지 목록 보기
- \[우리 서버 실제 사례\] 명부 서명 사이트(axis-sign 컨테이너): 2026-10-25에 확인해 보니 공개 화면이 10/19 첫 버전 코드와 똑같았다. 그 뒤에 고친 보안 강화판(10/19 시도 횟수 제한, 10/23 보안 패치)은 코드(레시피)만 준비돼 있고, 새 이미지로 빌드·배포되지 않은 상태 → 재빌드·재배포가 필요.
- \[우리 서버 실제 사례\] Hermes도 도커 이미지로 켠 컨테이너(hermes-work-hermes-agent-1)에서 돌아감 → Hermes 업데이트 = 새 버전 이미지로 바꿔 끼우기

**카톡으로 이해하기**

> **💬 A** 도커 이미지가 사진 파일 같은 거야?
>
> **🙋 B** 이름이 이미지니까 그림 아니야?
>
> **💬 A** 아니야! 이름만 같고 완전히 다른 뜻이야  
> 프로그램 실행에 필요한 걸 빌드한 순간 그대로 얼려 둔 복사본이야
>
> **🙋 B** 근데 왜 하필 '이미지'라고 불러?
>
> **💬 A** 컴퓨터에선 '그 순간 상태를 통째로 떠 둔 복사본'도 이미지라고 해  
> 윈도우 ISO 파일을 'CD 이미지'라고 부르잖아. 사진이 장면을 찍듯 이건 프로그램 상태를 찍은 거야
>
> **🙋 B** 그럼 이미지만 있으면 사이트가 돌아가?
>
> **💬 A** 아니, 이미지는 포장된 밀키트 상자야. 뜯어서 켜야(docker run) 컨테이너가 되고 그게 돌아가는 거야
>
> **🙋 B** 코드 고치면 이미지도 바뀌어?
>
> **💬 A** 안 바뀌어! 포장한 날 그대로 굳어 있어서 새로 빌드해야 해

### 디플로이먼트 (Deployment, 쿠버네티스)

`Infra` · Deployment (Kubernetes) · 추가 2026-11-02

> **'이 메뉴 쟁반을 항상 3개 유지해'라는 주문서**

**정의** '이 Pod를 이런 모습으로 항상 N개 유지해'라고 쿠버네티스에 맡기는 설정(주문서). 개수 유지·교체 배포·되돌리기를 맡는다.

**자세히**

비유: 주방장에게 주는 상시 주문서다. '김치찌개 쟁반을 항상 3개 준비해 둬'라고 적어 두면, 하나가 엎어져도 주방장이 알아서 새로 채운다. 레시피를 바꾸면 쟁반을 한꺼번에 버리지 않고 하나씩 새 레시피로 바꿔 손님이 끊기지 않게 한다.  
실제: YAML에 이미지(무슨 요리)·개수(replicas)·설정을 적어 제출한다. 쿠버네티스는 실제 Pod 수가 적어지면 늘리고, 이미지를 바꾸면 Pod를 하나씩 교체한다(롤링 업데이트). 문제가 생기면 이전 버전으로 되돌린다(롤백).  
주의: 이름이 '배포(Deploy)'와 같지만, 배포라는 '행동'이 아니라 쿠버네티스 안의 '설정 종류' 이름이다. GitOps에서는 이 YAML을 Git에 두고 Argo CD가 클러스터에 맞춘다.

**흐름**

- ① YAML에 이미지·개수(replicas) 적기
- ② 클러스터에 제출(또는 Git에 올리고 Argo CD가 반영)
- ③ 쿠버네티스가 Pod N개 생성
- ④ 계속 비교 — 모자라면 채움
- ⑤ 이미지 변경 → Pod 하나씩 교체
- ⑥ 문제 → 이전 버전으로 롤백

**헷갈리는 점**

- **흔한 오해** Deployment(쿠버네티스 설정) vs Deploy(배포 단계)
- **차이** Deploy = 만든 것을 서버에 올리는 '행동·단계' / Deployment = 쿠버네티스에서 Pod 개수·버전을 유지하는 '설정 종류'
- **기억법** 배포(행동)는 식탁에 올리기, 디플로이먼트(주문서)는 '항상 3개 준비'라는 상시 주문

**예시**

- replicas: 3 → Pod 하나가 죽으면 쿠버네티스가 자동으로 새 Pod를 띄워 다시 3개
- 이미지 1.2 → 1.3 변경 → Pod를 하나씩 교체(롤링 업데이트), 문제 시 1.2로 롤백
- \[우리 서버 실제 사례\] 우리 VPS는 쿠버네티스 없이 도커 컨테이너만 쓴다 — 쟁반(Pod) 없이 요리(컨테이너)를 화구에 바로 올리는 구조라 Pod·Deployment·Service가 없다. 대신 정문 역할은 Traefik이 한다 (2026-10 대화에서 확인한 구성 기준)

**카톡으로 이해하기**

> **💬 A** 디플로이먼트는 배포랑 같은 말이야?
>
> **🙋 B** 영어로 배포니까 같은 거 아니야?
>
> **💬 A** 쿠버네티스에선 '설정 이름'이야. 이 Pod를 항상 3개 유지하라는 주문서
>
> **🙋 B** 하나가 죽으면?
>
> **💬 A** 주방장이 알아서 하나 더 만들어 3개로 맞춰  
> 새 버전도 하나씩 바꿔 끼워서 손님이 안 끊겨

### 샌드박스 (Sandbox)

`Infra` · Sandbox · 추가 2026-10-12 · 보강 2026-10-23

> **외부와 격리된 안전한 실행 환경 — 위험한 코드·입력을 안에서만 실행해 시스템을 보호**

**자세히**

샌드박스는 모래놀이터처럼 '이 안에서는 뭘 해도 밖에 영향 없다'는 격리된 실행 공간이다. 악성 코드·검증되지 않은 입력·위험한 AI 프롬프트를 실제 시스템과 분리된 환경에서 실행해 피해를 막는다. 보안·개발·AI 세 분야 모두에서 핵심 개념이다.

**흐름**

- ① 의심스러운 입력·코드 수신
- ② 샌드박스 환경 생성 (격리된 공간)
- ③ 샌드박스 안에서 실행
- ④ 결과·출력만 추출
- ⑤ 샌드박스 폐기 (내부 흔적 제거)
- ⑥ 실제 시스템은 영향 없음

**헷갈리는 점**

- **흔한 오해** 샌드박스를 단순히 '테스트 환경'으로만 이해하는 경우
- **정확한 뜻** 테스트 환경도 샌드박스의 일종이지만 핵심은 '격리' — 안에서 일어나는 일이 밖에 영향을 못 줌
- **기억법** 모래놀이터(Sandbox) — 아이가 모래로 뭘 만들고 부숴도 놀이터 밖은 깨끗함

**예시**

- 브라우저 탭 — 각 탭이 샌드박스로 격리 → 한 탭이 해킹당해도 다른 탭·시스템 안전
- AI 프롬프트 인젝션 방어 — 의심스러운 입력을 샌드박스에서 실행 후 결과만 추출
- Docker 컨테이너 — 컨테이너 안에서 뭘 해도 호스트 서버에 영향 없음
- 바이러스 백신 — 의심 파일을 샌드박스에서 실행해 악성 여부 판단
- 개발 환경 — 실제 서버(운영)와 분리된 테스트 환경도 샌드박스 개념
- Claude Code /sandbox · Codex 권한 프로필 — AI 에이전트를 작업 폴더에 가두기 (lecture\_016)

**종류**

- **브라우저 샌드박스** 각 탭·iframe을 격리해 크로스 사이트 공격 방어
- **OS 샌드박스** 앱이 시스템 파일에 접근 못 하게 격리 (iOS 앱 권한)
- **컨테이너 샌드박스** Docker — 컨테이너 안에서만 실행
- **AI 샌드박스** 프롬프트 인젝션·악성 입력을 격리 실행 후 결과만 추출

**강의 보충** \[lecture\_016 보강\] AI 코딩 에이전트의 샌드박스는 '에이전트가 실행하는 명령'만 가둔다. Claude Code 샌드박스(bubblewrap, macOS·Linux·WSL2만): 기본값은 쓰기=작업폴더·임시폴더, 네트워크=허용 도메인만, 읽기=컴퓨터 대부분 허용(~/.ssh 포함) → 읽기 차단은 blockReadsOutsideWorkingDirectories를 같이 켜야 함. 파일 도구·MCP·훅은 샌드박스 밖. Codex Windows 샌드박스는 mxc(권장)/elevated/unelevated(읽기 거부 미지원) 3종. WSL2에서는 interop(powershell.exe 실행)이 샌드박스 우회로가 될 수 있음.

**카톡으로 이해하기**

> **💬 A** 샌드박스가 뭔지 알아?
>
> **🙋 B** 테스트 환경?
>
> **💬 A** 테스트 환경도 샌드박스의 일종이지만 핵심은 '격리'야  
> 안에서 일어나는 일이 밖에 영향을 못 주는 것
>
> **🙋 B** 왜 필요해?
>
> **💬 A** 코드 실행하거나 파일 처리할 때 보안 위협이 있을 수 있잖아  
> 샌드박스 안에서 실행하면 문제 생겨도 샌드박스 밖은 안전해
>
> **🙋 B** AI 에이전트에서도 쓰이는 거야?
>
> **💬 A** 맞아! AI가 코드 실행할 때 샌드박스 안에서 실행해서 시스템 건드리지 못하게 해  
> 하네스 엔지니어링의 핵심 요소야  
> 모래놀이터(Sandbox) — 뭘 만들고 부숴도 놀이터 밖은 깨끗함

<a id="term-016"></a>

### 서버

`Infra` · Server · 추가 2026-10-05

**정의** 다른 컴퓨터(클라이언트)의 요청을 받아 처리하고 응답을 돌려주는 컴퓨터 또는 프로그램.

**자세히**

인터넷에서 '서비스를 제공하는 쪽'이 서버, '요청하는 쪽'이 클라이언트.  
브라우저(클라이언트)가 naver.com을 요청하면 네이버 서버가 HTML을 돌려주는 구조.  

서버의 종류:  
- 웹 서버: HTML·이미지 등 정적 파일 제공 (Nginx, Apache)
- 애플리케이션 서버: 비즈니스 로직 처리 (Node.js, Python, Java)
- DB 서버: 데이터 저장·조회 (MySQL, PostgreSQL)
- AI 추론 서버: LLM 모델 실행 및 응답 생성

물리 서버 vs 클라우드 서버:  
- 물리 서버: 직접 구매·관리하는 하드웨어
- 클라우드 서버: AWS·GCP·Azure에서 빌려 쓰는 가상 서버 (VPS 포함)

### 서버 3단 구조 (3-Tier Architecture)

`Infra` · 3-Tier Architecture · 추가 2026-10-09

> **웹서버 → AP서버 → DB서버로 역할을 나눈 웹 서비스의 기본 구조**

**자세히**

서버 3단 구조는 웹 서비스를 프레젠테이션(웹서버)·비즈니스 로직(AP서버)·데이터(DB서버) 3개 계층으로 나눈 아키텍처다. 각 계층이 역할이 분리되어 있어 유지보수·확장이 쉽다.

**흐름**

- ① 사용자 요청 → 웹서버(1단: 요청 수신·정적파일)
- ② 웹서버 → AP서버(2단: 비즈니스 로직 처리)
- ③ AP서버 → DB서버(3단: 데이터 저장·조회)
- ④ DB→AP→웹서버→사용자 역순으로 응답 반환

**헷갈리는 점**

- **흔한 오해** 3단 구조를 물리적으로 서버 3대가 필요하다고 오해
- **차이** 개념적 구조이므로 작은 서비스는 1대 서버에서 3가지 역할 모두 수행 가능
- **기억법** 접수창구(웹) → 업무처리(AP) → 서류보관(DB) — 역할 분리가 핵심

**예시**

- 브라우저 → 웹서버(nginx, 요청 접수) → AP서버(Node.js, 로직 처리) → DB서버(MySQL, 데이터 저장)
- 맥도날드 비유: 카운터(웹서버) → 주방장(AP서버) → 냉장창고(DB서버)
- 로그인 흐름: 브라우저가 요청 → 웹서버 수신 → AP서버가 DB에서 계정 확인 → 결과 반환
- 동아리 홈페이지 구조: nginx → Node.js → MySQL

**구조**

- **1단** 웹서버 (nginx, Apache) — 요청 접수·정적 파일 서빙
- **2단** AP서버 (Node.js, Spring, Django) — 비즈니스 로직 처리
- **3단** DB서버 (MySQL, PostgreSQL, MongoDB) — 데이터 저장·조회

**카톡으로 이해하기**

> **💬 A** 서버 3단 구조가 뭔지 알아?
>
> **🙋 B** 그냥 서버 여러 개?
>
> **💬 A** 웹서버-AP서버-DB서버로 역할 나눈 구조야  
> 브라우저 요청 → 웹서버(nginx) → AP서버(Node.js) → DB서버(MySQL) 이 흐름
>
> **🙋 B** 왜 하나로 안 해?
>
> **💬 A** 역할을 분리하면 유지보수·확장이 쉬워  
> 트래픽 많아지면 AP서버만 늘릴 수 있고, DB 서버는 별도로 최적화할 수 있어
>
> **🙋 B** 아 분리하면 각각 독립적으로 관리 가능하구나
>
> **💬 A** 맞아! 웹서버는 대문, AP서버는 두뇌, DB서버는 창고 역할이야  
> 다 합친 게 풀스택 서버 구조야

### 서비스 (Service, 쿠버네티스)

`Infra` · Service (Kubernetes) · 추가 2026-11-02

> **쟁반이 바뀌어도 그대로인 고정 픽업 창구**

**정의** 계속 바뀌는 Pod들 앞에 놓는 고정 주소(이름·IP). 손님 요청을 살아 있는 Pod들로 나눠 보낸다.

**자세히**

비유: 쟁반(Pod)은 일회용이라 바뀔 때마다 번호표(IP)가 달라진다. 손님이 번호표를 쫓아다니게 할 수 없으니, 바뀌지 않는 픽업 창구를 하나 두고 창구가 그때그때 준비된 쟁반을 내준다. 쟁반이 3개면 손님을 골고루 나눠 준다.  
실제: 서비스는 고정된 이름과 내부 IP를 갖고, 꼬리표(label)가 맞는 Pod들을 찾아 요청을 나눠 보낸다(부하 분산). 종류: ClusterIP(클러스터 안에서만), NodePort·LoadBalancer(밖에서 들어오게). 바깥 도메인과 HTTPS는 보통 Ingress(정문)가 서비스 앞에서 맡는다.  
주의: 일상어 '서비스(웹서비스)'나 SaaS의 Service와 다른, 쿠버네티스 안의 설정 이름이다.

**흐름**

- ① 서비스에 꼬리표(label) 지정
- ② 꼬리표가 맞는 Pod들 자동으로 찾기
- ③ 고정 이름·주소로 요청 받기
- ④ 살아 있는 Pod들에 나눠 보내기
- ⑤ Pod가 바뀌면 연결 대상 자동 갱신

**헷갈리는 점**

- **흔한 오해** 서비스(쿠버네티스) = 웹서비스·SaaS
- **차이** 일상어 서비스 = 사용자에게 제공하는 기능 전체 / 쿠버네티스 Service = Pod들 앞의 고정 주소·창구(설정 이름)
- **기억법** 쟁반은 바뀌어도 창구는 그대로

**예시**

- Pod 3개(IP 계속 바뀜) 앞에 서비스 'web' → 다른 앱은 'web'이라는 이름으로만 부르면 됨
- Pod 하나가 새로 만들어져도 서비스가 자동으로 새 Pod를 연결
- \[우리 서버 실제 사례\] 우리 VPS는 쿠버네티스 없이 도커 컨테이너만 쓴다 — 쟁반(Pod) 없이 요리(컨테이너)를 화구에 바로 올리는 구조라 Pod·Deployment·Service가 없다. 대신 정문 역할은 Traefik이 한다 (2026-10 대화에서 확인한 구성 기준)

**카톡으로 이해하기**

> **💬 A** Pod가 다시 만들어지면 주소가 바뀐다며? 그럼 어떻게 찾아가?
>
> **🙋 B** 바뀐 주소를 매번 알려 줘야 하나?
>
> **💬 A** 그래서 서비스를 둬. 바뀌지 않는 픽업 창구야  
> 손님은 창구 이름만 부르면 창구가 살아 있는 Pod로 연결해
>
> **🙋 B** Pod가 3개면?
>
> **💬 A** 골고루 나눠 보내. 부하 분산도 같이 해 주는 거지

### 스토리지

`Infra` · Storage · 추가 2026-10-05

**정의** 데이터를 저장하고 필요할 때 꺼내 쓸 수 있도록 보관하는 공간 또는 시스템.

**자세히**

컴퓨터에서 '기억하는 곳'이 스토리지다.  

종류:  
- 로컬 스토리지: 내 컴퓨터 하드디스크·SSD
- 클라우드 스토리지: 인터넷에 저장 (Google Drive, S3, Dropbox)
- 오브젝트 스토리지: 이미지·영상·파일 같은 비정형 데이터 저장 (AWS S3)
- 블록 스토리지: 서버에 붙이는 가상 디스크 (AWS EBS)
- 데이터베이스: 정형 데이터를 구조화해서 저장·조회

브라우저 맥락:  
- localStorage: 브라우저에 데이터를 영구 저장 (창 닫아도 유지)
- sessionStorage: 탭을 닫으면 사라지는 임시 저장
- IndexedDB: 브라우저 내 대용량 구조화 데이터 저장

BaaS 맥락: Firebase Storage, Supabase Storage처럼 백엔드 없이 파일을 클라우드에 직접 올릴 수 있는 서비스도 있음.

**흐름**

- ① 데이터 생성
- ② 스토리지에 저장(파일·DB·오브젝트)
- ③ 필요 시 조회·수정·삭제
- ④ 백업·복제로 안전 보관

**헷갈리는 점**

- **흔한 오해** 스토리지와 캐시 혼동
- **차이** 스토리지 = 영구 저장 / 캐시 = 빠른 임시 저장(만료 후 삭제)
- **기억법** 스토리지 = 냉장고(영구) / 캐시 = 식탁 위 음식(임시)

**카톡으로 이해하기**

> **💬 A** 클라우드 스토리지랑 그냥 스토리지랑 뭐가 달라?
>
> **🙋 B** 스토리지 그냥 저장 공간 아니야?
>
> **💬 A** 맞아! 데이터 저장하고 필요할 때 꺼내 쓸 수 있는 공간이야  
> 로컬 스토리지는 내 컴퓨터 하드디스크, 클라우드는 인터넷 너머 서버에 저장하는 거고
>
> **🙋 B** 그럼 종류도 여러 가지야?
>
> **💬 A** 응. 블록 스토리지(SSD처럼 빠름), 오브젝트 스토리지(이미지·영상 저장에 최적, S3 같은 것)  
> 파일 스토리지(일반 폴더 구조) 등 있어
>
> **🙋 B** AI 에이전트도 스토리지 써?
>
> **💬 A** 당연하지. 에이전트 메모리도 스토리지야

### 인증 기관 (CA)

`Infra` · Certificate Authority · 추가 2026-10-22

**정의** 인증서를 발급하고 '이 서버는 진짜다'라고 보증해 주는 신뢰 기관. 브라우저가 미리 믿는 목록에 들어 있다.

**자세히**

브라우저·운영체제는 믿을 수 있는 최상위 인증기관(루트 CA) 목록을 처음부터 갖고 있다. 이 목록에 있는 기관이 보증한 인증서만 🔒로 통과시킨다.  

대표 인증기관: Let's Encrypt(ISRG, 무료), DigiCert, Sectigo, GlobalSign, Google Trust Services.  

인증기관이 아무 데서나 발급하지 않도록 엄격한 감사를 받고, 잘못 발급하면 브라우저 신뢰 목록에서 퇴출된다.  

\[우리 서버 실제 사례 · 2026-10-22 직접 확인\] 우리 VPS 인증서의 보증 기관은 Let's Encrypt, 그 위 최상위는 ISRG Root X1.

**흐름**

- ① 브라우저에 루트 CA 목록이 미리 들어 있음
- ② 서버가 인증서 제시
- ③ 브라우저가 발급자를 따라 올라감
- ④ 목록에 있는 루트 CA에 닿으면 신뢰
- ⑤ 닿지 않으면 '안전하지 않음' 경고

**헷갈리는 점**

- **흔한 오해** 인증기관이 사이트 내용까지 심사한다고 생각함
- **차이** DV 인증서 기준으로는 '주소의 주인인가'만 확인. 사이트가 정직한지는 보지 않는다
- **기억법** 인증기관 = 주민센터. 신분증은 떼 주지만 그 사람이 착한지는 보증 안 한다

**카톡으로 이해하기**

> **💬 A** 인증기관(CA)이 뭔지 알아?
>
> **🙋 B** 인증서 주는 곳?
>
> **💬 A** 맞아. '이 서버 진짜다'라고 보증해 주는 기관이야
>
> **🙋 B** 아무나 인증기관 할 수 있어?
>
> **💬 A** 아니. 브라우저가 미리 믿는 목록이 있어서 거기 있어야 해  
> 잘못 발급하면 목록에서 퇴출돼
>
> **🙋 B** 우리 서버는 어디서 받았어?
>
> **💬 A** Let's Encrypt. 그 위 최상위가 ISRG Root X1이야  
> 주민센터가 신분증 떼 주는 거랑 비슷해

### 인증서 (SSL/TLS Certificate)

`Infra` · SSL/TLS Certificate · 추가 2026-10-22

**정의** '이 서버는 이 주소의 진짜 주인이다'를 인증기관이 보증해 주는 디지털 신분증. 공개키와 유효기간이 들어 있다.

**자세히**

인증서에 들어 있는 것:  
- 주소(Subject/SAN) — 어느 도메인용인지
- 발급자(Issuer) — 누가 보증했는지
- 유효기간 — 언제부터 언제까지
- 공개키 — 암호 연결에 쓰는 열쇠
- 발급자의 서명 — 위조 방지

확인 수준 3단계:  
- DV(도메인 인증) — 주소의 주인인지만 확인. 자동·무료 (Let's Encrypt)
- OV(기관 인증) — 회사 실체까지 확인
- EV(확장 인증) — 가장 엄격한 법인 확인

\[우리 서버 실제 사례 · 2026-10-22 직접 확인\]  
- sign.axmaster.cloud — Let's Encrypt(YR1) 발급, 2026-10-19 ~ 2027-01-17 (90일), RSA 4096bit
- meeting.axmaster.cloud — Let's Encrypt(YR2) 발급, 2026-09-15 ~ 2026-12-14 (90일)

### 인증서 체인 (Chain of Trust)

`Infra` · Certificate Chain / Chain of Trust · 추가 2026-10-22

**정의** 우리 인증서 → 중간 인증기관 → 최상위(루트) 인증기관으로 이어지는 보증의 사슬. 브라우저는 이 사슬을 따라 올라가 루트에 닿으면 믿는다.

**자세히**

왜 사슬인가: 최상위(루트) 열쇠는 너무 중요해서 금고에 보관(오프라인)하고, 평소 발급은 중간 인증기관이 한다. 중간이 털려도 루트는 안전하게 남는다.  

3층 구조:  
- 서버 인증서(Leaf) — 우리 도메인용
- 중간 인증서(Intermediate) — 실제 발급 담당
- 루트 인증서(Root) — 브라우저에 미리 내장

\[우리 서버 실제 사례 · 2026-10-22 직접 확인\] sign.axmaster.cloud 체인:  
CN=sign.axmaster.cloud → Let's Encrypt YR1(중간) → ISRG Root YR → ISRG Root X1(루트)  
axmaster.cloud 체인: Let's Encrypt YE2 → ISRG Root YE → ISRG Root X2 → ISRG Root X1

**흐름**

- ① 서버가 자기 인증서 + 중간 인증서를 함께 보냄
- ② 브라우저가 서명을 따라 한 칸씩 위로
- ③ 중간 인증서의 발급자 확인
- ④ 내장된 루트 인증서에 도착
- ⑤ 사슬이 끊김 없이 이어지면 🔒 통과

**헷갈리는 점**

- **흔한 오해** 서버는 자기 인증서만 보내면 된다고 생각함
- **차이** 중간 인증서도 같이 보내야 한다. 빠뜨리면 일부 기기(특히 모바일)에서 '신뢰할 수 없음' 오류가 난다
- **기억법** 추천서의 추천서 — 나를 보증한 사람을 또 누가 보증했는지까지 보여 줘야 믿는다

**카톡으로 이해하기**

> **💬 A** 인증서 체인이라고 들어봤어?
>
> **🙋 B** 체인? 사슬?
>
> **💬 A** 응. 보증의 사슬이야  
> 우리 인증서를 Let's Encrypt가 보증하고, Let's Encrypt를 ISRG Root가 보증해
>
> **🙋 B** 왜 그렇게 여러 단계야?
>
> **💬 A** 최상위 열쇠는 너무 중요해서 금고에 넣어 두거든  
> 평소 발급은 중간 기관이 해
>
> **🙋 B** 브라우저는 어떻게 믿어?
>
> **💬 A** 사슬을 따라 올라가서 자기가 원래 아는 루트에 닿으면 믿어  
> 추천서의 추천서 같은 거야

### 최소 권한 원칙 (Least Privilege)

`Infra` · Principle of Least Privilege · 추가 2026-10-23

**정의** 프로그램·사람·AI에게 일을 끝내는 데 꼭 필요한 만큼의 권한만 주는 보안 원칙.

**자세히**

권한이 클수록 실수·해킹·AI 오작동 때 피해도 커진다. 그래서 '되는지'가 아니라 '이것만 되면 충분한지'를 기준으로 권한을 정한다.  
OpenAI Codex 문서도 권한 프로필을 '최소 권한 경계(least-privilege boundaries)'를 위한 기능으로 소개하고, '작업을 끝낼 수 있는 가장 좁은 프로필'을 고르라고 안내한다.  

\[lecture\_016 사례\] AI 에이전트에게 D:\\AX만 쓰기 허용 + 나머지 읽기 거부 + 명령 네트워크 차단.

**흐름**

- ① 할 일 정의 (예: AX 폴더 문서 정리)
- ② 필요한 권한만 목록화 (AX 읽기·쓰기)
- ③ 나머지는 기본 거부 (:root deny)
- ④ 꼭 필요한 예외만 추가 (:minimal 읽기)
- ⑤ 테스트로 '밖은 막히고 안은 되는지' 확인

**헷갈리는 점**

- **흔한 오해** 권한을 넉넉히 줘야 AI가 일을 잘한다고 생각함
- **차이** 권한이 넓어도 결과물 품질은 안 오른다. 사고 났을 때 피해 범위만 커진다
- **기억법** 호텔 카드키 — 내 방만 열리면 충분하다. 마스터키는 필요 없다

**카톡으로 이해하기**

> **💬 A** 최소 권한 원칙 알아?
>
> **🙋 B** 권한을 최소로 준다는 거?
>
> **💬 A** 응, 일 끝내는 데 꼭 필요한 만큼만 주는 거야
>
> **🙋 B** 넉넉히 주면 AI가 더 잘하지 않아?
>
> **💬 A** 일 품질은 그대로고, 사고 나면 피해만 커져  
> 호텔 카드키처럼 내 방만 열리면 충분해
>
> **🙋 B** 우리 가이드에선?
>
> **💬 A** D:\\AX만 쓰게 하고 나머지는 읽기도 막았어

### 캐싱 (Caching)

`Infra` · Caching · 추가 2026-10-09

> **자주 쓰는 데이터를 빠른 저장소에 미리 저장해 두고 빠르게 꺼내 쓰는 기법**

**자세히**

캐싱은 매번 DB나 서버에서 데이터를 가져오는 대신, 자주 쓰는 데이터를 메모리(RAM) 같은 빠른 저장소에 임시 저장해 두는 방식이다. 응답 속도를 크게 높이고 서버 부하를 줄인다. Redis가 대표적인 캐시 서버다.

**흐름**

- ① 첫 요청: DB·서버에서 데이터 조회(느림)
- ② 조회 결과를 캐시에 저장
- ③ 두 번째 요청: 캐시에서 바로 반환(빠름)
- ④ 캐시 만료 시 다시 원본에서 조회 후 캐시 갱신

**헷갈리는 점**

- **흔한 오해** 캐싱(Caching)과 스토리지(Storage)를 혼동하기 쉬움
- **차이** 스토리지=영구 저장 / 캐시=임시 저장(빠른 접근용, 만료 시 삭제)
- **기억법** 캐시 = 책상 위 메모지(빠르게 꺼냄, 임시) / 스토리지 = 서류 캐비넷(영구 보관)

**예시**

- 네이버 메인 뉴스 — 매번 DB 조회하지 않고 1분마다 캐시 갱신
- 브라우저 캐시 — 같은 이미지를 매번 다운받지 않고 로컬에 저장
- CDN — 전 세계 서버에 콘텐츠를 캐싱해 가까운 서버에서 빠르게 전달
- LLM 응답 캐싱 — 같은 질문이 반복되면 저장된 답변을 즉시 반환

**카톡으로 이해하기**

> **💬 A** 캐싱이 왜 중요해?
>
> **🙋 B** 그냥 저장하는 거 아니야?
>
> **💬 A** 캐싱은 자주 쓰는 데이터를 빠른 곳에 미리 저장해두는 거야  
> DB까지 매번 갔다오면 느린데, 캐시에 있으면 바로 돌려줄 수 있어
>
> **🙋 B** 영구 저장이랑 다른 거야?
>
> **💬 A** 달라! 캐시는 임시 저장이야. 만료되면 삭제돼  
> 스토리지 = 서류 캐비넷(영구 보관) / 캐시 = 책상 위 메모지(빠르게 꺼냄, 임시)
>
> **🙋 B** 그럼 언제 지워지는 거야?
>
> **💬 A** TTL(Time To Live) 설정해서 일정 시간 지나면 삭제해  
> 그리고 데이터가 바뀌면 캐시도 지워야 해 — 이게 캐시 무효화 문제야  
> 캐싱 전략 잘못하면 오래된 데이터 계속 보여주는 버그 생겨

### 컨테이너 (Container)

`Infra` · Container · 추가 2026-10-26 · 보강 2026-11-02

> **이미지가 밀키트 상자라면, 컨테이너는 상자를 뜯어 조리 중인 요리**

**정의** 도커 이미지를 실제로 켜서 지금 돌아가고 있는 프로그램.

**자세히**

서버에서 실제로 사용자의 요청을 받는 것은 이미지가 아니라 컨테이너다. 상자 하나로 요리를 여러 번 할 수 있듯, 이미지 하나로 컨테이너를 여러 개 켤 수 있다.  

컨테이너는 켜질 때 쓴 이미지를 그대로 따른다. 그래서 새 이미지를 빌드해도 이미 켜져 있는 컨테이너는 저절로 바뀌지 않는다 — 옛 컨테이너를 끄고 새 이미지로 다시 켜야 한다(재배포). 같은 이미지로 끄고 켜기만 하는 '재시작'은 내용이 바뀌지 않는다.  

컨테이너를 지우면 그 안에서 바뀐 내용도 같이 사라진다. 그래서 남겨야 할 데이터(명부·서명 등)는 컨테이너 밖의 저장 공간인 '볼륨'에 둔다. 컨테이너는 가상머신(VM)처럼 컴퓨터 전체를 흉내 내지 않고 서버의 운영체제를 함께 쓰면서 앱만 따로 격리하기 때문에 가볍다(자세한 비교는 Docker 항목).  

\[2026-11-02 보강\] 쿠버네티스에서는 컨테이너(요리)를 쟁반(Pod)에 담아 옮긴다 — 보통 쟁반 하나에 컨테이너 하나.

**흐름**

- ① 도커 이미지(상자) 준비
- ② docker run — 이미지로 컨테이너 켜기(조리 시작)
- ③ 실행 중 — 사용자 요청을 받음 (docker ps로 확인)
- ④ docker stop — 끄기 (다시 켜면 같은 내용 그대로)
- ⑤ docker rm — 지우기: 안에서 바뀐 내용은 사라지고, 볼륨의 데이터는 남음

**헷갈리는 점**

- **흔한 오해** 이미지 vs 컨테이너
- **차이** 이미지 = 멈춰 있는 포장 결과물(실행 안 됨) / 컨테이너 = 그 이미지로 켠, 지금 돌아가는 프로그램
- **기억법** 이미지 = 밀키트 상자, 컨테이너 = 조리 중인 요리. 상자 하나로 요리 여러 번 가능

**예시**

- \[우리 서버 실제 사례\] axis-sign = 명부 서명 사이트 컨테이너 / hermes-work-hermes-agent-1 = 지금 대답하는 Hermes 컨테이너
- docker ps = 지금 켜져 있는 컨테이너 목록 / docker ps -a = 꺼진 것까지 전부
- docker logs --tail 50 axis-sign = 그 컨테이너가 남긴 기록 마지막 50줄 보기
- 명부 서명 사이트는 데이터를 /data 볼륨에 저장하도록 설계(DATA\_DIR=/data) → 컨테이너를 새로 만들어도 명부·서명은 남음

**카톡으로 이해하기**

> **💬 A** 이미지랑 컨테이너가 뭐가 달라?
>
> **🙋 B** 둘 다 도커 아니야?
>
> **💬 A** 이미지는 포장된 밀키트 상자고, 컨테이너는 그걸 뜯어서 조리 중인 요리야  
> 서버에서 실제로 손님 받는 건 컨테이너야
>
> **🙋 B** 새 이미지 만들면 컨테이너도 알아서 바뀌어?
>
> **💬 A** 아니! 이미 조리 중인 요리는 그대로야. 옛 컨테이너 끄고 새 이미지로 다시 켜야 해
>
> **🙋 B** 컨테이너 끄면 명부 데이터 날아가는 거 아니야?
>
> **💬 A** 그래서 데이터는 '볼륨'이라는 바깥 창고에 둬. 컨테이너를 새로 만들어도 남아 있어

### 크론 (Cron, 예약 작업)

`Infra` · Cron / Scheduled Job · 추가 2026-10-21

**정의** 정해진 시간에 정해진 스크립트를 그대로 실행하는 서버의 예약 작업 기능.

**자세히**

\[lecture\_015 루프 엔지니어링 입문\]  
크론은 리눅스 서버의 예약 실행 기능. '0 8 \* \* \*' 같은 표기로 매일 아침 8시를 뜻한다(분 시 일 월 요일).  

크론 vs 루프 (강의 핵심 대비):  
- 예약 작업(cron) — 정해진 시간에 정해진 스크립트를 그대로 실행. 상황이 달라져도 늘 같은 일만 하고 결과를 보지 않는다
- 루프 — 정해진 시간에 지금 상태를 보고 다음 행동을 고르는 AI를 실행. 결과를 검사하고, 안 되면 다시 하고, 되면 멈춘다

크론은 루프의 '시간 기반 트리거'로 쓰일 수 있다.  

\[우리 서버 실제 사례\] Hermes 크론잡 = 크론(트리거) + AI 에이전트 실행. 검사·멈춤 조건까지 넣으면 루프가 된다.

**흐름**

- ① 시간 표기 작성 (예: 0 8 \* \* \* = 매일 8시)
- ② 실행할 작업 등록
- ③ 지정 시각 도달
- ④ 작업을 그대로 실행
- ⑤ (결과를 보지 않고) 다음 예약까지 대기

**헷갈리는 점**

- **흔한 오해** 크론으로 AI를 매일 돌리면 루프 엔지니어링이다
- **차이** 크론은 '언제'만 해결. 결과 검사·재시도·멈춤이 없으면 그냥 예약 실행. 루프는 결과를 보고 다음 행동을 고른다
- **기억법** 크론 = 매일 같은 시간 울리는 알람 / 루프 = 알람에 일어나서 상황 보고 할 일 정하는 사람

**카톡으로 이해하기**

> **💬 A** 크론이 뭔지 알아?
>
> **🙋 B** 서버 용어 같은데 잘 몰라
>
> **💬 A** 정해진 시간에 정해진 작업을 그대로 실행하는 예약 기능이야  
> '0 8 \* \* \*' 이렇게 쓰면 매일 아침 8시야
>
> **🙋 B** 그럼 크론으로 AI 매일 돌리면 루프야?
>
> **💬 A** 아니, 그게 제일 헷갈리는 부분이야  
> 크론은 결과를 안 봐. 상황이 바뀌어도 늘 같은 일만 해
>
> **🙋 B** 루프는?
>
> **💬 A** 지금 상태 보고 다음 행동을 골라. 검사하고, 안 되면 다시, 되면 멈춰  
> 크론은 루프를 깨우는 알람 역할로 쓰는 거야

### 클러스터 (Cluster)

`Infra` · Cluster · 추가 2026-11-02 · 보강 2026-11-02

> **화구 여러 개를 묶은 큰 주방 하나 — 화구 하나가 꺼져도 요리는 계속 나간다**

**정의** 여러 대의 서버(노드)를 묶어서 한 대처럼 쓰는 묶음. 영어 cluster는 '포도송이'라는 뜻이다.

**자세히**

비유: 서버 한 대 = 화구 하나. 클러스터 = 화구 여러 개를 묶은 큰 주방 하나. 주방장(쿠버네티스)이 어느 화구에서 어떤 요리(컨테이너)를 할지 정하고, 화구 하나가 고장 나면 그 요리를 다른 화구로 옮긴다.  
실제: 쿠버네티스 클러스터는 '지휘하는 부분(컨트롤 플레인)' + '일하는 서버들(노드)'로 이뤄진다. 사람은 서버마다 들어가지 않고 클러스터에 '이 앱을 3개 띄워 줘'라고 한 번 지시하면, 클러스터가 알아서 노드에 나눠 배치한다.  
왜 묶나: ① 한 대가 고장 나도 서비스가 멈추지 않는다(고가용성) ② 손님이 몰리면 서버를 더 붙이고 한가하면 줄인다(확장) ③ 여러 대를 한 번에 관리한다.  
다른 뜻: DB 클러스터(데이터베이스 여러 대 묶음)도 같은 '묶음' 뜻이다. 머신러닝의 '클러스터링(군집화)'은 이름만 비슷하고 전혀 다른 것이다.  

\[2026-11-02 보강\] 주방 안의 크기 순서: 클러스터(주방) > 노드(화구) > Pod(쟁반) > 컨테이너(요리). 전체 지도는 '흐름: 쿠버네티스 큰 주방 지도 (클러스터→노드→Pod→컨테이너)'.

**흐름**

- ① 서버 여러 대 준비 — 노드
- ② 지휘부(컨트롤 플레인) 설치 — 쿠버네티스
- ③ 노드들을 지휘부에 연결 = 클러스터 완성
- ④ '앱을 N개 띄워 줘' 설정(YAML) 제출
- ⑤ 지휘부가 노드에 나눠 배치
- ⑥ 노드 고장·손님 증가 시 자동으로 옮기고 늘림

**헷갈리는 점**

- **흔한 오해** ① 컨테이너가 여러 개면 클러스터다 ② 클러스터 = 머신러닝 클러스터링
- **차이** ① 클러스터는 '서버 여러 대'의 묶음. 서버 한 대에 컨테이너가 여러 개면 그냥 서버 1대다 ② 클러스터링(군집화)은 비슷한 데이터끼리 무리 짓는 분석 방법 — '묶음'이라는 뜻만 같다
- **기억법** 화구(서버)가 여러 개여야 큰 주방(클러스터). 냄비(컨테이너)가 여러 개인 건 상관없다

**예시**

- 노드 3대짜리 쿠버네티스 클러스터에 웹앱 6개 → 노드마다 2개씩 배치, 노드 1대가 꺼지면 남은 2대로 옮겨 계속 서비스
- 클라우드의 관리형 클러스터: AWS EKS, Google GKE, Azure AKS
- \[우리 서버 실제 사례\] 우리는 호스팅어 VPS 한 대(VPS-IP) 위에 Hermes·Traefik·sign 사이트 등 도커 컨테이너 여러 개를 띄워 쓴다 — 화구 하나에 냄비 여러 개를 올린 '서버 1대' 구성이라 클러스터가 아니고, 쿠버네티스·Argo CD도 쓰지 않는다 (2026-10 대화에서 확인한 구성 기준)

**카톡으로 이해하기**

> **💬 A** 클러스터가 뭐야?
>
> **🙋 B** 컨테이너 여러 개 모아 둔 거?
>
> **💬 A** 아니, 서버 여러 대를 묶어서 한 대처럼 쓰는 거야  
> 화구 여러 개를 묶은 큰 주방이라고 보면 돼
>
> **🙋 B** 우리 서버도 컨테이너 여러 개잖아. 그럼 클러스터야?
>
> **💬 A** 우리는 서버 한 대에 컨테이너만 여러 개야  
> 화구 하나에 냄비 여러 개 올린 거라 클러스터는 아니야
>
> **🙋 B** 머신러닝 클러스터링이랑은?
>
> **💬 A** 그건 데이터를 비슷한 것끼리 무리 짓는 분석이야. 이름만 닮았어

### 프로토콜 (Protocol)

`Infra` · Protocol · 추가 2026-10-09

> **컴퓨터끼리 데이터를 주고받을 때 지켜야 하는 규칙과 약속**

**자세히**

프로토콜은 서로 다른 기기·시스템이 데이터를 주고받을 때 '이 형식으로 보내고, 이 순서로 확인하자'고 약속한 규칙이다. 사람으로 치면 언어와 예절이다. 대표적으로 HTTP(웹), TCP/IP(인터넷 기본), HTTPS(보안 웹), FTP(파일 전송) 등이 있다.

**흐름**

- ① 송신측이 프로토콜 규칙대로 데이터 포장
- ② 네트워크로 전송
- ③ 수신측이 같은 프로토콜로 해석
- ④ 데이터 복원

**헷갈리는 점**

- **흔한 오해** HTTP와 HTTPS를 단순히 자물쇠 유무로만 이해
- **차이** HTTP = 평문 전송(누구나 볼 수 있음) / HTTPS = TLS 암호화 전송(중간에서 못 읽음)
- **기억법** 프로토콜 = 외교 의전 규칙 — 나라(기기)마다 다르면 소통 불가, 공통 규칙 필요

**예시**

- HTTP — 브라우저와 서버가 웹 페이지를 주고받는 규칙
- HTTPS — HTTP + 암호화(TLS) = 보안 통신
- TCP/IP — 인터넷의 기본 전송 규칙 (패킷 분할·재조립·순서 보장)
- API 호출도 프로토콜 위에서 동작 — REST API = HTTP 프로토콜 기반

**카톡으로 이해하기**

> **💬 A** 프로토콜이 뭔지 알아? HTTP가 프로토콜이잖아
>
> **🙋 B** HTTP가 뭔가 규칙이라는 건 알아
>
> **💬 A** 프로토콜 = 컴퓨터끼리 통신하는 공통 규칙이야  
> 외교 의전처럼, 서로 다른 기기가 소통하려면 같은 규칙을 따라야 해
>
> **🙋 B** HTTP, HTTPS, FTP 다 프로토콜이야?
>
> **💬 A** 맞아! 각각 용도가 달라  
> HTTP = 웹 문서 전송 / HTTPS = HTTP + TLS 암호화 / FTP = 파일 전송
>
> **🙋 B** HTTPS랑 HTTP 차이가 자물쇠 하나 아니야?
>
> **💬 A** 그 차이가 엄청 커! HTTP는 평문 전송이라 중간에서 볼 수 있어  
> HTTPS는 TLS로 암호화되어서 중간에서 못 읽어  
> 프로토콜 = 언어 규약 — 같은 언어 써야 대화 가능한 것처럼

### 프록시 (Proxy)

`Infra` · Proxy · 추가 2026-10-09

> **클라이언트와 서버 사이에서 요청·응답을 대신 전달하는 중간 서버**

**자세히**

프록시는 클라이언트(브라우저)와 실제 서버 사이에 위치해 요청을 대신 처리하는 중간자다. 보안·캐싱·로드밸런싱·SSL 처리 등을 담당한다. nginx가 대표적인 리버스 프록시로, 외부 요청을 받아 내부 AP 서버로 전달한다.

**흐름**

- ① 클라이언트가 프록시에 요청 전송
- ② 프록시가 실제 서버에 대신 요청
- ③ 서버 응답 → 프록시 수신
- ④ 프록시가 클라이언트에 응답 전달

**헷갈리는 점**

- **흔한 오해** 포워드 프록시 vs 리버스 프록시 혼동
- **차이** 포워드 = 클라이언트 앞에서 외부 요청 대리 / 리버스 = 서버 앞에서 외부 요청 수신
- **기억법** 리버스 프록시 = 서버 쪽 대문지기 — 밖에서 오는 손님(요청)을 안쪽 방(서버)으로 안내

**예시**

- nginx → Node.js 서버로 요청 전달 = 리버스 프록시
- 회사 방화벽 → 직원 인터넷 요청 대신 처리 = 포워드 프록시
- axis.axmaster.cloud:80 → 내부 3000포트로 전달 = 프록시 라우팅
- CDN = 전 세계에 분산된 프록시 서버 네트워크

**카톡으로 이해하기**

> **💬 A** 프록시가 뭔지 알아?
>

>
> **💬 A** 비슷한 개념! 클라이언트와 서버 사이에서 중간 대리인 역할하는 거야
>
> **🙋 B** 왜 직접 연결 안 해?
>
> **💬 A** 여러 이유가 있어. 보안(IP 숨기기), 캐싱(자주 쓰는 데이터 캐시), 접근 제어 같은 거야
>
> **🙋 B** 포워드 프록시랑 리버스 프록시 차이가 뭐야?
>
> **💬 A** 포워드 = 클라이언트 앞에서 외부 요청 대리 (내 IP 숨기기)  
> 리버스 = 서버 앞에 서서 외부 요청 수신 (서버 숨기기, nginx 같은 것)
>
> **🙋 B** 아 nginx가 리버스 프록시구나
>
> **💬 A** 맞아! 리버스 프록시 = 서버 쪽 대문지기야

### 프록시 라우팅 (Proxy Routing)

`Infra` · Proxy Routing · 추가 2026-10-09 · 보강 2026-10-22

> **도메인·경로에 따라 요청을 알맞은 내부 서버로 전달하는 nginx 설정**

**자세히**

프록시 라우팅은 하나의 도메인으로 들어오는 요청을 경로나 서브도메인에 따라 다른 내부 서버(포트)로 보내는 설정이다. axmaster.cloud(녹음기)와 axis.axmaster.cloud(동아리 홈페이지)를 같은 VPS에서 분리 운영할 수 있는 원리다.

**흐름**

- ① 브라우저 → axis.axmaster.cloud 접속
- ② DNS → VPS IP(VPS-IP) 반환
- ③ nginx(80/443포트) 수신
- ④ server\_name axis.axmaster.cloud 블록 매칭
- ⑤ proxy\_pass → localhost:3000으로 전달
- ⑥ Node.js 서버 처리 → 응답 반환
- ⑦ nginx → 브라우저에 응답 전달

**헷갈리는 점**

- **흔한 오해** 프록시 라우팅을 DNS와 혼동
- **차이** DNS = 도메인→IP 변환 / 프록시 라우팅 = IP에 도달한 후 어느 서버(포트)로 전달할지 결정
- **기억법** DNS = 주소 찾기 / 프록시 라우팅 = 주소 찾은 후 어느 방으로 안내할지

**예시**

- axis.axmaster.cloud → 내부 localhost:3000 (동아리 홈페이지)
- axmaster.cloud → 내부 localhost:8000 (녹음기 서비스)
- axmaster.cloud/api → 내부 localhost:4000 (API 서버)
- nginx 설정: proxy\_pass http://localhost:3000

**우리 서버 메모** \[우리 서버 실제 사례\] 우리 VPS의 프록시 라우팅은 nginx 설정 파일이 아니라 Traefik 라벨(traefik.http.routers.&lt;앱>.rule=Host(\`도메인\`))로 한다.

**카톡으로 이해하기**

> **💬 A** 프록시 라우팅이 DNS랑 어떻게 달라?
>
> **🙋 B** 둘 다 어디로 보낼지 결정하는 거 아니야?
>
> **💬 A** 달라! DNS는 도메인→IP 변환이야 — 주소 찾기  
> 프록시 라우팅은 IP에 도달한 후 어느 서버(포트)로 보낼지 결정이야
>
> **🙋 B** 예를 들어줘
>
> **💬 A** axis.axmaster.cloud 접속하면  
> DNS가 IP(VPS-IP) 알려주고  
> 그 IP에서 nginx가 어느 포트로 전달할지 결정해 — 이게 프록시 라우팅이야
>
> **🙋 B** 아 주소 찾기는 DNS, 집 안에서 방 찾기는 프록시 라우팅이네
>
> **💬 A** 딱 맞아! DNS = 주소 찾기 / 프록시 라우팅 = 어느 방으로 안내할지야

### 핑 (Ping)

`Infra` · Ping · 추가 2026-10-09

> **특정 서버가 살아있는지, 응답 시간이 얼마나 걸리는지 확인하는 네트워크 명령어**

**자세히**

Ping은 내 컴퓨터에서 특정 서버에 작은 신호를 보내고 돌아오는 시간을 측정한다. 서버가 응답하면 살아있는 것이고, 응답이 없으면 서버가 죽었거나 네트워크 문제가 있는 것이다. 단위는 ms(밀리초)이며 낮을수록 빠른 연결이다.

**흐름**

- ① ping 명령 실행(ping google.com)
- ② ICMP Echo Request 패킷 전송
- ③ 대상 서버가 ICMP Echo Reply 반환
- ④ 왕복 시간(RTT) 측정·출력
- ⑤ 패킷 손실률 계산

**헷갈리는 점**

- **흔한 오해** 핑(Ping)을 단순 속도로만 이해하는 경우
- **정확한 뜻** Ping = 왕복 응답 시간(RTT, Round Trip Time) — 보내고 받기까지의 시간
- **기억법** 잠수함 소나(음파 탐지) — 소리 보내고 메아리 돌아오는 시간 측정과 동일

**예시**

- ping google.com → 응답시간 12ms = 구글 서버까지 12ms
- 게임에서 '핑 높다' = 서버와의 응답시간이 느려 지연 발생
- ping VPS-IP → VPS 서버 살아있는지 확인
- Request timeout = 서버가 응답 없음 (죽었거나 방화벽 차단)

**카톡으로 이해하기**

> **💬 A** 핑(Ping)이 뭔지 알아?
>
> **🙋 B** 서버 응답 확인하는 거?
>
> **💬 A** 맞아! 특정 서버에 신호 보내고 돌아오는 시간 측정하는 거야  
> ping google.com 이런 식으로 써
>
> **🙋 B** 그럼 ping이 낮을수록 좋은 거야?
>
> **💬 A** 응! ping이 낮다 = 응답이 빠르다 = 레이턴시 낮다는 뜻이야  
> 게임에서 ping 낮아야 딜레이 없이 플레이 가능하잖아
>
> **🙋 B** 정확히 뭘 측정하는 거야?
>
> **💬 A** RTT(Round Trip Time) = 패킷 보내고 받기까지 왕복 시간이야  
> 잠수함 소나 비유 좋아 — 음파 보내고 메아리 돌아오는 시간 측정하는 것처럼
