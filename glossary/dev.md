### API

`Dev` · Application Programming Interface · 추가 2026-10-05

**정의** 두 소프트웨어가 서로 대화하는 방법을 정의한 약속.

**자세히**

프로그램끼리 데이터를 주고받는 '창구' 역할.  
요청(Request)과 응답(Response) 형식을 미리 정해두면 서로 내부 구조를 몰라도 연결할 수 있다.  

비유: 식당에서 손님(프론트엔드)이 메뉴를 주문하면 웨이터(API)가 주방(백엔드)에 전달하고 음식을 가져오는 구조.  

대표 유형:  
- REST API: URL + HTTP 메서드(GET/POST/PUT/DELETE)로 요청
- GraphQL: 필요한 데이터만 골라서 요청
- WebSocket: 실시간 양방향 통신

AI 맥락: ChatGPT·Claude API = 모델에게 프롬프트를 보내고 답을 받는 창구.

**흐름**

- ① 클라이언트가 API 요청 전송(HTTP)
- ② API 서버 수신
- ③ 인증 확인(API Key 등)
- ④ 요청 처리(DB 조회·로직 실행)
- ⑤ JSON 응답 반환
- ⑥ 클라이언트가 응답 처리

**헷갈리는 점**

- **흔한 오해** API를 URL과 혼동하거나 API=서버로 오해
- **차이** API = 두 시스템이 대화하는 약속(규칙) / URL = 그 약속에 접근하는 주소
- **기억법** API = 식당 메뉴판(주문 규칙) / URL = 식당 주소

**카톡으로 이해하기**

> **💬 A** 앱 개발할 때 API 연동한다는 말 자주 듣는데 API가 정확히 뭐야?
>
> **🙋 B** URL 같은 거 아니야?
>
> **💬 A** 달라! API는 두 소프트웨어가 서로 대화하는 약속이야  
> URL은 그 약속에 접근하는 주소고
>
> **🙋 B** 예시 들어줘봐
>
> **💬 A** 식당으로 비유하면, 손님이 메뉴 주문하면 웨이터가 주방에 전달하고 음식 가져오잖아  
> 손님이 프론트엔드, 웨이터가 API, 주방이 백엔드야
>
> **🙋 B** 아 중간 연결해주는 역할이구나
>
> **💬 A** 맞아. 요청(Request)과 응답(Response) 형식을 미리 정해두면  
> 서로 내부 구조를 몰라도 연결할 수 있어  
> API = 메뉴판(주문 규칙) / URL = 식당 주소라고 기억해

### Config (설정 파일)

`Dev` · Configuration · 추가 2026-10-19

**정의** 프로그램의 코드를 고치지 않고도 동작 방식을 바꿀 수 있게, 바꿀 값들을 따로 모아둔 것(설정).

**자세히**

프로그램에는 '바뀌지 않는 로직(코드)'과 '상황마다 바뀌는 값(설정)'이 있다. 포트 번호, 도메인, 사용할 AI 모델, 알림 받을 채팅방 같은 값을 코드 안에 박아두면 바꿀 때마다 코드를 고쳐야 한다. 그래서 이런 값을 config 파일·환경변수로 빼둔다.  

설정을 담는 방법:  
- 설정 파일: config.yaml, config.json, settings.toml
- 환경변수 파일: .env (비밀값은 주로 여기)
- 명령어 옵션: --port 3010 처럼 실행할 때 지정

\[우리 서버 실제 사례\]  
- Hermes: config.yaml 에 사용할 모델·도구 설정
- OpenClaw(AutoPy): \`openclaw config set commands.ownerAllowFrom ...\` 으로 주인 등록
- 서명 사이트: PORT, DATA\_DIR, CREATE\_KEY 를 환경변수로 주입(/root/axis-sign.env)

**흐름**

- ① 바뀔 값을 코드에서 분리
- ② config 파일/환경변수에 저장
- ③ 프로그램 시작 시 읽어옴
- ④ 값만 바꾸고 재시작 → 동작 변경

**헷갈리는 점**

- **흔한 오해** config = 특정 파일 형식이라고 생각
- **차이** config는 '설정'이라는 개념 / YAML·JSON은 그 설정을 적는 '문법(형식)'
- **기억법** config = 가전제품 설정 메뉴, 코드 = 가전제품 내부 회로 — 설정만 바꿔도 동작이 바뀐다

**카톡으로 이해하기**

> **💬 A** config 파일 고치라는데 그게 뭐야?
>
> **🙋 B** 프로그램 설정 모음이야
>
> **💬 A** 코드랑 뭐가 달라?
>
> **🙋 B** 코드는 기계 내부 회로, config는 설정 메뉴  
> 포트 번호, 도메인, AI 모델 같은 걸 코드 안 고치고 바꿀 수 있어
>
> **💬 A** 아 그래서 서명 사이트 키도 파일로 넣은 거구나
>
> **🙋 B** 맞아! 비밀값은 .env 같은 파일로 따로 빼두는 게 원칙이야

**연결 용어** [YAML](#term-118) · JSON · 환경변수 · 배포

### Credentials (크리덴셜)

`Dev` · Credentials · 추가 2026-10-09

> **시스템·서비스에 접근할 수 있는 인증 정보 — 아이디·비밀번호·토큰·키 등**

**자세히**

Credentials는 '내가 이 서비스를 사용할 권한이 있다'는 것을 증명하는 모든 인증 정보를 말한다. 사람의 신분증과 같은 역할이며, 유출되면 보안 사고로 이어지기 때문에 절대 코드에 직접 넣지 않고 환경변수(.env)나 비밀 저장소(Secret Manager)에 보관한다.

**흐름**

- ① 서비스 가입 → Credentials 발급 (API Key, Client ID/Secret)
- ② .env 파일에 저장 (코드에 직접 X)
- ③ .gitignore에 .env 추가 → GitHub 업로드 차단
- ④ 서버에서 환경변수로 읽어 사용
- ⑤ 유출 시 → 즉시 재발급·폐기

**헷갈리는 점**

- **흔한 오해** Credentials를 단순히 '비밀번호'로만 이해하는 경우
- **정확한 뜻** 비밀번호뿐 아니라 토큰·API 키·인증서·OAuth 정보 등 접근 권한을 증명하는 모든 것
- **주의사항** 코드에 직접 쓰면 GitHub에 올릴 때 유출 위험 → .env 파일에 보관 + .gitignore 처리 필수
- **기억법** 신분증(ID) + 열쇠(Key) 묶음 — 이게 있어야 문이 열린다

**예시**

- Google OAuth Client ID + Client Secret = Credentials
- GitHub Personal Access Token = Credentials
- DB 접속 정보 (host, port, username, password) = Credentials
- API Key (OpenAI, Notion 등) = Credentials
- n8n에서 서비스 연결 시 입력하는 인증 정보 = Credentials

**카톡으로 이해하기**

> **💬 A** Credentials(크리덴셜)이 그냥 비밀번호야?
>
> **🙋 B** 영어로 자격증명 아니야?
>
> **💬 A** 더 넓은 개념이야. 비밀번호뿐 아니라 API Key, OAuth 토큰, 인증서까지  
> 접근 권한을 증명하는 모든 것이 Credentials이야
>
> **🙋 B** 왜 이걸 따로 관리해?
>
> **💬 A** 코드에 직접 쓰면 GitHub에 올렸을 때 유출될 수 있어  
> .env 파일에 보관하고 .gitignore에 추가해서 Git에 올라가지 않게 해야 해
>
> **🙋 B** 유출되면 어떡해?
>
> **💬 A** 즉시 재발급·폐기해야 해! 누군가 내 API Key 갖고 있으면 대신 요청 할 수 있어  
> 신분증+열쇠 묶음 — 이게 있으면 문 열린다고 기억해

**연결 용어** [백엔드 인증 (Backend Authentication)](#term-040) · Google OAuth · [API](#term-013) · 환경변수 · 보안

### Git

`Dev` · Git · 추가 2026-10-09

> **코드의 변경 이력을 추적하고 여러 사람이 협업할 수 있게 해주는 버전 관리 시스템**

**자세히**

Git은 파일의 변경 이력을 저장하고, 이전 버전으로 돌아가거나 여러 사람이 동시에 작업할 수 있게 해주는 도구다. 내 컴퓨터(로컬)에서 작동한다. 코드뿐 아니라 모든 텍스트 파일의 버전 관리에 사용된다.

**흐름**

- ① git init — 레포지토리 생성
- ② git add — 변경 파일 스테이징
- ③ git commit — 스냅샷 저장
- ④ git push — 원격 저장소 업로드
- ⑤ git pull — 원격 변경사항 다운로드

**헷갈리는 점**

- **흔한 오해** Git과 GitHub을 같은 것으로 혼동하는 경우가 많음
- **차이** Git = 내 컴퓨터에서 돌아가는 버전 관리 도구 / GitHub = Git 저장소를 온라인에 올리는 서비스
- **비유** Git = 내 일기장 / GitHub = 일기장을 올려두는 클라우드

**예시**

- 어제 작동하던 코드로 되돌리기 → git checkout
- 기능 A와 기능 B를 동시에 개발 → 브랜치(branch) 분리
- '저장'이 아닌 '기록' — 언제 누가 무엇을 바꿨는지 모두 남음
- 구글 Docs의 '수정 이력 보기'와 비슷한 개념

**카톡으로 이해하기**

> **💬 A** Git이 뭔지 설명해봐
>
> **🙋 B** GitHub 아니야?
>
> **💬 A** 달라! Git은 내 컴퓨터에서 돌아가는 버전 관리 도구야  
> GitHub는 Git 저장소를 온라인에 올리는 서비스고
>
> **🙋 B** 버전 관리가 왜 필요해?
>
> **💬 A** 코드 수정하다가 잘못되면 이전 버전으로 돌아갈 수 있어  
> 그리고 여러 명이 협업할 때 충돌 관리도 해줘
>
> **🙋 B** 어떻게 쓰는 거야?
>
> **💬 A** git init으로 시작 → git add로 스테이징 → git commit으로 저장  
> git push하면 GitHub에 올리고, git pull로 받아와  
> Git = 내 일기장 / GitHub = 일기장 올리는 클라우드로 기억해

### GitHub

`Dev` · GitHub · 추가 2026-10-09

> **Git 저장소를 온라인에 올려 협업·공유·배포할 수 있게 해주는 플랫폼**

**자세히**

GitHub는 Git으로 관리하는 코드를 인터넷에 올려두고 여러 사람이 함께 작업할 수 있는 서비스다. 코드 공유·오픈소스·CI/CD 배포·GitHub Pages까지 지원한다. Microsoft가 2018년에 인수했다.

**흐름**

- ① 로컬에서 git push
- ② GitHub 원격 레포에 코드 업로드
- ③ PR(Pull Request) 생성
- ④ 코드 리뷰·승인
- ⑤ main 브랜치에 merge

**헷갈리는 점**

- **흔한 오해** GitHub = Git이라고 오해 / GitLab·Bitbucket과 동일하게 봄
- **차이** Git(도구) ≠ GitHub(서비스) / GitHub·GitLab·Bitbucket은 모두 Git 기반 플랫폼이지만 별개 서비스
- **기억법** Git = 엔진 / GitHub = 엔진을 얹은 자동차(서비스)

**예시**

- 동아리 발표자료 올리기 → github.com/kchmok-art/axis-slides
- 오픈소스 프로젝트 — React, Python, Linux 모두 GitHub에서 관리
- GitHub Pages — 코드를 올리면 자동으로 웹사이트로 서빙
- Pull Request — 내가 고친 코드를 메인 코드에 합쳐달라는 요청

**카톡으로 이해하기**

> **💬 A** GitHub이 Git이랑 어떻게 달라?
>
> **🙋 B** 그냥 같은 거 아니야?
>
> **💬 A** 완전 달라! Git = 버전 관리 도구(내 컴퓨터에 설치) / GitHub = Git 저장소 호스팅 서비스(온라인)  
> Git이 엔진이면 GitHub는 엔진을 얹은 자동차야
>
> **🙋 B** GitHub 없이 Git만 써도 돼?
>
> **💬 A** 응! 혼자 할 때는 로컬에서 git만 써도 충분해  
> GitHub는 여러 명 협업, 코드 공개, PR 리뷰 같은 게 편해서 쓰는 거야
>
> **🙋 B** GitLab이나 Bitbucket도 같은 거야?
>
> **💬 A** Git 기반 플랫폼이라는 점은 같은데, 별개 서비스야  
> GitHub = 개인 개발자·오픈소스 강세 / GitLab = 기업 내부 CI/CD 강세야

### iframe

`Dev` · Inline Frame · 추가 2026-10-09

> **웹페이지 안에 다른 웹페이지를 액자처럼 끼워 넣는 HTML 요소**

**자세히**

iframe은 페이지 안에 또 다른 페이지를 삽입하는 HTML 태그다. 유튜브 영상 임베드, 지도 삽입, 발표자료 뷰어 등에 사용된다. 안쪽 페이지와 바깥 페이지는 서로 독립적으로 작동한다.

**흐름**

- ① 부모 페이지에 &lt;iframe src='URL'> 삽입
- ② 브라우저가 src URL 별도 요청
- ③ 응답받은 페이지를 iframe 영역에 렌더링
- ④ 부모·자식 페이지 독립적으로 작동

**헷갈리는 점**

- **흔한 오해** iframe을 이미지 삽입과 혼동
- **차이** img = 이미지 파일 삽입 / iframe = 다른 웹페이지 전체를 액자로 삽입
- **기억법** iframe = 액자 안에 다른 TV 화면을 넣는 것

**예시**

- 유튜브 영상 공유 → '퍼가기' 코드가 바로 iframe

### URI (Uniform Resource Identifier)

`Dev` · Uniform Resource Identifier · 추가 2026-10-09

> **인터넷에서 자원(페이지·파일·API)을 식별하는 고유한 주소 형식**

**자세히**

URI는 인터넷상의 모든 자원에 고유한 이름을 붙이는 체계다. URL이 URI의 일종이다. URI는 '이 자원이 무엇인가'를 식별하고, URL은 '이 자원이 어디 있는가'까지 포함한다. 실무에서는 URL과 URI를 거의 같은 의미로 사용한다.

**흐름**

- ① 리소스 식별 필요
- ② URI 구조 설계(scheme://host/path?query)
- ③ 클라이언트가 URI로 요청
- ④ 서버가 URI 파싱 → 해당 리소스 반환

**헷갈리는 점**

- **흔한 오해** URI와 URL을 다른 것으로 구분하려다 혼란
- **차이** URL ⊂ URI — URL은 URI의 하위 개념. 실무에서는 거의 같은 의미로 사용
- **기억법** URI = 이름표 / URL = 이름표 + 주소까지 포함

**예시**

- https://axis-is.kr/slides — URI이자 URL
- http://VPS-IP:3000/auth/google/callback — Google OAuth 리디렉션 URI
- mailto:운영자 메일 — URI지만 URL은 아님 (위치가 아닌 식별자)
- API endpoint: /api/users/123 — URI로 특정 사용자 자원 식별

**카톡으로 이해하기**

> **💬 A** URI랑 URL이 다른 거야?
>
> **🙋 B** 그냥 같은 거 아니야?
>
> **💬 A** URL이 URI 안에 포함돼! URI = 리소스 식별자 전체 개념, URL = 주소 포함한 식별자
>
> **🙋 B** 그럼 URL이 더 좁은 개념이야?
>
> **💬 A** 맞아. URL ⊂ URI야  
> 'https://example.com/page' 이게 URL이고 URN(이름만 있는 것) 같은 것도 URI에 포함돼
>
> **🙋 B** 실무에서 구분해서 써야 해?
>
> **💬 A** 실무에서는 거의 같은 의미로 써. 큰 차이 없어  
> URI = 이름표 / URL = 이름표 + 주소까지 포함이라고 기억해  
> scheme://host/path?query 이 구조가 URI/URL 기본 형태야

### 리다이렉트 (Redirect)

`Dev` · Redirect · 추가 2026-10-09

> **특정 URL에 접속하면 자동으로 다른 URL로 보내버리는 것**

**자세히**

Redirect는 사용자가 A 주소로 접속했을 때 서버나 브라우저가 자동으로 B 주소로 보내는 동작이다. 로그인이 필요한 페이지에 비로그인 상태로 접근하면 로그인 페이지로 보내는 것이 대표적 사용 사례.

**흐름**

- ① 사용자가 A URL 요청
- ② 서버가 302(임시)/301(영구) 응답 + Location: B URL
- ③ 브라우저가 B URL로 자동 재요청
- ④ B URL 페이지 표시

**헷갈리는 점**

- **흔한 오해** 301과 302 차이 모름
- **차이** 301 = 영구 이동(검색엔진이 URL 변경으로 인식) / 302 = 임시 이동(검색엔진은 원래 URL 유지)
- **기억법** 301 = 이사 완료(주소 변경) / 302 = 임시 자리 비움

**예시**

- 로그인 안 한 상태로 발표자료 URL 접속 → 자동으로 로그인 페이지로 이동
- http://사이트.com → https://사이트.com 으로 자동 이동 (보안 리다이렉트)
- 구 URL → 새 URL로 자동 이동 (페이지 주소 바뀔 때)
- 결제 완료 → 자동으로 완료 페이지로 이동

### 리다이렉트 URI (Redirect URI)

`Dev` · Redirect URI · 추가 2026-10-09

> **OAuth 인증 완료 후 인증 코드를 받아올 서버 주소 — 사전에 등록된 주소만 허용**

**자세히**

Redirect URI는 OAuth 인증 흐름에서 구글·카카오 등 인증 서버가 인증 완료 후 사용자를 돌려보낼 주소다. 보안을 위해 반드시 사전에 등록된 주소만 허용하며, IP 주소는 허용하지 않고 도메인만 허용한다. 미등록 주소로 요청하면 에러가 발생한다.

**흐름**

- ① Google 콘솔 → Redirect URI 사전 등록 (axis-is.kr/auth/google/callback)
- ② 사용자 → 로그인 버튼 클릭
- ③ 서버 → Google 인증 URL로 이동 (redirect\_uri 파라미터 포함)
- ④ Google → 인증 완료 → 등록된 Redirect URI로 코드 전달
- ⑤ 서버 → 코드 수신 → 토큰 교환 → 로그인 완료

**헷갈리는 점**

- **흔한 오해** Redirect URI에 IP 주소 입력해도 된다고 생각하는 경우
- **정확한규칙** Google OAuth는 공개 도메인만 허용. localhost는 개발용으로 예외 허용
- **기억법** 초대장에 적힌 주소(사전 등록) = Redirect URI — 주소가 다르면 입장 불가

**예시**

- http://axis-is.kr:3000/auth/google/callback — 등록된 Redirect URI
- Google OAuth 설정에서 '승인된 리디렉션 URI'에 반드시 사전 등록 필요
- IP(VPS-IP)로 등록 시 에러 → 반드시 도메인으로 등록
- localhost:3000/auth/google/callback — 개발 환경용 Redirect URI

**카톡으로 이해하기**

> **💬 A** Redirect URI가 뭔지 알아? OAuth에서 나오는 거
>
> **🙋 B** 리디렉션 주소?
>
> **💬 A** 맞아! Google OAuth 인증 후 코드를 받을 서버 주소야  
> Google 콘솔에 사전 등록해둔 주소로만 콜백이 와
>
> **🙋 B** 왜 미리 등록해야 해?
>
> **💬 A** 보안 때문이야. 악의적인 사이트가 우리 Client ID 훔쳐서  
> 자기 주소를 Redirect URI로 쓰면 인증 코드를 탈취할 수 있어  
> 등록된 주소로만 보내게 해서 막는 거야
>
> **🙋 B** IP 주소로 등록하면 안 돼?
>
> **💬 A** Google OAuth는 공개 도메인만 허용해. localhost는 개발용으로 예외야  
> 초대장에 적힌 주소 = Redirect URI — 주소 다르면 입장 불가

### 리디렉션 (Redirection)

`Dev` · Redirection · 추가 2026-10-09

> **사용자를 A 주소에서 B 주소로 자동으로 이동시키는 것**

**자세히**

리디렉션은 특정 URL로 접속했을 때 서버나 브라우저가 자동으로 다른 URL로 보내는 동작이다. HTTP 상태코드로 구분되며 301(영구 이동), 302(임시 이동)이 대표적이다. 보안·인증·페이지 이동에 핵심적으로 사용된다.

**흐름**

- ① 사용자 → A URL 접속
- ② 서버 → 301/302 응답 + Location: B URL 헤더 전송
- ③ 브라우저 → B URL로 자동 재요청
- ④ B URL 페이지 표시

**헷갈리는 점**

- **흔한 오해** 리디렉션(Redirection)과 리다이렉트(Redirect)는 같은 말
- **차이** Redirect = 동사(행위) / Redirection = 명사(현상) — 실무에서 혼용
- **301_vs_302** 301 = 영구 이동(SEO에 영향) / 302 = 임시 이동(SEO 영향 없음)
- **기억법** 도로 공사 우회로 표지판 — 원래 길 막히면 자동으로 다른 길로 안내

**예시**

- 로그인 안 한 상태로 발표자료 접속 → 로그인 페이지로 리디렉션
- http://axis-is.kr → https://axis-is.kr 자동 이동 (보안 리디렉션)
- Google OAuth: 로그인 완료 → /auth/google/callback으로 리디렉션
- 구 도메인 → 신 도메인 자동 이동 (301 영구 리디렉션)

**카톡으로 이해하기**

> **💬 A** 리디렉션이 리다이렉트랑 달라?
>
> **🙋 B** 같은 말 아니야?
>
> **💬 A** Redirect = 동사(행위), Redirection = 명사(현상)이야. 실무에선 혼용해
>
> **🙋 B** 언제 써?
>
> **💬 A** 사이트 주소 바뀌었을 때 옛날 링크도 새 주소로 보내주거나  
> 로그인 안 된 상태에서 마이페이지 들어오면 로그인 페이지로 보내는 거
>
> **🙋 B** 301이랑 302 차이가 뭐야?
>
> **💬 A** 301 = 영구 이동. 검색엔진이 새 URL로 업데이트해서 SEO에 영향 줘  
> 302 = 임시 이동. 검색엔진 그대로 유지야
>
> **🙋 B** 그럼 도메인 이전할 때는 301이네
>
> **💬 A** 맞아! 도로 공사 우회로 표지판 — 원래 길 막히면 자동으로 다른 길로 안내

### 백엔드 인증 (Backend Authentication)

`Dev` · Backend Authentication · 추가 2026-10-09

> **서버에서 '이 사용자가 누구인지, 접근 권한이 있는지' 확인하는 처리**

백엔드 인증은 두 단계로 나뉜다. 인증(Authentication): 이 사람이 누구인가 (로그인). 인가(Authorization): 이 사람이 이걸 볼 권한이 있는가 (접근 제어). 동아리 홈페이지에서 Google 로그인 후 발표자료 접근 허용이 대표 사례다.

**흐름**

- ① 로그인 요청(이메일·비번 or OAuth)

- ③ 세션·토큰 발급
- ④ 이후 요청마다 토큰 확인(인가·Authorization)
- ⑤ 권한 없으면 403 반환

**헷갈리는 점**

- **흔한 오해** 인증(Authentication)과 인가(Authorization) 혼동
- **차이** 인증 = 누구인가(신분 확인) / 인가 = 이걸 할 권한이 있는가(권한 확인)
- **기억법** 인증 = 신분증 확인 / 인가 = 입장권 확인

**예시**

- Google 로그인 → 서버가 토큰 발급 → 이후 요청마다 토큰 확인 = 인증
- 로그인은 됐지만 관리자 페이지는 못 들어감 = 인가(권한) 처리
- JWT 토큰, 세션, OAuth — 모두 백엔드 인증 방식
- 동아리 홈페이지: Google 계정이 화이트리스트에 있는지 서버에서 확인 = 백엔드 인증

**카톡으로 이해하기**

> **💬 A** 백엔드 인증이 뭐야?
>
> **🙋 B** 로그인 확인하는 거 아니야?
>
> **💬 A** 맞아! 사용자가 누구인지 확인하고, 어떤 권한 있는지 검증하는 거야
>
> **🙋 B** 어떻게 확인하는 거야?
>
> **💬 A** 로그인하면 서버가 토큰(JWT 같은 거) 발급해줘  
> 이후 요청마다 그 토큰을 보내면 백엔드가 검증해서 신원 확인해
>
> **🙋 B** 아 매번 아이디/비밀번호 보내는 게 아니구나
>
> **💬 A** 맞아. 토큰이 신분증 역할이야. 서버가 '이 토큰 진짜야? 어떤 권한이야?' 확인하는 게 인증  
> 인증(Authentication) = 신원 확인 / 인가(Authorization) = 권한 확인이야

### 백엔드 처리 (Backend Processing)

`Dev` · Backend Processing · 추가 2026-10-09

- ② 인증·인가 확인

- ④ 비즈니스 로직 실행

**헷갈리는 점**

- **차이** 실제로는 웹서버·AP서버·DB서버·캐시 서버 등이 협력해서 처리
- **기억법** 백엔드 처리 = 팀 플레이 — 각 서버가 역할 분담

**예시**

- 게시글 작성 → 서버 수신 → 유효성 검사 → DB 저장 → 성공 응답
- 백엔드 처리 = 인증 + 로직 + DB + 응답의 전체 파이프라인

**구조**

**카톡으로 이해하기**

>
> **💬 A** 암호화가 아니라 해시야. 그래서 복호화도 안 돼
>
> **🙋 B** 복호화가 뭔데?
>
> **💬 A** 암호화된 걸 키로 원본 되돌리는 거야. 근데 해시는 단방향이라 복호화 불가능해  
> 그래서 로그인할 때 입력한 비밀번호를 같이 해시해서 저장된 값이랑 비교하는 거야

> **🙋 B** 아 그래서 비밀번호 찾기가 아니라 재설정이구나

> **💬 A** 맞아! 복호화는 열쇠(키) 있어야 금고 열린다고 기억해

### 암호화

`Dev` · Encryption · 추가 2026-10-05

**정의** 데이터를 열쇠(키)가 있어야만 읽을 수 있도록 변환하는 것. 보안이 목적이다.

**자세히**

인코딩과 결정적 차이: 암호화는 '키(Key)'가 없으면 원본을 복원할 수 없다.  

종류:  
- 대칭키 암호화: 암호화·복호화에 같은 키 사용 (AES 등). 빠르지만 키 공유가 문제.
- 비대칭키 암호화: 공개키로 암호화, 개인키로 복호화 (RSA 등). HTTPS가 이 방식.
- 해시: 단방향 변환 — 복호화 불가. 비밀번호 저장에 사용 (SHA-256, bcrypt 등).

실생활 예시:  
- HTTPS = 브라우저와 서버 사이 통신을 암호화
- 카카오톡 암호화 = 메시지를 서버에서도 읽지 못하게 보호
- 비밀번호 해시 = DB에 비밀번호를 그대로 저장하지 않고 해시값으로 저장

**흐름**

- ① 원본 데이터(평문)
- ② 암호화 키 준비
- ③ 암호화 알고리즘 적용(AES, RSA 등)
- ④ 암호문 생성
- ⑤ 전송·저장
- ⑥ 수신 측에서 키로 복호화

**헷갈리는 점**

- **흔한 오해** 대칭키와 비대칭키 혼동
- **차이** 대칭키(AES) = 같은 키로 암호화·복호화 / 비대칭키(RSA) = 공개키로 암호화, 개인키로 복호화
- **기억법** HTTPS = 비대칭키로 세션키 교환 → 이후 대칭키로 통신

**카톡으로 이해하기**

> **💬 A** HTTPS 쓰면 데이터가 안전하다는 게 무슨 뜻이야?
>
> **🙋 B** 그냥 잠금 표시 있으면 안전한 거 아니야?
>
> **💬 A** 맞긴 한데 원리가 암호화야. 데이터를 키 없이는 못 읽게 변환하는 거
>
> **🙋 B** 인코딩이랑 다른 거야?
>
> **💬 A** 완전히 달라. 인코딩은 키 없이 누구나 되돌릴 수 있는데  
> 암호화는 키 있는 사람만 원본 볼 수 있어
>
> **🙋 B** 암호화도 종류가 있어?
>
> **💬 A** 응. 대칭키는 같은 키로 암호화·복호화 다 하고(빠름)  
> 비대칭키는 공개키로 암호화하고 개인키로 복호화해 — HTTPS가 이 방식  
> 해시는 단방향이라 복호화 아예 불가능해. 비밀번호 저장에 써

### 워커 (Worker)

**자세히**

Worker는 Queue에서 작업을 하나씩 꺼내 처리하는 프로세스(프로그램)다. 큐가 '대기줄'이라면 워커는 '직원'이다. 워커를 여러 개 띄우면 작업을 병렬로 빠르게 처리할 수 있다.

**흐름**

- ① 워커 프로세스 실행 시작
- ② 큐에서 작업 꺼냄(dequeue)
- ③ 작업 처리
- ④ 완료 후 다시 큐에서 다음 작업 꺼냄
- ⑤ 큐가 빌 때까지 반복

**헷갈리는 점**

- **흔한 오해** 워커와 서버를 같은 것으로 혼동
- **차이** 서버 = 요청 수신·응답 / 워커 = 큐에서 작업 꺼내 처리(응답 없이 실행만)
- **기억법** 서버 = 카운터 직원 / 워커 = 주방 직원

**예시**

- 🍔 맥도날드 비유 — 주문서(큐)를 받아서 실제로 버거를 만드는 직원(워커)
- 🖨️ 프린터 비유 — 인쇄 대기열(큐)에서 문서를 꺼내 출력하는 프린터 엔진(워커)
- 🤖 AI 이미지 생성 — 요청 큐에서 작업을 꺼내 GPU로 이미지를 만드는 서버 프로세스
- 워커 3개 = 직원 3명 — 같은 큐를 3명이 동시에 처리하면 3배 빨라짐

**카톡으로 이해하기**

> **💬 A** 워커(Worker)가 뭔데? 일꾼이야?
>
> **🙋 B** 뭔가 처리하는 프로세스?
>
> **💬 A** 맞아! 큐에 쌓인 작업을 하나씩 꺼내서 처리하는 프로세스야  
> 이메일 발송, 파일 변환 같은 백그라운드 작업 담당해
>
> **🙋 B** 큐랑 같이 쓰는 거야?
>
> **💬 A** 항상 세트야. 큐에 작업 쌓고 → 워커가 꺼내서 처리하는 구조  
> 워커 여러 개 띄우면 동시에 처리할 수 있어
>
> **🙋 B** 아 그럼 워커 많을수록 빨리 처리되는 거네
>
> **💬 A** 맞아. 근데 워커가 많으면 서버 자원도 많이 써. 균형이 중요해  
> 큐=대기줄, 워커=카운터 직원으로 생각해

AI 에이전트 맥락: Claude Code·Codex 같은 코딩 에이전트가 멀티 에이전트 병렬 작업 시 각 에이전트에게 독립적인 워크트리를 할당해 서로 충돌 없이 동시에 코드를 수정하는 용도로 활용.

- ④ 작업 완료 후 git worktree remove로 제거

**헷갈리는 점**

- **흔한 오해** 워크트리를 브랜치와 동일시
- **차이** 브랜치 = 코드 분기 / 워크트리 = 브랜치를 별도 폴더에 동시에 체크아웃해서 작업하는 방법
- **기억법** 브랜치 = 나뭇가지 / 워크트리 = 가지별로 작업실을 따로 만든 것

**카톡으로 이해하기**

>

>
> **💬 A** 달라! 브랜치는 코드의 분기점(논리적 개념)이고  
> 워크트리는 브랜치를 물리적으로 다른 폴더에 펼쳐놓은 거야
>
> **🙋 B** 그럼 같은 저장소에서 두 개 작업 동시에 할 수 있어?
>
> **💬 A** 그게 바로 워크트리의 핵심이야. git worktree add 명령으로  
> 브랜치를 별도 폴더에 체크아웃해서 동시에 작업할 수 있어
>
> **🙋 B** 왜 그냥 브랜치 두 개 만들면 안 돼?
>
> **💬 A** 브랜치 전환할 때마다 파일이 바뀌잖아. 워크트리는 폴더가 따로 있어서 동시에 열어놓을 수 있어  
> 브랜치=나무의 가지, 워크트리=가지마다 별도 작업 책상 놓은 것

### 워크트리 (Worktree)

`Dev` · Git Worktree · 추가 2026-10-09

> **하나의 Git 저장소에서 여러 브랜치를 동시에 다른 폴더에서 작업하는 Git 기능**

**자세히**

Git Worktree는 하나의 저장소(.git)를 공유하면서 여러 브랜치를 각각 다른 폴더에 체크아웃해 동시에 작업할 수 있는 기능이다. 브랜치를 왔다갔다 전환할 필요 없이 여러 작업을 병렬로 진행할 수 있다. 멀티 AI 에이전트가 각자 독립된 작업 공간에서 동시에 개발할 때 활용된다.

**흐름**

- ① git worktree add ../branch-folder branch명
- ② 새 폴더에 브랜치 체크아웃
- ③ 두 폴더 동시 작업
- ④ git worktree remove로 제거

**헷갈리는 점**

- **흔한 오해** 브랜치(Branch)와 워크트리(Worktree)를 같은 개념으로 혼동
- **차이** 브랜치 = 코드의 분기점(논리적 개념) / 워크트리 = 브랜치를 물리적으로 다른 폴더에 펼쳐놓은 것
- **기억법** 브랜치 = 나무의 가지 / 워크트리 = 가지마다 별도 작업 책상을 놓은 것

**예시**

- 기능 A 개발 중에 긴급 버그 수정 필요 → 워크트리로 별도 폴더에서 동시 작업
- AI 에이전트 3개가 각자 다른 기능을 병렬 개발 → 워크트리로 충돌 없이 분리
- git worktree add ../feature-b feature-b → feature-b 브랜치를 별도 폴더에 체크아웃
- 멀티 에이전트 코딩의 핵심 인프라 — 에이전트마다 독립 작업 공간 제공

**카톡으로 이해하기**

> **💬 A** 워크트리 명령어 써봤어? git worktree
>
> **🙋 B** 그게 뭐야? 처음 봐
>
> **💬 A** Git 저장소 하나에서 여러 브랜치를 동시에 다른 폴더에 펼쳐두는 거야  
> AI 에이전트로 병렬 작업할 때 특히 유용해
>
> **🙋 B** 브랜치 여러 개 만들면 되는 거 아니야?
>
> **💬 A** 브랜치는 논리적 분기점이고, 워크트리는 그걸 물리적 폴더로 분리하는 거야  
> 브랜치 전환 없이 두 폴더 동시에 열어서 작업할 수 있어
>
> **🙋 B** 어떻게 써?
>
> **💬 A** git worktree add ../other-branch branch명 하면  
> ../other-branch 폴더에 그 브랜치 체크아웃 돼  
> 브랜치=나무의 가지, 워크트리=가지마다 별도 책상 놓은 것

### 인코딩

**자세히**

인코딩은 보안이 목적이 아니라 '형식 변환'이 목적이다.

- URL 인코딩: 공백→%20, 한글→%EC%95%88 등 URL에 쓸 수 없는 문자를 변환
- UTF-8: 한글·한자 등 문자를 컴퓨터가 읽는 바이트로 변환하는 문자 인코딩

LLM 맥락: 토크나이저가 텍스트를 토큰 ID(숫자)로 변환하는 것도 인코딩의 일종.

**흐름**

- ① 원본 데이터(텍스트·이미지 등)
- ② 인코딩 규칙 적용 (UTF-8, Base64 등)
- ③ 변환된 형식으로 저장·전송
- ④ 수신 측에서 디코딩으로 복원

**헷갈리는 점**

- **흔한 오해** 인코딩과 암호화를 같은 것으로 혼동
- **차이** 인코딩 = 형식 변환(키 없이 누구나 복원 가능) / 암호화 = 보안 변환(키 있어야 복원)
- **기억법** 인코딩 = 번역 / 암호화 = 금고에 넣기

**카톡으로 이해하기**

> **💬 A** Base64 인코딩이라는 거 봤는데 이거 암호화야?
>
> **🙋 B** 겉보기엔 알아볼 수 없으니까 암호화 아니야?
>
> **💬 A** 아니! 인코딩이랑 암호화는 달라  
> 인코딩은 보안이 목적이 아니라 형식 변환이 목적이야  
> 규칙만 알면 누구나 원래대로 되돌릴 수 있어
>
> **🙋 B** 아 그럼 Base64는 어떤 상황에서 써?
>
> **💬 A** 이미지나 파일을 텍스트로 전송할 때 써. 이메일 첨부파일이나 HTML 인라인 이미지 같은 거  
> URL 인코딩은 공백이나 한글 같이 URL에 못 쓰는 문자를 변환할 때 쓰고
>
> **🙋 B** 그럼 암호화는 뭐가 달라?
>
> **💬 A** 암호화는 키(Key)가 있어야 원본 복원이 가능해. 보안이 목적이지  
> 인코딩은 번역이고, 암호화는 금고에 넣는 거로 기억해

- **기억법** 쿠키 = 도서관 대출증 — 내가 들고 다니며 매번 제시 / 세션 = 도서관 대출 기록 — 서버가 보관

**예시**

- 로그인 후 브라우저 닫았다 열어도 로그인 유지 = 쿠키에 세션 ID 저장
- 쇼핑몰 장바구니 — 로그인 안 해도 담긴 것 기억 = 쿠키
- Google Analytics — 방문자 추적에 쿠키 사용
- AX:IS 홈페이지: 로그인 → 서버가 세션 ID를 쿠키로 발급 → 이후 요청마다 자동 전송

### 큐 (Queue)

`Dev` · Queue · 추가 2026-10-08

> **먼저 들어온 것이 먼저 나가는 줄 세우기 자료구조 (FIFO)**

**자세히**

Queue는 First In, First Out(FIFO) 구조로, 먼저 들어온 데이터가 먼저 처리된다. 줄 서기와 동일한 원리. 작업 대기열, 메시지 큐, API 요청 순서 처리 등에 활용된다.

**흐름**

- ① 작업 생성 → 큐에 추가(enqueue)
- ② 큐가 순서대로 작업 보관(FIFO)
- ③ 워커가 큐에서 작업 꺼냄(dequeue)
- ④ 작업 처리
- ⑤ 완료 후 다음 작업 꺼냄

**헷갈리는 점**

- **흔한 오해** 큐(Queue)와 스택(Stack) 혼동
- **차이** 큐 = FIFO(먼저 들어온 게 먼저 나감) / 스택 = LIFO(나중에 들어온 게 먼저 나감)
- **기억법** 큐 = 줄 서기(편의점) / 스택 = 접시 쌓기(위에서부터 꺼냄)

**예시**

- 🍔 맥도날드 주문 — 손님이 주문(큐에 넣기) → 주방이 순서대로 만들기(큐에서 꺼내기)
- 🖨️ 프린터 — 문서 3개를 동시에 보내도 먼저 보낸 것부터 출력
- 📱 카카오톡 알림 — 메시지 10개가 한꺼번에 와도 순서대로 표시
- 🤖 AI 이미지 생성 — 요청 100개가 몰려도 먼저 요청한 사람부터 처리
- 💬 개발자 말투: '큐 날린다' = 작업을 대기열에 집어넣는다

**비유** 편의점 계산대 줄 — 나중에 온 사람이 새치기하면 안 되듯, 큐도 순서를 반드시 지킨다

**카톡으로 이해하기**

> **💬 A** 큐(Queue)가 뭔지 알아?
>
> **🙋 B** 줄 서는 거 아니야?
>
> **💬 A** 맞아! 데이터 구조에서도 줄 서는 것처럼 먼저 들어온 게 먼저 나가는 거야  
> FIFO(First In First Out) 구조
>
> **🙋 B** 실제로 어디서 쓰는 거야?
>
> **💬 A** 이메일 발송, 동영상 변환, 알림 전송 같은 시간이 걸리는 작업을  
> 바로 처리하지 않고 큐에 쌓아두고 순서대로 처리해
>
> **🙋 B** 아 비동기 처리 같은 거네?
>
> **💬 A** 맞아! 큐 없으면 요청 100개 동시에 들어오면 서버 터지잖아  
> 큐에 넣고 워커가 하나씩 꺼내서 처리하는 거야. 큐=대기줄로 기억해

**예시**

- 경매사이트 목업 — 상품 목록·입찰 버튼·가격 표시 위치를 HTML로 미리 그려봄
- 피그마(Figma)로 로그인 화면 목업 제작 → 개발자에게 전달
- 동아리 홈페이지 — 발표자료 카드 레이아웃을 목업으로 먼저 확인 후 개발
- 종이에 손으로 그린 것도 목업 — 도구보다 '미리 그려보는 행위'가 핵심

**도구**

- **전문 도구** Figma, Adobe XD, Sketch
- **간단 도구** PowerPoint, Canva, Notion
- **코드 목업** HTML/CSS로 직접 제작 (지금 하는 방식)

**카톡으로 이해하기**

> **💬 A** 화면 목업이 뭔지 알아?
>
> **🙋 B** 디자인 시안 같은 거?
>
> **💬 A** 맞아! 실제처럼 보이는 정적 화면이야. 색상·폰트·이미지 다 있는데 클릭은 안 돼
>
> **🙋 B** 와이어프레임이랑 다른 거야?
>
> **💬 A** 와이어프레임은 뼈대만 있어. 위치·구조만 박스와 선으로 표현하고 디자인 없어  
> 목업은 실제처럼 보이는 정적 디자인이야
>
> **🙋 B** 그럼 프로토타입은?
>
> **💬 A** 클릭하면 반응하는 인터랙티브 버전이야  
> 와이어프레임=집 설계도 / 목업=모델하우스 외관 / 프로토타입=들어가볼 수 있는 모델하우스
>
> **🙋 B** 순서가 있어?
>
> **💬 A** 와이어프레임 → 목업 → 프로토타입 → 개발 순서야
