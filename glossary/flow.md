### 흐름: AI 계층 구조

`ML` · Flow: AI Hierarchy · 추가 2026-10-09

> **AI → 머신러닝 → 딥러닝 → 인공신경망 → Transformer → LLM → Agent**

**흐름**

- AI (인공지능) — 기계가 인간처럼 생각·판단하게 하는 기술 전체
- └ 머신러닝 — 데이터로 스스로 학습하는 AI
-   ├ 지도학습 / 강화학습 / 비지도학습
-   └ 딥러닝 — 신경망을 깊게 쌓은 머신러닝
-     └ 인공신경망 — 뉴런 구조 모방
-       ├ CNN (이미지) / RNN·LSTM (순서) / GAN (생성)
-       └ Transformer — 어텐션 기반 현대 주류 구조
-         └ LLM — 대규모 텍스트 학습한 Transformer
-           └ AI Agent — LLM이 도구를 쓰며 자율 실행

**카톡으로 이해하기**

> **💬 A** AI랑 머신러닝이랑 딥러닝이 어떤 관계야?
>
> **🙋 B** 다 비슷한 거 아니야?
>
> **💬 A** 포함 관계야! AI > 머신러닝 > 딥러닝 순서야  
> AI = 가장 큰 개념, 기계가 인간처럼 생각하게 하는 모든 기술
>
> **🙋 B** 머신러닝이 AI 안에 있는 거구나
>
> **💬 A** 맞아! 머신러닝 = 데이터로 스스로 학습하는 AI  
> 딥러닝 = 신경망 깊게 쌓은 머신러닝
>
> **🙋 B** 그럼 LLM은?
>
> **💬 A** LLM = 대규모 텍스트로 학습한 Transformer 기반 딥러닝이야  
> AI > ML > 딥러닝 > 신경망 > Transformer > LLM > AI Agent 순서야  
> 러시아 마트료시카 인형처럼 안에 포함되어 있어

### 흐름: AI 에이전트 폴더 잠금

`Agent` · Flow: Locking an AI agent to one folder · 추가 2026-10-23

> **지침 ≠ 권한 → 권한 설정 → 샌드박스 → 우회로 차단 → 테스트 8종 → (민감하면) VM**

**정의** 지침이 아닌 설정으로 AI 에이전트를 작업 폴더(D:\\AX)에 가두고, 우회 경로까지 테스트로 확인하는 순서.

**자세히**

\[lecture\_016 기준\]  
Codex(Windows): 권한 프로필 workspace-only(:root deny, :workspace 쓰기, network off) + MXC/elevated 샌드박스 + approval\_policy never.  
Claude Code(WSL2): blockReadsOutsideWorkingDirectories + sandbox(enabled, failIfUnavailable, allowUnsandboxedCommands false) + dontAsk + Edit(//mnt/d/AX/\*\*) 허용 + WSL interop 끄기.  
공통 점검: MCP·훅·커넥터는 별도. 테스트는 AI의 말이 아니라 실제 오류·탐색기로 판정.

**흐름**

- ① 지침만으론 안 된다는 것 인식
- ② 도구별 권한 설정 (Codex 프로필 / Claude blockReads)
- ③ 샌드박스 켜기 + 못 켜면 시작 거부
- ④ 우회로 차단 (interop 끄기, 샌드박스 밖 재시도 금지, MCP·훅 점검)
- ⑤ 테스트 8종: 밖 읽기·C드라이브·스크립트·쓰기·powershell.exe·touch ~·외부접속 차단 + AX 안 정상
- ⑥ 민감자료면 VM으로 분리

**헷갈리는 점**

- **흔한 오해** 설정 파일을 저장하면 끝났다고 생각함
- **차이** 버전·OS·대체 샌드박스에 따라 설정이 조용히 무시될 수 있다. 막히는 걸 직접 봐야 완료
- **기억법** '설정했다'가 아니라 '막히는 걸 봤다'가 완료

**카톡으로 이해하기**

> **💬 A** AI를 AX 폴더에만 가두는 순서 알려줄까?
>
> **🙋 B** 그냥 'AX만 봐'라고 하면 안 돼?
>
> **💬 A** 그건 부탁이지 잠금이 아니야. 설정으로 막아야 해
>
> **🙋 B** 설정만 하면 끝?
>
> **💬 A** 샌드박스 켜고, 우회로도 막아야 해. WSL이면 윈도우 프로그램 실행 기능도 꺼
>
> **🙋 B** 그다음엔?
>
> **💬 A** 테스트 8개. 밖은 다 막히고 AX 안만 되는지 직접 확인  
> 개인정보 있으면 아예 VM에서 돌리고

**자세히**

\[2026-10-31 보강\] 이 진화선 옆에 다른 가지들도 있다 — 기반(InfraOps·CloudOps·GitOps·FinOps), 보안(DevSecOps·SecOps), 데이터(DataOps), 행동(AgentOps), 반대 방향(AIOps), 방식(ChatOps). 전체 지도는 '흐름: Ops 패밀리 지도 (식당 비유)'.

**흐름**

- ① DevOps — 코드 배포·운영 자동화 (2010년대)
- ② MLOps — AI 모델도 코드처럼 배포·관리 필요 (2018~)
- ③ LLMOps — LLM 특화 운영 과제 등장 (2023~)

- **MLOps** ⭐⭐⭐⭐ — 기술 중상단
- **LLMOps** ⭐⭐⭐⭐⭐ — 기술 최상단

**핵심** AX는 Ops보다 쉬운 게 아니라 레이어가 다름. AX=전략·방향 / Ops=구현·운영. AX를 잘 하려면 Ops가 무엇인지는 알아야 하지만 직접 구현할 줄 알 필요는 없음.

**카톡으로 이해하기**

>
> **💬 A** 맞아! DevOps가 먼저고, AI 붐 타면서 MLOps, LLM 등장하면서 LLMOps야
>
> **🙋 B** 각각 핵심이 뭐야?
>
> **💬 A** DevOps = 코드 배포·운영 자동화 (2010년대)  
> MLOps = AI 모델도 코드처럼 배포·관리 (2018년~)

### 흐름: DevOps 사이클

`Infra` · Flow: DevOps Lifecycle · 추가 2026-10-09

> **Plan → Code → Build → Test → Release → Deploy → Operate → Monitor → (반복)**

**흐름**

- ① Plan — 기능 계획·이슈 등록 (Jira, GitHub Issues)
- ② Code — 코드 작성·Git 커밋·Push (Git, GitHub)
- ③ Build — 소스코드 → 실행 패키지 변환 (Docker Build)
- ④ Test — 자동화 테스트 실행 (Jest, pytest)
- ⑤ Release — 버전 부여·배포 승인
- ⑥ Deploy — 서버 자동 배포 (GitHub Actions, CI/CD)
- ⑦ Operate — 서버 운영·자동 확장 (Kubernetes)
- ⑧ Monitor — 실시간 관제·알림 (Grafana)
- → 다시 ①로 — 무한 반복

**예시 장면**

동아리 홈페이지 개발: 로그인 기능 계획 → 코드 작성 → 빌드 → 테스트 → 배포 → 서버 운영 → 모니터링 → 다음 기능 계획

**카톡으로 이해하기**

> **💬 A** DevOps 사이클 8단계 흐름 설명해봐
>
> **🙋 B** Plan이랑 Monitor는 알겠는데 중간이 헷갈려
>
> **💬 A** Plan(기획) → Code(개발) → Build(빌드) → Test(테스트)  
> → Release(릴리즈) → Deploy(배포) → Operate(운영) → Monitor(관제)야
>
> **🙋 B** 이게 한 번으로 끝이야?
>
> **💬 A** 아니! 무한 반복이야. Monitor에서 문제 발견하면 다시 Plan으로 돌아가
>
> **🙋 B** CI/CD가 어느 구간이야?
>
> **💬 A** Build~Test~Deploy 구간 자동화가 CI/CD야  
> 코드 올리면 자동으로 빌드·테스트·배포까지 가는 거지  
> 이 사이클이 빠르게 돌수록 서비스가 빠르게 발전해

### 흐름: Google OAuth 인증

`Dev` · Flow: Google OAuth · 추가 2026-10-09

> **로그인 버튼 → Google 인증 → 토큰 발급 → 권한 확인 → 서비스 접근**

**흐름**

- ① 사용자 → '구글로 로그인' 버튼 클릭
- ② 서버 → Google OAuth URL로 리다이렉트
- ③ Google 로그인 페이지 → 사용자 구글 계정 인증
- ④ Google → 서버에 인증 코드 전달 (callback)
- ⑤ 서버 → Google에 코드로 액세스 토큰 교환
- ⑥ 서버 → 이메일·프로필 정보 수신
- ⑦ 서버 → 화이트리스트 확인 (동아리원 여부)
- ⑧ 통과 → 세션 발급 → 발표자료 접근 허용
- ⑨ 실패 → 접근 거부 페이지로 리다이렉트

**예시 장면**

동아리 홈페이지: 구글 로그인 → 이메일 확인 → 동아리원이면 발표자료 열람 허용

**카톡으로 이해하기**

> **💬 A** Google OAuth 인증 흐름이 어떻게 돼?
>
> **🙋 B** 구글로 로그인 버튼 누르면 되는 거 아니야?
>
> **💬 A** 버튼 뒤에 단계가 많아!  
> 버튼 클릭 → Google 로그인 페이지로 리다이렉트 → 구글 계정 인증 → 서버에 코드 전달이야
>
> **🙋 B** 코드가 뭐야?
>
> **💬 A** Google이 인증 성공했다는 증거로 서버에 코드 보내줘  
> 서버가 그 코드로 Google에게 액세스 토큰 교환 요청해
>
> **🙋 B** 그다음이 로그인 완료야?
>
> **💬 A** 아직! 토큰으로 이메일·프로필 받아서, 화이트리스트 확인하고, 통과하면 세션 발급해  
> 그래야 로그인 완료야
>
> **🙋 B** 아 구글이 인증하지만 우리 서버가 최종 권한 결정하는 거구나

### 흐름: TLS 핸드셰이크

`Infra` · Flow: TLS Handshake (TLS 1.3) · 추가 2026-10-22

> **인사(Hello) → 인증서 제시 → 검증 → 세션 키 생성 → 암호화 통신**

**정의** HTTPS 연결 직전에 브라우저와 서버가 인사하며 암호 방식을 정하고, 인증서를 확인하고, 비밀 열쇠를 만드는 과정.

**자세히**

TLS 1.3은 이 과정을 왕복 1번으로 줄여서 TLS 1.2보다 빠르다.  
핵심: 공개키 방식은 '서로 처음 만나 열쇠를 안전하게 나누는 데'만 쓰고, 실제 대화는 빠른 대칭키(세션 키)로 암호화한다.  

\[우리 서버 실제 사례 · 2026-10-22 직접 확인\] 우리 서버 연결 결과: Protocol TLSv1.3, Cipher TLS\_AES\_128\_GCM\_SHA256 → AES 128bit로 내용을 암호화하고 SHA-256으로 무결성을 확인한다는 뜻.

**흐름**

- ① Client Hello — 브라우저: 'TLS 1.3 쓸 수 있고, 이런 암호 방식이 가능해' + 열쇠 재료
- ② Server Hello — 서버: '이 방식으로 하자' + 열쇠 재료
- ③ 서버가 인증서(+중간 인증서) 제시 + 인증서의 진짜 주인이라는 서명
- ④ 브라우저가 인증서 체인·주소·유효기간 검증
- ⑤ 양쪽이 같은 세션 키를 각자 계산 (열쇠 자체는 오가지 않음)
- ⑥ Finished — 이후 모든 HTTP 내용이 세션 키로 암호화

**헷갈리는 점**

- **흔한 오해** 인증서 안의 공개키로 모든 내용을 암호화한다고 생각함
- **차이** 공개키는 신원 확인·열쇠 합의 단계에만 쓴다. 본문은 연결마다 새로 만든 세션 키(대칭키)로 암호화한다 — 빠르고, 나중에 서버 키가 털려도 지난 대화는 안전(전방 보안)
- **기억법** 처음 만나 신분증 확인하고 암호표 정하는 데 1분, 그 뒤 대화는 암호표로

**카톡으로 이해하기**

> **💬 A** HTTPS 접속할 때 0.1초 사이에 뭐가 일어나는지 알아?
>
> **🙋 B** 그냥 연결되는 거 아니야?
>
> **💬 A** 핸드셰이크라는 인사 과정이 있어  
> 브라우저가 '나 이런 암호 쓸 수 있어' 하면 서버가 '이걸로 하자' 해
>
> **🙋 B** 그다음엔?
>
> **💬 A** 서버가 인증서 보여주고, 브라우저가 진짜인지 확인해  
> 그리고 둘이 각자 같은 비밀 열쇠를 계산해. 열쇠는 안 주고받아
>
> **🙋 B** 인증서 공개키로 다 암호화하는 거 아니었어?
>
> **💬 A** 그건 처음 인사할 때만이야. 실제 대화는 그 비밀 열쇠로 암호화해  
> 우리 서버는 TLS 1.3에 AES 128비트 쓰고 있어

### 흐름: 루프 기본 사이클

`Agent` · Flow: Basic Loop Cycle · 추가 2026-10-21

> **트리거 → 일 → 검증 → 완료(사람 확인) / 실패 시 다시**

**정의** 트리거 → 에이전트가 일한다 → 검증 → (통과) 완료·보고 / (실패) 다시. 상한 도달 시 사람 호출.

**자세히**

\[lecture\_015 루프 엔지니어링 입문\]  
공식: 루프 = 시작 조건 + 일 + 검사 + 멈춤 + 사람이 보는 지점  
로봇청소기 비유: 정해진 시간에 출발(트리거) → 청소(일) → 센서로 확인(검증) → 도킹(완료). 배터리 부족 = 상한선, 막히면 사람 부름 = 사람 호출 지점.

**흐름**

- ① 트리거 — 시간 또는 사건으로 시작
- ② 에이전트 — 도구를 쓰며 일한다
- ③ 검증 — 테스트·검사로 기계가 확인
- ④ 실패 → ②로 돌아가 다시
- ⑤ 통과 → 완료, 멈추고 사람에게 보고
- ⑥ 상한 도달 → 멈추고 사람 호출
- ⑦ 사람이 확인

**헷갈리는 점**

- **흔한 오해** '완료'를 AI가 '다 했어요'라고 말한 시점으로 봄
- **차이** 완료는 검증 통과 시점. AI의 말이 아니라 검사가 정한다
- **기억법** 로봇청소기 — 센서가 '깨끗함'이라고 해야 도킹한다

**카톡으로 이해하기**

> **💬 A** 루프가 어떻게 도는지 한 줄로 말해볼까?
>
> **🙋 B** 좋아
>
> **💬 A** 트리거 → 일 → 검증 → 통과하면 완료, 실패하면 다시
>
> **🙋 B** 로봇청소기 같네?
>
> **💬 A** 딱 그거야! 시간 되면 출발, 청소, 센서로 확인, 다 됐으면 도킹  
> 배터리 없으면 멈추고, 막히면 사람 불러
>
> **🙋 B** 완료는 AI가 다 했다고 할 때야?
>
> **💬 A** 아니, 검사를 통과했을 때야. 루프 = 시작 조건 + 일 + 검사 + 멈춤 + 사람이 보는 지점

- ③ 실제값과 비교: 우도 / 마진 / 불순도 / 손실
- ④ 규칙 조정: 계수 / 결정함수 / 분할 / 가중치
- ⑤ 새 데이터로 판단·검증(교차검증·테스트)

- **차이** 뼈대는 같고 '차이를 재는 자'와 '고치는 대상'만 다름
- **기억법** 같은 요리 순서, 다른 레시피

**예시**

- lecture\_017 4장: 세 접근을 같은 뼈대 위에 올려 비교

**카톡으로 이해하기**

>
> **🙋 B** 같은 요리 순서에 레시피만 다른 거네
>
> **💬 A** 그거야. 은닉층 없는 신경망은 아예 로지스틱 회귀랑 같아

**정의** 월요일 아침 트리거 → 카드 7장 초안 → 기계 검사 → 채점 AI(9점 이상) → 실패 시 재시도(최대 5바퀴) → 사람이 사실 확인 후 게시.

**자세히**

\[lecture\_015 루프 엔지니어링 입문\]  
실제 실행 결과(글만 채점): 기계 검사 5바퀴 모두 통과, 채점 7.8 → 8.0 → 8.6 → 8.8 → 8.8(기준 9.0 미달) → 5바퀴 상한에서 멈추고 사람 호출 → 사람이 브리프와 대조해 승인.  
채점 코멘트 예: '카드1 제목만 보면 누가 한 말인지 몰라 의외성이 죽음', '카드4 앤드류 응의 실험은 브리프에 없는 표현'.  

그림까지 채점(만드는 쪽에 손, 채점 쪽에 눈): 8.5 → 8.7 → 8.6 → 8.9 → 9.1로 5바퀴 통과. 하지만 카드2는 3바퀴 그림이 더 분명했고 시각 점수는 1.4 → 1.6으로 거의 그대로, 합계를 올린 건 글 항목.  

교훈: 루프는 점수를 올린다. 좋아진다는 보장은 없다. ①검사하는 것만 좋아진다 ②만드는 쪽이 고칠 수 있는 것만 고쳐진다 ③채점 기준이 일관되지 않으면 결과도 일관되지 않다.

**흐름**

- ① 트리거: 월요일 아침
- ② 주제 백로그에서 하나 선택, 브리프의 사실만 사용해 카드 7장 초안
- ③ 기계 검사: 글자 수·금칙어·해상도·숫자 출처
- ④ 채점 AI(다른 컨텍스트): 훅·한 장 한 메시지·행동 유도·출처 → 9점 이상?
- ⑤ 미달 → ②로 재시도 (최대 5바퀴)
- ⑥ 상한 도달 or 통과 → 검토 폴더
- ⑦ 사람이 사실 확인 후 게시

**헷갈리는 점**

- **흔한 오해** 채점 점수가 올랐으니 결과물이 좋아졌다
- **차이** 점수는 채점 기준이 보는 것만 반영. 실제 그림 품질은 그대로거나 나빠질 수도 있다
- **기억법** 시험 점수 ≠ 실력 — 채점표에 없는 건 안 좋아진다

**카톡으로 이해하기**

> **💬 A** 루프로 카드뉴스 만든 실험 알아?
>
> **🙋 B** 어떻게 했는데?
>
> **💬 A** 초안 7장 → 기계 검사 → 채점 AI가 9점 이상인지 봐. 최대 5바퀴
>
> **🙋 B** 결과는?
>
> **💬 A** 7.8에서 8.8까지 올랐는데 9.0을 못 넘었어. 5바퀴에서 멈추고 사람 불렀지
>
> **🙋 B** 그림까지 보게 하면 더 좋아지지 않아?
>
> **💬 A** 점수는 9.1로 통과했어. 근데 어떤 카드는 3바퀴 그림이 더 나았어  
> 시각 점수는 거의 그대로고 글 점수가 합계를 올린 거야
>

### 흐름: 쿠버네티스 큰 주방 지도 (클러스터→노드→Pod→컨테이너)

`Infra` · Flow: Kubernetes Kitchen Map · 추가 2026-11-02

> **주방(클러스터) > 화구(노드) > 쟁반(Pod) > 요리(컨테이너) + 주문서·창구·검수**

**정의** 쿠버네티스 용어를 '큰 주방' 하나에 겹쳐 본 지도. 크기 순서와 각자 하는 일을 한 줄로 잇는다.

**흐름**

- ① 클러스터 = 큰 주방 — 서버 여러 대를 한 대처럼
- ② 쿠버네티스 = 주방장 — 어느 화구에 무엇을 올릴지 결정
- ③ 노드 = 화구 — 클러스터에 묶인 서버 한 대
- ④ Pod = 쟁반 — 같이 나갈 컨테이너 묶음, 일회용
- ⑤ 컨테이너 = 요리 — 이미지(포장된 상자)로 만든 실행 중인 앱
- ⑥ 디플로이먼트 = 상시 주문서 — '쟁반 항상 N개, 새 레시피로 하나씩 교체'
- ⑦ 서비스 = 고정 픽업 창구 — 쟁반이 바뀌어도 손님은 같은 창구로
- ⑧ Argo CD = 검수 담당 — 레시피북(Git)과 주방을 계속 대조해 맞춤

**헷갈리는 점**

- **흔한 오해** 크기 순서와 '설정' 대 '실물' 구분
- **차이** 실물(크기 순): 클러스터 > 노드 > Pod > 컨테이너 / 설정(주문서·창구): 디플로이먼트·서비스는 실물을 어떻게 유지·연결할지 적은 것
- **기억법** 주방 > 화구 > 쟁반 > 요리, 그리고 주문서와 창구

**예시 장면**

새 버전 배포: 개발자가 Git의 디플로이먼트 YAML에서 이미지 1.3으로 수정 → Argo CD가 감지 → 쿠버네티스가 노드들 위의 Pod를 하나씩 1.3으로 교체 → 서비스는 같은 이름 그대로 새 Pod로 손님 연결 → 문제 시 Git을 이전 커밋으로 되돌려 롤백. \[우리 서버 실제 사례\] 우리 VPS는 쿠버네티스 없이 도커 컨테이너만 쓴다 — 쟁반(Pod) 없이 요리(컨테이너)를 화구에 바로 올리는 구조라 Pod·Deployment·Service가 없다. 대신 정문 역할은 Traefik이 한다 (2026-10 대화에서 확인한 구성 기준)

**카톡으로 이해하기**

> **💬 A** 쿠버네티스 용어가 너무 많아
>
> **🙋 B** 클러스터, 노드, 파드… 뭐가 큰 거야?
>
> **💬 A** 주방 > 화구 > 쟁반 > 요리 순서야  
> 클러스터 > 노드 > Pod > 컨테이너
>
> **🙋 B** 디플로이먼트랑 서비스는?
>
> **💬 A** 그건 실물이 아니라 주문서랑 창구야  
> '쟁반 3개 유지'가 디플로이먼트, '바뀌지 않는 픽업 창구'가 서비스
>
> **🙋 B** Argo CD는?
>
> **💬 A** 레시피북(Git)이랑 주방을 계속 대조하는 검수 담당
